# 分包本地持久化：P1 现状与 P2 设计输入

> 结论先说：**P1 没有"安装分包到本地"这一步。** P1 只产出一份 H5 构建，财务分包随基座一起发布，
> 浏览器按普通静态资源缓存。真正的"下载 → 校验 → 落盘 → 激活"属于 P2 的远程下发，本仓尚未实现。
>
> 本文取代 2026-10-09 的草案。那一版假设了 `uni.registerBundle`、wgt 文件目录结构和
> `v1.0.0/current` 符号链接等并不存在的 API/能力，不能作为实现依据。

## 1. P1：H5 静态缓存

P1 的"按需"发生在构建期与路由层：

- 构建期：`pages.json` 把已出生面（P1 = finance）作为 subPackage，Vite 产出独立的
  `assets/pages-finance-*.js` chunk；未出生面零 chunk（PRD 18.2#9）。
- 运行期：进入财务面时才加载对应 chunk，这是浏览器的模块加载，不需要下载安装包。
- 持久化：资源 URL 带 content hash，服务器对 `/releases/base/{版本}/` 下发
  `Cache-Control: public, max-age=31536000, immutable`；升级版本即换 URL。
- 清单：`GET /api/homeos/app/bundles` 每次按需读取（响应很小），服务端从内嵌清单作答；
  `installed` 参数在 P1 只接收不解释，因为客户端还没有本地安装物可比对。
- 版本检查：登录后静默请求 `GET /api/homeos/app/version`，失败不阻断首屏（PRD 3.4.8）。

因此 P1 的缓存清理就是普通 Web 缓存清理：发布新版本、nginx 换 URL、旧版本目录择期删除。
没有"清除分包缓存"这个客户端动作。

## 2. P2：远程下发的持久化（设计输入，未实现）

P2 每个面独立打包后，客户端才需要把面包落到本地。下面这些是**待定设计**，不是现有代码：

### 2.1 需要的能力

| 能力 | 说明 | 状态 |
|---|---|---|
| 下载 | 按清单 `url` 取面包，支持超时与重试 | 未实现 |
| 校验 | 先比 `size`，再算 sha256；不符即丢弃 | 未实现 |
| 落盘 | 写临时文件 → 校验通过 → 原子改名为 `{code}/{version}` | 未实现（P2） |
| 索引 | 记录 `{code, version, sha256, size, 安装时间}`，启动时可快速判断 | 未实现（P2） |
| 激活 | 新版本下载完成后，下次冷启动切换；不打断当前会话 | 未实现（P2） |
| 清理 | 保留当前版 + 上一版；用户可手动清除某面缓存 | 未实现（P2） |

### 2.2 平台差异（实现前必须先确认）

- **App（uni-app 打包）**：文件读写走 `plus.io`（HTML5+）或原生插件；存储目录由平台给出，
  路径不能写死。P1 的 `web/src/manifest.json` 里 `appid` 为空，当前只能构建 H5，**P1 无法验证
  App 侧持久化**——这是 P2 的验收前置，不是本文能承诺的。
- **H5**：不能把 JS 包"安装"到本地再动态执行（会绕过同源/完整性约束）；能做的是 HTTP 缓存或
  Service Worker 预缓存，后者是否采用由 P2 决定。
- **小程序**：主包/分包体积上限由平台强制，不能做运行时替换。

### 2.3 与清单的关系

清单里的 `sha256`/`size` 是校验依据；`min_compat` 是兼容门槛。客户端流程（P2）：

```
读 app/bundles?codes=已启用面&installed={本地索引}
  → 逐面比较 (code, version)
  → 需要更新：下载 → 校验 size/sha256 → 临时目录 → 原子改名
  → 校验失败：保留旧版本，该面显示「暂不可用」，基座与其他面不受影响
  → 校验通过：更新本地索引，下次冷启动激活
```

服务端的清单接口不需要为持久化改协议；客户端本地索引只影响它传什么 `installed`。

## 3. 不做的事

- 不在 P1 引入 wgt 下载/安装、符号链接指针、差分更新；
- 不自动删除用户已下载的面包（清理策略待 P2 定）；
- 不把运行期缓存目录提交进仓库（见 `.gitignore`）。
