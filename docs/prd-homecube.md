# 家立方 HomeCube 产品需求文档

**产品名称：** 家立方 HomeCube
**产品定位：** 全家生活一站式管理 App
**品牌 Slogan：** 全家生活，立体管理。
**面目录（当前六面）：** 财务、采购、饮食、出行、家人、成长 —— 面目录由 registry 持续扩展，一个家庭实际拥有哪些面由家庭管理员配置（17.8）
**系统架构：** 一个底层系统 HomeOS + 六个业务系统
**设计原则：** 一面一系统，系统有边界，数据有归属，联动靠事件。
**迭代原则：** 不设 MVP，按 P1-P6 分期交付，由 Agent 全流程推进，人类负责目标与验收。
**端的形态：** iOS 与 Android 为主形态，H5 随技术栈天然具备并作为 Web 的过渡形态；一期不做桌面级 Web 客户端，平板与折叠屏走响应式兜底。

> **本文档的读法**
> 这是 HomeCube 的唯一需求文档，按可交付口径撰写：每个系统给出定位、边界、详细需求、数据模型、接口与验收标准；跨面的归属、权限、导航、依赖、分级与排期单列成章。
> 正文只写现行口径，不写修订过程。三处内容受控（数据归属权威表 16.2、权限矩阵 15.3、验收口径十八章），修改需人类批准；条款见二十三章。

## 一、产品概述

### 1.1 产品背景

家庭日常生活涉及钱、物、吃、行、人、成长六大核心场景，但现有工具高度碎片化：记账用记账 App，购物用清单 App，菜谱用菜谱 App，提醒用日历 App，家庭成员信息分散在微信、备忘录、相册中。家庭缺少一个统一入口，也缺少面与面之间的自动流转。

家立方 HomeCube 以"一个家，六个面"为核心理念，把家庭生活管理拆成**面目录当前的六个**完整业务系统（面目录由 registry 持续扩展，且一个家庭实际挂载哪些面由管理员配置，17.8），每面独立完整，面间通过底层能力拉通，形成家庭生活闭环。

### 1.2 产品定位

- **一句话定位：** 全家生活一站式管理 App。
- **品牌 Slogan：** 全家生活，立体管理。
- **六面一句话：** 钱有账，物有库，吃有谱，行有程，人有录，长有迹。
- **产品形态：** iOS、Android 为主形态；H5 随技术栈天然具备并作为 Web 的过渡形态，**本版不做桌面级 Web 客户端**；平板与折叠屏走响应式兜底；智能家居接入属六期之外的远景，不在本版承诺范围。
- **目标用户：** 有家庭生活管理需求的个人与家庭，覆盖无娃家庭、有娃家庭、有老人家庭、养宠家庭。
- **单人可用原则：** 六面在**无家庭（单人）状态下必须完整可用**，加入家庭只是把数据从个人域提升到家庭域并开启协作。理由：家庭协作类工具的真实失败模式是"一人记录，全家不用"，冷启动必须由单人独立价值支撑。每一面在其**出生期**的交付都必须包含"一个人的完整闭环"。

### 1.3 设计原则

1. **每面独立完整**：每一面是一个完整业务系统，内部高内聚，外部低耦合。
2. **交互因面而异**：不追求六面交互一致。财务偏数据报表，采购偏清单勾选，饮食偏图片卡片，出行偏时间线地图，家人偏档案标签，成长偏记录打卡。一级导航为例外，全 App 统一（见十七章）。
3. **底层拉通**：时间、日历、提醒、待办、人员、权限、通知、同步、动态、搜索、AI 归类，全部下沉为底层基础能力。
4. **面间联动**：通过底层事件总线与规则引擎，不直接耦合。
5. **去 MVP 化**：不以最小可用为目标。在新模型下这条有明确的可执行含义——**一面在其出生期一次做完整面（闭环 + 深度域同批交付）**，不出现「这面先上简版、下期再补」。**P1 的财务面是这条原则的样板**：底座之外，财务的记账闭环与借还款、储蓄目标、AA 分账、净资产在同一条期里做完。跨面联动能力（规则引擎）本身按 P6 交付，属分期而非砍功能。
6. **Agent 驱动**：需求、设计、开发、测试、部署、文档、复盘由 Agent 协作推进，人类负责目标、优先级、验收与伦理。

### 1.4 名词定义

| 名词 | 定义 |
|---|---|
| 面 | 六大业务域之一，如财务面、采购面 |
| 系统 | 一个面即一个完整系统，如财务系统 |
| 底层 | 六面共用的基础系统 HomeOS |
| 事件总线 | 系统间联动的基础设施 |
| 规则引擎 | 系统间自动流转的配置中心。与总线分离：总线是 P1-M1 底座能力，规则引擎是 P6 产品能力 |
| 期 | 迭代期（P1-P6）。**每期严格交付一个面**（P1 额外含 HomeOS 底座、前端 shell 与财务面），期与期串行推进，期末验收未过不得进入下一期；P1 内部再分 M1/M2 两个验收点 |
| 出生期 | 一个面（及其服务、schema、迁移序列、前端分包）被创建的那一期。六面依次为：财务 P1、采购 P2、饮食 P3、家人 P4、成长 P5、出行 P6。**该面的全部验收项在其出生期末判定** |
| 服务随面出生 | 服务端只在某面的出生期创建它的服务，不预建空服务、空 schema、空分包；七个 code 的命名域在 P1 一次性登记 registry（卷首第 12 项） |
| Agent | 参与研发全流程的智能体 |
| **系统 code** | 七系统的英文标识，用于事件命名与接口前缀：`homeos` / `finance` / `purchase` / `diet` / `trip` / `kin` / `growth`（见 16.1）。家人系统取 `kin`，避免与 HomeOS 的 `Family` 实体同名 |
| **权威源** | 一个数据对象唯一的归属系统，只有归属系统可写入；其他系统为只读引用方 |
| **生成型单据** | 由跨面事件自动产生的业务对象，带 `generated_by` 事件标记；可编辑，被人工删除即视为冲正，事件重放不再重建 |

## 二、系统总览

### 2.1 系统分层

家立方由 **7 个系统**组成：

| 层级 | 系统 | code | 定位 | 建设方式 |
|---|---|---|---|---|
| 底层 | 家庭操作系统 HomeOS | `homeos` | 六面共用的基础系统 | **全新建**（身份、家庭、权限、日历到期、通知、同步、事件总线、搜索均在本仓库内从零实现，遵循十四章的工程约定） |
| 业务层 | 财务系统 | `finance` | 管钱 | **全新建**（账本与流水口径以本文档第四章为需求基线，代码与表结构在本仓库内从零实现） |
| 业务层 | 采购系统 | `purchase` | 管物 | 新建 |
| 业务层 | 饮食系统 | `diet` | 管吃 | 新建 |
| 业务层 | 出行系统 | `trip` | 管行 | 新建 |
| 业务层 | 家人系统 | `kin` | 管人 | 新建 |
| 业务层 | 成长系统 | `growth` | 管长 | 新建 |

七个系统同仓、**各自一个服务**（monorepo + 七服务，卷首第 12 项）：每个 code 同时是服务名、路由域 `/api/{code}/*`、事件前缀 `{code}.`、schema 名与迁移序列前缀；服务间经 NATS JetStream 与只读接口通信，跨面读取方式见 16.3，实现层约束见 22.2。本需求与任何既有项目不存在代码、表结构、迁移、数据与部署层面的复用关系，复用边界与两套系统并存的政策见十四章。

一句话：

> **一个底层系统 + 六个业务系统。**
> **底层管连接，六面管生活。**

七个服务之间**没有共享内存、没有跨 schema SQL、没有分布式事务**；唯一的同步读路径是只读接口，唯一的跨面写效果路径是事件。

### 2.3 系统设计原则

1. **一面一系统**：每个面是一个完整系统，内部高内聚，外部低耦合。
2. **系统有边界**：每个系统明确"做什么、不做什么"。
3. **数据有归属**：每个数据对象**有且只有一个归属系统**，归属系统是唯一可写方；其他系统通过只读接口或事件订阅消费，**不得建立字段同构的第二套实体**。全量清单见十六章「数据归属权威表」。
4. **能力不重复**：时间、权限、通知、同步等能力只在底层实现。到期型对象（有 `due_at`/`schedule`/`expire_at`/`trigger_at` 语义的）必须在 HomeOS 注册，以便被到期中心与日历聚合，注册契约见 16.4。
5. **交互可异构**：每个系统按自己的业务逻辑设计交互，不强制统一。一级导航除外（见 1.3 第 2 条与十七章）。
6. **联动靠事件，读取可调用**：跨面的状态变更与联动一律经底层事件总线最终一致（3.4.6）；实时读取走归属服务的只读接口（16.3）。**不在请求链路上调用他服务的写能力**，一次请求同步 fan-out 至多 1 个他服务。
7. **系统可独立**：每个业务系统是**独立进程、独立部署、独立发布、独立迁移序列**的服务，可独立交付、可独立验收；但运行期依赖 HomeOS 服务的权限、到期提醒与同步契约，不能脱离底座运行。"可独立成 App"只在六期之外的远景下成立，不作为设计约束。**服务随面出生**（卷首第 12 项、11.1）：本条说的是一个服务出生后的形态，不是 P1 就要有七个服务。

### 2.4 关键场景串联

需求文档的验收以功能域为单位，但交付判定必须回到场景。以下为六条**贯穿链路验收场景**：一期一面下，一条场景通常横跨多个面，因此**按可跑的步骤段在其依赖面出生期判，完整链路在其最晚出生面的期末判**，P6 期末六条全部复跑（对应 18.6 场景验收）：

| 场景 | 链路 | 涉及面 | 完整链路判定期 |
|---|---|---|---|
| S1 周末吃什么 | 家人面看忌口 → 饮食面点菜投票 → 生成周菜单 → 菜单生成采购清单 → 采购完成 → 库存入库 → 费用进财务 | 家人→饮食→采购→财务 | **P4**（忌口属 `kin`，P3 只能跑到「菜单→清单→入库→流水」段） |
| S2 一次旅行 | 出行面建行程 → 旅行预算与行李清单 → 采购面出游物资 → 行程结束费用归集进财务（标记项目=旅行账本） | 出行→采购→财务 | **P6**（出行面出生期） |
| S3 孩子兴趣班 | 成长面排课程 → 课程进 HomeOS 日历 + 上课提醒 → 费用归集财务 → 接送排班到出行面 | 成长→HomeOS→出行→财务 | **P6**（P5 判到费用归集段） |
| S4 老人生日 | 家人面纪念日提前 7 天 → 礼物心愿转采购清单 → 采购完成费用进财务 → 生日当天提醒全家 | 家人→采购→财务→HomeOS | **P4** |
| S5 库存补货 | 采购面库存低于阈值 → 自动加购 → 买齐入库 → 临期食材在饮食面推荐菜谱 | 采购→饮食 | **P3**（P2 判到自动加购段） |
| S6 月度收口 | 财务面月报 → 预算超支事件广播 → 各面在首页标注超支来源 | 财务→全部 | **P6**（P1-M2 判「月报 + HomeOS 下发」段） |

分段判定不降低目标值：**在完整链路判定期之前，未出生的面不得被计入「失败」**，也不得因此把该段永久免除（18.1 延后判定条）。每条链路的**数据一致性检查点**与判定口径见 18.6。

## 三、底层系统：家庭操作系统 HomeOS

### 3.1 系统定位

HomeOS 是六面共用的基础系统，负责**连接、协调、支撑**，不直接面向家庭业务。它相当于家庭生活的"操作系统"，六面是运行其上的"原生应用"。

### 3.2 系统边界

**做：**
- 家庭、成员、角色、权限
- 时间、日历、提醒、待办、周期任务
- 通知、消息、动态、协作
- 数据同步、备份、加密、导出
- 全局搜索、语音、拍照、AI 归类
- 事件总线与规则引擎，分两批交付：**P1-M1 交付事件总线骨架**（事件定义/发布/订阅/日志/幂等/重试/死信/版本），**P6 交付规则引擎**（规则配置/优先级/模拟测试）
- 设置、主题、账号、安全

**不做：**
- 不做记账、清单、菜谱、行程、档案、成长记录等业务
- 不存储业务数据，只做索引与引用
- 不定义业务规则，只提供规则执行能力

**底座新建范围与结构要求**：HomeOS 的账号体系、家庭体系、权限模型、离线同步**全部新写**。新底座自第一版起必须满足以下结构约定，违反任意一条即视为架构缺陷：
- 模型按领域分层（身份域与财务域不同包），有 service 层；展示字段不靠 ORM 旁路（如 `gorm:"-"`）在 handler 里拼装。
- 路由带系统前缀（`/api/{system}/*`），不允许扁平根路径。
- JWT claims 携带 `family_id`、角色与权限快照；权限判定在中间件统一生效，不允许业务 handler 用裸 SQL `family_id = ?` 现场判定。
- 一个账号可属多个家庭并显式区分当前会话家庭，不支持"一人隐式一个家庭"。
- 所有业务对象带 `version` 字段（乐观锁）。

### 3.3 系统职责

| 职责 | 说明 | 建设范围 |
|---|---|---|
| 身份与权限 | 谁是谁、谁能看什么、谁能改什么 | **全新建**：验证码登录、邀请入家、**多家庭与当前家庭上下文**、四级角色、模块/数据/操作三维权限、字段级可见性（十五章）。其中 JWT claims 携带 `family_id`/角色/权限、Role/Permission 表齐备、一账号多家庭三项，**从第一版就必须做对**，不得后补。 |
| 时间与提醒 | 所有系统的时间触发统一由底层处理 | **全新建**：日历、提醒、待办、周期任务、到期中心均从零实现。 |
| 通知与协作 | 所有系统的消息、动态、投票统一由底层处理 | **全新建**：推送通道（APNs/厂商）+ 站内兜底 + 动态流 + 留言 + 投票。推送通道是新建能力，不得按已有触达能力排期；站内通知接口形态（列表/已读/全部已读）见 3.7。 |
| 数据与同步 | 所有系统的数据同步、备份、加密统一由底层处理 | **全新建**：离线队列 + 重放 + 幂等键 + **版本乐观锁冲突策略**（3.4.4）。冲突策略按 3.4.4 的对象分类表执行，不接受「FIFO + 服务端时间戳决胜」的整库单一策略。 |
| 智能与搜索 | 所有系统的搜索、语音、拍照、AI 归类统一由底层处理 | **全新建**：OCR、语音、AI 归类均自建并新签供应商（十九章）；全局搜索从数据模型阶段即考虑六面数据投影。 |
| 事件与规则 | 所有系统之间的联动统一由底层事件总线与规则引擎处理 | **全新建**。 |
| 设置与安全 | 全局设置、账号、安全、隐私统一由底层处理 | **全新建**：设置必须是活配置（写入即生效，禁止只做静态展示层）；审计日志、数据分级落地（二十章）新建。 |

### 3.4 详细需求

#### 3.4.1 家庭核心

- 创建家庭、加入家庭、切换家庭、解散家庭
- 面配置：管理员开通/停用本家庭使用哪些面（17.8），新家庭创建时强制选面
- 邀请成员：链接、二维码、邀请码、通讯录
- 成员管理：添加、编辑、移除、转让管理员
- 角色：管理员、成人成员、儿童/老人、访客
- 权限：模块级、数据级、操作级
- 隐私：字段级可见性、财务隐私、健康隐私、儿童保护

细化规则：

- **切换家庭**：多家庭是底座的一等设计。一个账号 ≤5 个家庭，可切换；切换后重建上下文缓存（权限、币种、时区、投影表全部按 `family_id` 重新装载），同账号跨家庭的数据不合并。JWT claims 必须携带 `family_id` 与角色快照，**七个服务共用由 HomeOS 发布的鉴权 SDK**，在各自中间件统一校验当前会话家庭的 `family_id` 隔离（15.6、22.2 第 5 条），不允许业务 handler 用裸 SQL 现场判定。
- **儿童/老人成员**：**允许无账号成员**（`Member.user_id` 可为空），由监护人代管，代管人写入时携带 `on_behalf_of`；无账号成员不可登录、不出现在邀请列表。这是家人面与成长面能建模"被记录者"的前提。
- **权限三级维度**定义与默认矩阵见 **十五章**。
- **面配置变更**：仅管理员可开通/停用本家庭的某个面（`scope = module`，15.2）。变更写入 `homeos_family_module`（带 `version` 乐观锁）→ 落审计 + `pver+1` + 发 `homeos.family.module.updated` → 各服务失效 module 缓存、客户端重建首页矩阵与五个导航消费位（≤2 秒，18.2#9）。**开通不创建任何业务数据，停用不删数据、不改变统计口径**（17.8）。
- **解散家庭**：需管理员 + 二次确认；数据保留 30 天冷存后可导出，逾期物理删除（口径见 21.4）。

#### 3.4.2 时间系统

- 日历：家庭共享、个人、多视图（日/周/月/年）
- 提醒：单次、周期、位置、到期
- 待办：创建、分配、完成、归档、子任务
- 周期任务：每天/周/月/年、自定义、跳过、顺延
- 到期中心：聚合六面所有到期事项
- 通知：推送、站内信、@、免打扰、分组；**站内通知必须分型为 `budget_alert`（预算预警）/ `system`（系统与家庭事件）/ `reminder`（到期与待办）三类**，消息列表按型分组，App 图标与底部「消息」Tab 显示**未读红点与计数**（进入列表即读、"全部已读"可批量），顶栏消息入口显示**同一口径的未读红点（只显点、不显数）**，两处的熄灭时机一致——分型与未读口径由 HomeOS 唯一持有，业务面不得自建通知类型与红点（17.7 第 1 条；顶栏位的呈现分工与同源断言见 17.1；面停用后该面的深链行为才是第 2 条）

**到期中心机制**：到期中心不是"轮询六面私有库"，而是六面按 **16.4 注册契约**把到期型对象登记为 HomeOS 的 `CalendarEvent` / `Todo` / `Reminder`，HomeOS 是唯一聚合与触发方。六面**不得自建推送链路**。字段映射、删除与完成回写语义见 16.4。

**位置提醒限制**：iOS/Android 后台定位权限受限，位置提醒（如"到超市提醒"）默认降级为地理围栏 + 失败即回落到时间提醒，需在设置里明示不保证触达。到达率指标（3.8，≥99.9%）不含位置类提醒，度量口径见 18.2。

#### 3.4.3 协作系统

- 动态流：六面所有变更、完成记录
- 留言：家庭留言板、模块内评论
- 投票：单选、多选、匿名、截止时间
- @提醒、已读状态、家庭公告

动态流的写入路径**只有事件总线**（业务面不直接写 `Dynamic`），保证 P6 接规则引擎时动态流不需要改造。投票（饮食面点菜、家人面照护轮值）由 HomeOS 提供投票对象，业务面引用 `vote_id`，**不自建投票表**。

#### 3.4.4 数据系统

- 多端同步：实时、离线、冲突解决（LWW + 业务合并）
- 备份恢复：自动每日、手动、版本回滚
- 加密：传输 TLS 1.3、存储 AES-256、敏感端到端
- 导出：Excel、PDF、CSV、图片
- 迁移：导入、导出、跨设备

**冲突解决策略（按对象类别）**：

| 对象类别 | 策略 | 说明 |
|---|---|---|
| 财务流水、账单、借贷 | **服务端版本号乐观锁 + 拒绝后到** | 金额型数据不允许静默覆盖；客户端冲突需重拉后重试 |
| 清单条目、库存数量 | **字段级 LWW + 数量走增量合并** | 数量用 `delta` 而非绝对值合并（避免两人同时出库互相覆盖） |
| 档案、偏好、菜谱正文 | 字段级 LWW | 文本型可接受后到覆盖 |
| 打卡、完成状态 | **幂等 + 只进不退** | 状态机单向（`done` 不可被旧 `pending` 覆盖） |

写路径从一开始就落 `version` 字段与乐观锁（对象级版本 + 冲突返回 409 及双版本 payload），列入 P1-M1（14.5 第 5 项）。**业务对象无 `version` 列不得进 P1-M1。**

**备份口径**：每日全备 + binlog/WAL 连续归档，**RPO ≤ 15 分钟**（财务数据不接受"最多丢 24 小时"），RTO ≤ 30 分钟。详见 21.3。

**加密与搜索的互斥处理**：端到端加密与"服务端跨六面全局搜索"不能同时成立于同一字段。按**对象级分级**处理，见 **二十章数据分级表**：L1（服务端加密 + 可索引）、L2（服务端字段加密 + 密文/本地索引）、L3（端到端，不参与服务端搜索，仅本地可搜）。

#### 3.4.5 智能系统

- 全局搜索：跨六面、自然语言
- 语音输入：记账、添加、提醒
- 拍照识别：OCR 小票、条码、菜谱、证件
- AI 归类：内容识别 → 归入对应系统
- 智能建议：基于家庭数据的主动建议
- 产品内 Agent：家庭助手、问答、主动提醒

**分期切分**：P1 底座段**不含任何识别类 AI**，只做关键词全局搜索（自然语言搜索在 P6）。识别/录入类能力与其宿主业务域**同一期**交付：

- 财务的小票 OCR、语音记账 → **P1-M1**
- 饮食菜谱拍照识别 → **P3**
- 采购条码识别与条码库 → **P2**
- 语音「添加清单条目」随采购主功能 **P2**（降级路径为系统键盘语音输入，零外部依赖）
- P6 做**理解与预测侧**：AI 归类、补货预测、菜谱推荐、营养分析、成长报告、产品内 Agent

任何依赖第三方识别/模型服务的能力，其**手工降级路径必须同批次交付**：服务不可用时可纯手输，不阻塞宿主业务主流程（如记账）。

**外部依赖**：以上识别、录入与理解类能力全部依赖第三方识别/模型服务，均为新建 + 新签供应商；成本、供应商与降级见 **十九章**。19.3 规定"供应商未定的能力不得进排期"。

#### 3.4.6 事件系统

事件总线在 **P1-M1** 交付。

- 事件定义、发布、订阅、日志
- 幂等、重试、死信、版本管理

总线由 **NATS JetStream 持久化流**承载（卷首第 12 项、22.2 第 4 条），七个服务均为其客户端：

- **发布**：业务事务内先写本服务 schema 的 outbox 表，事务提交后由投递器发布到 subject `{code}.{object}.{action}`；进程崩溃由 outbox 重投保证不丢（at-least-once）。
- **消费**：每个消费者组独立 durable consumer，按 `idempotency_key` 去重（10.4）；失败指数退避重试至多 3 次，超限投递到死信 subject 并落本服务 `{code}_dead_letter`。
- **日志**：JetStream 流即全量事件日志的权威载体，可回放；热存 90 天 / 冷存 1 年（21.4）。回放不产生重复业务对象。
- **目录**：事件目录是仓库内的版本化文件，未在目录登记的事件不得发布（10.1），由契约门禁拦截（22.5 第 5 道）。

**不存在跨服务分布式事务**：一次写操作只落在一个服务内；跨面效果一律经事件达到最终一致，补偿与对账见 18.6。

#### 3.4.7 规则系统

规则引擎在 **P6** 交付。

- 规则配置、默认规则、自定义规则
- 优先级、冲突处理、模拟测试、执行日志

默认规则即 10.3 的十一条联动，P6 出厂即启用且**可关闭**（每家庭粒度）；自定义规则只允许"事件 → 创建 HomeOS 待办 / 通知 / 只读投影更新"三类动作，**不允许业务面注入任意代码执行**（安全边界）。

#### 3.4.8 设置系统

- 主题、通知、账号、安全、帮助、关于
- 多语言、时区、货币、日期格式
- **设备锁（PIN）**：App 本地口令（4-6 位），冷启动与后台回前台超过设定时限时要求解锁；PIN **只以不可逆散列存设备本地，不发往服务端、服务端不托管也不存储**；忘记口令的唯一恢复路径是手机号验证码重验后重置，重置即清除本机加密缓存与未提交草稿并需明示。PIN 是 20.2「L3 读取需设备级解锁」的实现载体，属 P1-M1 交付（14.5 第 9 项）。
- **客户端更新**：启动时**静默检查** wgt 版本（走 HomeOS 的只读版本接口），有新版本不打断当前操作，更新引导只在「我的 → 关于」与下次冷启动各出现一次且可跳过；仅当服务端标记了最低兼容版本时才强制更新（12.4）。

### 3.5 交互设计

- **首页**：家庭与成员区（含问候语）、**今日到期与待办的当日时间轴卡**、**家庭服务矩阵（已启用面宫格，首页主视觉，也是全 App 唯一的面入口）**、动态流、快捷入口
- **导航**：**顶栏一行**（家庭切换器 + 右侧两个动作位：全局搜索、带未读红点的消息入口，17.1）+ 底部 Tab 固定五项（首页、动态、+、消息、我的）；**顶栏不放面切换器**（定版 ⑫），**页面全部独立路由，不注册原生 tabBar**（17.7 第 6 条）
- **全局 +**：语音、拍照、文字、模板
- **设置**：分组列表、搜索、帮助
- **风格**：中性、克制、系统感，不抢业务系统视觉

面入口结构为「**底部 Tab 固定 + 首页家庭服务矩阵**」——早期口径里的「顶栏面横向切换器」已由 ⑫ 移除（17.1），代价与取舍见 17.2「面入口只有一处」。完整信息架构、面内二级 Tab、全局 + 的 AI 归类分流见 **十七章**，面目录与家庭面配置见 **17.8**。首页矩阵、「＋」目标对象、搜索分组、到期中心注册项、动态流筛选**五处**的面集合**同源**：都取本家庭**已启用且服务已出生**的面（`GET /api/homeos/family/modules` 与首页聚合接口），未启用与未出生的面**不出现在导航里、不在首页占位**；管理员在「我的 → 开通更多面」的目录页里看到全量面目录并选择开通。首页每格一句今日状态：待买 N 件 / 今晚吃什么 / 明日行程 / 宝宝身高 / 本周作业 / 预算余额。

### 3.8 验收标准

- 家庭创建、邀请、权限生效 ≤ 2 秒
- 提醒、待办到达率 ≥ 99.9%
- 同步延迟 ≤ 1 秒，冲突可解决
- 搜索响应 ≤ 500ms，跨面命中（「跨六面命中」的完整口径在 P6 判定，P1-P5 判已出生域，见 18.1 延后判定条与 18.2#4）
- 事件幂等、可重试、可追溯
- 权限变更实时生效
- 敏感数据加密存储
- 崩溃率 ≤ 0.1%

以上各条均已补「度量定义 + 分母 + 采样方法 + 判定方式」，见 **18.2**。其中：「到达率 99.9%」**不含位置类提醒与服务端无法保证的 APNs/厂商通道回执**，改测"服务端触发成功率 + 客户端展示率"两个可测口径；「权限变更实时生效」定义为 ≤1 秒内新请求生效。所有度量事件与验收样本显式携带 `family_id` 维度。

补充验收项：

- 无账号成员可由监护人代管建档，代管写入在动态流标注 `on_behalf_of`
- 到期中心聚合**各已出生服务**已注册对象（随出生期逐步增加：P1 = `homeos` + `finance`，P6 = 全部七域），未出生面不注册、不留占位行；**聚合与触发一律按本家庭的已挂载面集合过滤**（17.8）——被停用面的注册项不消失也不触发、不出现在日历与待办里，重新启用后按其自身时间规则照常恢复；各面各自无需暴露推送通道
- **面开通与按需加载**：管理员开通某面后该面在首页矩阵出现的端到端时限、首次进入该面的分包就绪时限、以及「未启用/未出生面在客户端零请求零下载」三条，按 **18.2#9** 判定；新家庭创建必须经过强制选面引导且至少启用 1 个面（17.8）
- 底座骨架自检（P1-M1 硬性门禁，见 14.5）：**当期服务（P1 = `svc-homeos` + `svc-finance`）与 NATS、Postgres、Nginx 全栈一条命令起停 ≤30 分钟**、当期服务的路由域与 schema/表前缀就位，同时**七个 code 的命名域全部登记进 registry**（`homeos` / `finance` / `purchase` / `diet` / `trip` / `kin` / `growth`，16.1、卷首第 12 项，CI 按 registry 校验且不要求服务已存在）、鉴权由共用 SDK 在各服务中间件统一生效（不在业务 handler 内裸 SQL 判家庭）、多家庭切换后上下文重建 ≤1 秒、到期中心可注册可触发、总线幂等重放不产生重复对象、**财务面跨服务五步全通**（注册→写→只读→事件→提醒，18.2 附加门禁①；其余五面在各自出生期以同一判据复验，11.9）

## 四、财务系统

### 4.1 系统定位

家庭财务管理系统，管钱。

### 4.2 系统边界

- 做：收支、账户、预算、报表、账单、借贷、储蓄目标、共享账本。
- 不做：不做采购执行、不做饮食消费决策、不做投资理财建议。

本面**全新建**。功能基线（P1-M1 必须达到的最低水位）：记账（支出/收入/转账、快捷记账、软删、幂等写）、账户（预置 + 自定义、余额计算）、二级分类、流水筛选与游标分页、统计（概览/趋势/分类/成员/折线饼图）、预算（月度 + 分类 + 固定/周期 + 超支提醒）、票据附件、离线队列与重放、wgt 热更新（含启动静默检查与可跳过更新引导，3.4.8）。在此之上补齐账单、借贷、目标、分账、资产负债。

- 图标用图标集名、禁止 emoji
- 分类表用 `family_id` 可空表示"预置字典 + 家庭自定义"

### 4.5 详细需求

#### 4.5.1 记账

- 快速记账：金额、分类、账户、备注、拍照
- 多账本：日常、旅行、装修、孩子、项目
- 分类：一级/二级、自定义图标、颜色
- 账户：现金、银行卡、支付宝、微信、信用卡、公积金、外币
- 收支类型：支出、收入、转账、借入、借出、报销
- 标签：项目、成员、地点、商家
- 周期记账：房租、房贷、工资、订阅
- 模板记账、语音记账、拍照记账、OCR
- 流水：按日/周/月/年、分类、账户、成员
- 搜索筛选、编辑删除、批量、回收站

**账本（Ledger）语义**：账本只是**报表与归集分组单元**——按标签（如 `project`）与成员范围过滤出的报表单元（日常、旅行、装修、孩子、项目等），**不是数据隔离域，也不是权限边界**；`Ledger` 表只存分组定义与成员范围。数据隔离靠权限与字段级可见性实现，不靠账本实体实现。旅行/装修/孩子账本的需求用报表与标签即可满足，不引入跨账本权限复杂度。私密流水用**行级可见性**实现：仅作者与管理员可读，且这类流水不参与 AA 分摊与跨面归集。

**回收站**：删除为软删 + 30 天可恢复，**P1-M1 必做项**。家庭账本误删是不可逆体验事故，不接受延后交付。

**语音/OCR/多币种**：均为新建，依赖第三方服务（十九章）。小票 OCR 与语音记账随记账主功能在 **P1-M1** 交付，且手工降级路径同批次：OCR 识别失败必须回落纯手输，不阻塞记账主流程。多币种需外部汇率源与更新频率口径（见 19.2）。

#### 4.5.2 预算

- 总预算、分类预算、成员预算
- 周期：月/季/年
- 进度、超支提醒、结转、模板
- 预算与实际对比

月度与分类预算为 P1-M1 基线（含固定/周期口径）；季度/年、结转、模板为 P1-M2。超支提醒通过 HomeOS 通知下发，本面**不自建推送**（见 3.4.2）。

#### 4.5.3 报表

- 趋势、分类、成员、商家、净资产、资产负债
- 月报、年报、自定义
- 导出 Excel/PDF

**导出硬性要求**（列入 18.3「导出数据完整」验收）：
1. 导出覆盖家庭**全部成员**的流水记录，不得限定"仅导出本人创建的记录"；
2. `type` / `days` / `format` 三个筛选参数**全部生效**；
3. 导出行数与页面筛选结果对账一致。

**净资产与资产负债依赖账户域先补齐负债对象（P1-M2）**。

**全局时间轴（P1-M1 必做）**：首页、流水、报表、预算四处共用**同一个时间窗切换器**（早期文本称「月份切换器」，0929 定版 ⑬ 扩为三档后该称呼作废）——在任一处切换时间窗，其余三处回到同一时间窗（会话内一致，跨会话记住最后一窗）。

- **三档粒度与 `period` 编码**（一次定版，各期不再扩）：月 `YYYY-MM`（如 `2026-09`）、季 `YYYY-Qn`（如 `2026-Q3`，季度按家庭时区的自然季，1-3 月为 Q1）、年 `YYYY`。**只有这一种编码**，客户端不得出现 `2026/9`、`202609`、时间戳区间之类的第二形态；接口收到无法解析的 `period` 返回 400，**不得静默回落到当前月**。
- **`period` 是 shell 级状态**（按 `family_id` 隔离），业务面只消费；分包内自造时间窗状态即门禁 4 失败（17.7 第 8 条）。
- **环比的上期随粒度定**：月 → 上一自然月，季 → 上一自然季，年 → 上一自然年；上期为空一律显示「无对比期」，**不得按 0 代入除法**（与 18.3#9 同口径）。
- **粒度是查询参数，预算周期是业务对象，两者不得绑死**：`Budget` 的季度/年周期属 **P1-M2**（4.4），M1 期间用户把时间窗切到季或年时，服务端**只返回该窗口内的实际收支与累计余额**，状态句与报表显「未设该周期预算」，**不得把月度预算乘 3 或乘 12 造一个假预算剩余**——这是 ⑬ 唯一的红线。
- 统计口径必须同时给出**环比**（按上一条的上期定义）与**累计余额**（按账户余额逐期累加，与 4.5.8 的余额派生口径同源，**累加由服务端做，不得由前端二次累加**）。时间窗一律按家庭时区计算（3.4.8），跨时区家庭的「2026-Q3」以家庭时区为边界。
- **首页恒渲染时间窗条**（17.2）：首页有读 `period` 的状态句，所以「时间窗条只在业务面出现」的旧写法不成立。
- **时间窗档位 ≠ 列表分组维度**：4.5.1 的「流水按日/周/月/年」是**列表内的分组表头**，不改变所选时间窗；时间窗切换器只有月/季/年三档，**不出现第四档，也不把分组维度当筛选条件**。

#### 4.5.4 共享账本

- 家庭共享、多人记账、权限
- AA 分账、共同支出分摊
- 结算中心：谁欠谁、一键结清

AA 分账参与范围（默认）：仅标记为「共享」的流水参与分摊，日常流水不摊；标记为私密的流水（行级可见性）不参与 AA 分摊与跨面归集。结算产生的转账/收款记录是**生成型单据**，其重放与重复写入遵循幂等写约定（10.4）。分账金额精度：以「分」为最小单位整数存储，分摊余数按参与人固定顺序分配，**结清判定 = 各参与人净额为 0**（18.3 有对应验收）。

#### 4.5.5 账单

- 周期账单、提醒、自动扣款标记
- 待缴、已缴、逾期、发票

账单到期通过 16.4 契约注册到 HomeOS 到期中心，本面**不自建提醒定时器**（见 3.4.2）。"自动扣款标记"仅人工确认，**不做任何银行/支付宝/微信账单自动导入**（产品非目标，且属合规高风险项，见 20.4）。

#### 4.5.6 借贷

- 借入、借出、还款计划、提醒、逾期、报表

新增对象 `RepaymentPlan`（id、loan_id、due_at、amount、status），逐期到期走 16.4 注册。借贷属家庭外往来，`counterparty` 允许非成员。

#### 4.5.7 目标

- 储蓄目标、进度、自动存入、家庭共同目标

"自动存入"指**记账层面的自动转账记录生成**（周期规则），不接任何资金通道、不做真实资金划转（合规边界，见 20.4）。

#### 4.5.8 账户资产

- 余额、流水、信用卡账单、还款日、资产/负债总览

`Account` 需补 `credit_bill_day`、`repay_day`、`debt_amount`；资产负债总览是财务面首页净资产卡与 HomeOS 首页**财务格子**状态句的唯一数据源（17.2）。

#### 4.5.9 分类与账户的可维护性

- **分类停用**：`is_active=false` 的分类不再出现在记账选择器里，**历史流水照常显示与统计**；停用可逆。预置字典项可停用不可删除。
- **分类排序**：家庭可自定义显示顺序（`sort_order`），记账选择器、报表图例、筛选 chips 三处共用同一顺序；排序写入需带 `version`（与流水同套乐观锁口径）。
- **账户归档与恢复**：`is_archived` 的账户从记账默认账户位与账户汇总里移出，**但其历史流水仍参与统计与净资产**（归档只影响"今后能不能选"，不影响历史归属）；归档前若该账户余额非 0，必须先做一笔转账到存续账户或显式确认为 0，避免净资产与账户合计长期不一致。归档可逆。
- **删除与归档的分工**：分类与账户都**不提供物理删除**（预置项更不能），只提供停用/归档；需要清理错建的自定义项才走软删 + 回收站（4.5.1），且被流水引用时一律拒绝并提示改用停用。

### 4.6 交互设计

- **首页**：净资产卡片 + 本月收支 + 预算进度 + 快捷记一笔
- **底部 Tab**：流水、报表、预算、账本、我的
- **记账入口**：悬浮 +、语音、拍照
- **流水**：按日分组、滑动编辑、长按批量
- **报表**：图表切换、时间筛选、下钻
- **风格**：数据感、清晰、克制

财务面的「流水/报表/预算/账本/账户与设置」是**面内二级 Tab**（末位不叫「我的」，17.3）；一级导航（底部五项 + 顶栏一行的家庭切换与两个动作位，**不含面切换器**，见 3.5、17.1）不被替换、不叠加悬浮 Tab，避免七套导航并存。**切到别的面只能回首页矩阵点格**（⑫），财务面不得在自己的分包里放面切换器。面 shell 为全新前端工程，按「每面一个 pages 目录 + 一级 Tab 常驻」组织；工程从第一版起按 **subPackages 分面包**（每面一个分包，分包随面出生并按需加载，11.3 第 ⑧ 项、17.8），避免各面在主包体积与构建时间上互相拖累（17.7 第 4 条）。

### 4.9 验收标准

- 记账 ≤ 3 步完成，≤ 5 秒
- 流水加载 ≤ 300ms（1000 条）
- 报表生成 ≤ 1 秒
- 预算超支提醒准确率 100%
- 共享账本多人同步 ≤ 1 秒
- 分账结算金额零误差
- 导出数据完整、格式正确
- 财务数据加密，权限隔离
- **时间窗一致**：时间窗切换器（月/季/年三档，⑬）在首页/流水/报表/预算四处任一处切换后，其余三处回到同一时间窗；环比与累计余额取服务端值，前端不二次累加（4.5.3）
- **停用与归档可维护**：分类停用后不出现在记账选择器，但历史流水仍可筛、仍可统计；账户归档不影响历史流水与净资产，余额非 0 时拒绝归档并提示先转账（4.5.9）

以上各条均已补口径（超支阈值、1000 条的构造方法、导出完整性校验方式等），见 **18.3**；验收样本与度量事件显式携带 `family_id` 维度。其中「流水加载 ≤300ms（1000 条）」增加**多年累积衰减约束**——单家庭 5 年 ≤ 6 万条，P95 仍需 ≤ 500ms（见 21.2）。

## 五、采购系统

### 5.1 系统定位

家庭采购与库存管理系统，管物。

### 5.2 系统边界

- 做：购物清单、库存、补货、采购记录、比价。
- 不做：不做支付、不做物流、不做电商交易、不做电商实时价格抓取。

采购系统是全家庭唯一的物品与库存权威源，包含冰箱里的食材。饮食面没有独立库存实体，只有指向本域的只读视图与出库登记接口调用；同一件物品的数量只在本域记录一次。

### 5.3 系统职责

- 管理家庭购物需求
- 管理家庭物品库存
- 管理保质期与补货
- 记录采购历史
- 支持家庭协作采购

### 5.4 核心能力域

| 能力域 | 内容 | 期 |
|---|---|---|
| 清单 | 多清单、共享、认领、常买、模板、语音添加 | P2（语音添加走系统键盘语音，零外部依赖） |
| 库存 | 物品档案、位置、入库出库、批次、保质期 | P2 整面（批次与保质期同批，条码识别随 P2） |
| 补货 | 消耗记录、低库存提醒、自动加购 | P2 阈值提醒 + P6 预测 |
| 记录 | 采购历史、价格、商家、统计 | P2 |
| 比价 | 优惠券、价格跟踪、促销提醒 | 价格跟踪不做自动抓取，P2 仅人工券与价格历史；自动比价不做 |
| 协作 | 家庭共享、任务分配、完成动态 | P2（认领 = HomeOS Todo 分配，不自建） |

### 5.5 详细需求

#### 5.5.1 购物清单

- 多清单：日常、超市、网购、旅行、节日
- 添加：名称、数量、单位、分类、备注、图片
- 勾选、已买、未买、排序、拖拽、分组
- 常买清单、一键复用、模板清单
- 多人共享、实时同步、认领
- 提醒：到超市、指定时间
- 语音添加、拍照添加

认领实现为 HomeOS `Todo` 分配给成员（16.4），清单面读取投影。「到超市提醒」受位置提醒降级口径约束（3.4.2）。「语音添加」走系统键盘语音，零外部依赖；「拍照添加」依赖识别能力，在 P2 交付，识别失败必须可手输。「分类」为物品分类，不等同费用分类；入库转支出时需映射到 `finance.Category`，映射表由用户首次使用时确认，之后自动。

#### 5.5.2 库存

- 物品档案：名称、分类、数量、单位、位置
- 位置：冰箱、厨房、卫生间、储藏室、药箱
- 入库、出库、调整、批次
- 阈值、低库存提醒
- 保质期、临期提醒
- 扫码、拍照录入

本域是食材库存的唯一归属：饮食面「冰箱临期」「剩余食材推荐」全部查询本域的 `InventoryItem` + `Batch`，不得写入。临期与低库存的提醒对象注册到 HomeOS 到期中心（16.4），本面不自建定时器。库存录入 P2 走手工录入；扫码与拍照识别依赖条码库（19.1），在 P2 交付，识别失败必须可手输名称与分类。

盘点按位置粒度进行，不做全仓盘点（家庭场景不现实）。`Stocktake` 记录一次盘点的差异，误差 = 盘点差异条目数 / 盘点条目总数，用于支撑 5.9 的库存一致性验收。

#### 5.5.3 补货
- 消耗记录、消耗速度
- 自动补货建议、低库存自动加购
- 临期优先使用

消耗记录 = 出库事件累计。「自动加购」在 P2 只做阈值触发：低于阈值即生成清单条目，规则固定、无学习；P6 才引入消耗速度预测。5.9 的「准确率 ≥98%」只对阈值触发口径度量（18.4）。

#### 5.5.4 采购记录
- 历史、价格、商家、统计、月度支出

采购完成生成财务支出的事件链路（10.3）适用生成型单据语义：财务侧可改可删，删后不重建。

#### 5.5.5 比价
- 优惠券、价格跟踪、促销提醒

范围限于：人工录入优惠券（名称/面额/有效期/使用状态）、同一物品的历史价格曲线、促销提醒仅来自用户自建周期提醒。不做电商实时价格抓取（无合规数据源、单机做不到、成本不可控）。

#### 5.5.6 协作
- 共享采购、任务分配、认领、完成动态

### 5.6 交互设计

- **首页**：待买清单 + 库存预警 + 临期 + 常买
- **底部 Tab**：清单、库存、记录、统计、我的
- **清单**：大勾选框、滑动删除、拖拽
- **库存**：分类网格、搜索、扫码
- **风格**：清单感、勾选感、轻快

面内二级 Tab 不替换一级导航，同 4.6。

| Supplier | id、family_id、name、contact、notes | P2 |
| Coupon | id、family_id、name、value、expire_at、status | P2，人工录入 |
| Stocktake | id、family_id、location、started_at、items、diff、done_at | 支撑 5.9 盘点误差可测 |
| ConsumptionLog | id、item_id、qty、consumed_at、member_id | 消耗速度基础（P6 预测数据源） |

食材不单设实体，由 `InventoryItem` + `Batch` 承载，`location = 冰箱` 即食材。

### 5.8 接口

| 接口 | 说明 |
|---|---|
| `POST /api/purchase/lists` | 创建清单 |
| `POST /api/purchase/lists/{id}/items` | 添加物品 |

| `POST /api/purchase/inventory` | 入库 |

### 5.9 验收标准

- 清单添加 ≤ 2 步，勾选 ≤ 1 步
- 库存扫码识别率 ≥ 95%
- 临期提醒提前 3 天触达
- 低库存自动加购准确率 ≥ 98%
- 多人同步 ≤ 1 秒
- 采购完成生成财务支出零误差
- 库存数量与实际一致（盘点误差 ≤ 2%）

各条口径定义见 18.4。「扫码识别率 ≥95%」限定在标准商品条码 + 光线正常条件下测，非标准码不计入分母。「采购完成生成财务支出零误差」定义为金额字段一致 + 不重复 + 可人工冲正三项校验。

## 六、饮食系统

### 6.1 系统定位

家庭饮食管理系统，管吃。

### 6.2 系统边界

- 读：菜谱、菜单、点菜、做饭计划、饮食记录由本面维护；食材库存由采购域维护，本面只读。

### 6.3 系统职责

- 管理家庭菜谱与菜单
- 基于采购库存做饮食视角展示与消耗登记
- 协调家庭点菜与做饭
- 记录家庭饮食
- 消费家人系统的口味与忌口，用于菜单过滤

### 6.4 核心能力域

| 能力域 | 内容 | 数据归属 |
|---|---|---|
| 菜谱 | 收藏、创建、导入、评分、笔记 | 本面唯一 |
| 菜单 | 周菜单、点菜、投票、模板 | 菜单归本面；投票对象归 HomeOS |
| 食材 | 冰箱库存、临期、剩余食材推荐 | 库存归采购；本面只读 + 出库登记 |
| 口味 | 成员忌口、过敏、偏好、辣度 | 归家人系统 `Preference`；本面只读消费 |
| 做饭 | 今日菜单、谁做、任务、提醒、打卡 | 任务与提醒归 HomeOS |
| 记录 | 饮食记录、营养、外卖、餐厅 | 本面唯一 |

### 6.5 详细需求

#### 6.5.1 菜谱
- 收藏、创建、编辑、导入、拍照识别
- 食材、步骤、图片、视频
- 分类：家常、快手、宴客、儿童、减脂
- 标签、搜索、筛选、评分、笔记、做过次数

「拍照识别菜谱」依赖外部识别服务（19.1），在 P3 交付，失败必须可手输；同批次交付手工录入路径。菜谱食材项需与 `purchase.InventoryItem` 建立名称对齐（可自动匹配 + 人工确认别名表），否则「剩余食材推荐」无法命中；别名表归本面维护（`IngredientAlias`）。

#### 6.5.2 菜单
- 周菜单：早中晚、加餐
- 拖拽安排、点菜、投票、模板
- 菜单生成采购清单

点菜投票调用 HomeOS `Vote`（3.4.3），投票结果回写菜单。「菜单 → 采购清单」为事件驱动（`diet.menu.created` → 采购），清单条目携带 `recipe_id` 便于反查。缺料计算 = 菜单食材需求 − 采购库存只读快照，不锁库存。

#### 6.5.3 食材视图
- 冰箱库存、保质期、临期提醒
- 食材与菜谱关联、剩余食材推荐

本域无独立库存实体。展示数据来自 `GET /api/purchase/inventory?location=fridge`；临期提醒由采购域注册到到期中心，饮食首页仅按「食材」视角聚合展示；做饭完成后调用 `POST /api/purchase/inventory/{id}/out` 登记消耗。本面不接受食材写请求。

#### 6.5.4 口味消费
- 成员忌口、过敏、偏好、辣度
- 菜单自动过滤

数据源为家人系统 `Preference`（type ∈ 忌口/过敏/偏好/辣度）。饮食面订阅 `kin.preference.updated` 事件刷新本地过滤缓存，不建第二套偏好表。「忌口生效」的验收是读取一致性：偏好写入后 ≤5 秒，饮食过滤结果反映新值；不做「同步 100% 成功」承诺（18.5）。

#### 6.5.5 做饭
- 今日菜单、谁做、任务、提醒、打卡

「谁做/打卡」实现为 HomeOS `Todo` 分配 + 完成回写（16.4），打卡不建本面私有状态机。

#### 6.5.6 外卖餐厅
- 外卖记录、餐厅收藏、评分、家庭常点

#### 6.5.7 饮食记录
- 饮食记录、卡路里、营养统计、家庭报告

卡路里/营养数值来自菜谱录入时的自填或识别结果，不接外部营养成分库（无权威免费数据源，且属健康建议边界，列入 19.2 明确排除）；报告页标注「参考值，非营养建议」（20.3）。

### 6.6 交互设计

- **首页**：今日菜单 + 冰箱临期 + 家庭点菜 + 推荐菜谱
- **底部 Tab**：菜单、菜谱、食材、记录、我的
- **菜谱**：大图卡片、瀑布流
- **菜单**：周视图、拖拽
- **风格**：温暖、食欲感、图片驱动

| Recipe | id、family_id、name、ingredients、steps、images、tags、rating、cook_count | `ingredients` 携带可选 `inventory_item_id` 对齐 |

| MenuVoteRef | menu_id、vote_id、resolved_at | 只引用 HomeOS Vote，不复制投票数据 |

食材库存与口味偏好不在本域设表：前者由采购域 `InventoryItem` 承载，后者由家人系统 `Preference` 承载，本域均只读消费。

## 八、家人系统

家庭成员信息与照护管理系统，管人。

### 8.2 系统边界

- 不做：不做医疗诊断、不做社交动态、不做健康监测、不给健康建议或风险判断。

记录血型、过敏史、身高体重属档案记录，不属健康监测/诊断，页面不得给出健康建议或风险判断；紧急卡内容为事实展示，急救场景免责声明保留。`kin.Profile` 是生日、血型、过敏、联系方式、紧急联系人的唯一权威源；生日归属本域维护，HomeOS `Member` 不存生日。

- 管理家庭成员信息

- 管理照护安排
- 管理纪念日与礼物
- 管理家庭分工
- 管理紧急信息

### 8.4 核心能力域

| 能力域 | 内容 | 数据归属 |
|---|---|---|
| 成员 | 档案、联系方式、隐私 | 本面唯一（身份主体在 HomeOS；**称谓/关系归 HomeOS `Member.relation`**，本面只读，8.5.1、16.2） |
| 偏好 | 口味、忌口、尺码、礼物、心愿 | 本面唯一权威源，饮食/采购只读消费 |
| 照护 | 孩子、老人、宠物、轮值、记录 | 任务与轮值归 HomeOS（`Todo`/`Vote`） |
| 纪念日 | 生日、结婚纪念日、家庭日 | 本面唯一，提醒注册 HomeOS |

### 8.5 详细需求

#### 8.5.1 成员
- 档案：姓名、生日、血型、过敏、联系方式、紧急联系人、照片；**关系不在本面存储**（见下）
- 隐私设置

档案与账号解耦：支持无账号成员（婴儿、老人共用账号场景），由监护人代管（`guardian_id`，3.4.1）。

**「关系 / 称谓」的权威归属是 `homeos`，不是本面**（16.2、3.6 `Member.relation`，0929 定版 ⑭）：`relation` 是「这个人在本家庭里怎么称呼」（爸爸 / 奶奶 / 哥哥），随家庭建档产生、属家庭级身份而非个人档案，首页问候语在 **P1** 就要用它（17.2）。本面 P4 出生时的**家庭关系图**（父母/子女/配偶/其他）按 16.3 的只读接口消费 `Member.relation`，**不得建 `kin_relation` 一类的第二数据源**；成长面「被记录对象」选择器（P5）同样只读它。若 P4 需要「一个人对不同人的多条关系边」，那是关系图的边、与单一称谓字段是两个语义，届时按 23.1 提案扩表，不在本条预建。

#### 8.5.2 偏好
- 口味、忌口、过敏、尺码、礼物、心愿、颜色、品牌

`Preference` 含 `severity`（忌口/过敏的严重程度，供饮食面直接消费，避免饮食面再建一套表）与 `visibility`（过敏默认对全家可见；尺码/礼物偏好可按成员隐藏，依 15.4 字段级可见性）。饮食面通过订阅 `kin.preference.updated` 刷新过滤缓存。

#### 8.5.3 照护

## 十、系统间接口与事件规范

### 10.1 事件命名

命名规则 `系统.对象.动作`。前缀取 16.1 的系统 code（**当前七个**；面目录可扩展，新增一面即新增一个前缀，且必须先进 registry 才能发事件，17.8），不使用表外前缀：

`homeos.`　`finance.`　`purchase.`　`diet.`　`trip.`　`kin.`　`growth.`

`kin.` 不写作 `family.`，避免与 HomeOS 的 `Family` 实体同名。新增事件必须先登记进事件目录（P1-M1 交付物，见 11.3）再发布。

当前事件清单：

- `homeos.todo.completed`
- `homeos.permission.updated`（各服务据此失效权限缓存，15.6）
- `homeos.family.module.updated`（某家庭启用/停用某个面；各服务据此失效 module 判定缓存、客户端据此重建首页矩阵与其余四个消费位，17.8、⑫）
- `{code}.due.registered` / `{code}.due.revoked`（**16.4 到期注册与撤销的唯一通道**，各面向 HomeOS 注册定时语义；`{code}` 取发布方自己的 code，符合「每服务只被授权发布自己那条流」）
- `homeos.reminder.fired`（HomeOS 到点触发后下发，业务面据此更新自身展示态）
- `finance.bill.paid`（账单标记已缴 → HomeOS 消费置完成，17.5 深链闭环）
- `{code}.audit.recorded`（各服务在自己流上发审计事实，`svc-homeos` 消费后统一落 `homeos_audit_log`，21.5）
- `finance.transaction.created` / `finance.budget.exceeded`
- `purchase.order.completed`
- `diet.menu.created`
- `trip.maintenance.due` / `trip.completed`
- `kin.birthday.upcoming` / `kin.preference.updated`
- `growth.course.scheduled` / `growth.course.fee`

### 10.2 事件结构

```json
{
  "event_id": "uuid",
  "type": "purchase.order.completed",
  "source": "purchase",
  "family_id": "uuid",
  "member_id": "uuid",
  "payload": {},
  "version": "1.0",
  "created_at": "ISO8601",
  "idempotency_key": "purchase.order.completed:{business_id}",
  "causation_id": "uuid | null",
  "attempt": 0,
  "delivery": "in-process"
}
```

字段口径：

- `event_id`：每次发布唯一，仅用于单条事件的追溯与排查，**不作幂等键**。
- `idempotency_key`：`event_type + business_id`，消费端据此去重。
- `causation_id`：触发本事件的上游事件 id，无上游则为 `null`，用于链路追溯与死信排查。
- `version`：语义化版本，只允许向后兼容的扩展。
- `attempt`：重试序号，从 0 起。
- `delivery`：投递形态，当前为 `stream`（outbox → NATS JetStream，22.2 第 4 条）；同一事件在流内的 subject 即 `{type}`，消费端组名 = 目标服务名。
- `family_id` / `member_id`：数据归属与操作人，消费端不得跨家庭处理。

### 10.3 关键联动事件

十一条事件的**目录条目全部在 P1-M1 登记进 registry**（未出生面只有目录条目、无生产者，14.5 第 6 项）；**启用期 = 源面出生期末**（11.1「联动随该面出生期交付」），跨面全量启用与规则引擎在 P6 收口。

| 事件 | 源 | 目标 | 动作 | 说明 | 启用期 |
|---|---|---|---|---|---|
| `diet.menu.created` | 饮食 | 采购 | 生成清单 | 条目携带 `recipe_id`；缺料计算读库存快照，不锁库存 | **P3** |
| `purchase.order.completed` | 采购 | 财务 | 生成支出 | 生成型单据，适用「人工删除后不重建」语义 | **P2** |
| `purchase.order.completed` | 采购 | 饮食 | 更新食材 | 不复制食材数据：饮食面对采购库存为只读投影（16.3），本事件仅作饮食首页缓存失效通知 | P2 发布、**P3 起有消费方** |
| `kin.birthday.upcoming` | 家人 | HomeOS | 提醒 | 走 16.4 注册契约，非直接推送 | **P4** |
| `kin.birthday.upcoming` | 家人 | 采购 | 推荐礼物 | 读 `kin.Preference(gift/wish)`，生成 `ShoppingItem` | **P4** |
| `kin.preference.updated` | 家人 | 饮食 | 更新过滤 | 语义为缓存失效 + 只读重取，不写饮食库 | **P4** |
| `trip.maintenance.due` | 出行 | HomeOS | 提醒 | 16.4 注册 | **P6** |
| `trip.completed` | 出行 | 财务 | 归集费用 | 按 `trip_id` 标签聚合，生成型单据 | **P6** |
| `growth.course.scheduled` | 成长 | HomeOS | 日历 | 16.4 注册 `CalendarEvent` | **P5** |
| `growth.course.fee` | 成长 | 财务 | 支出 | 成长面只存 `transaction_id` 引用，不复制财务数据（16.2） | **P5** |
| `finance.budget.exceeded` | 财务 | 各系统 | 提醒 | 广播给 HomeOS，由其按来源标签下发；各面不自建推送 | **P1-M1**（HomeOS 下发）；他面订阅随各自出生期接入 |

### 10.4 事件治理

- 幂等键：`event_type + business_id`。`event_id` 每次发布都不同，用它做幂等键等于没有幂等；`causation_id` 用于链路追溯。
- 投递保证：at-least-once（outbox + JetStream 持久化流）+ 消费端幂等；**不承诺恰好一次，也不提供跨服务事务**。
- 重试：消费端指数退避，最大 3 次。
- 死信：失败投递到死信 subject 并落消费方 `{code}_dead_letter`，管理台可查看与人工重放（重放接口见 3.7）。
- 版本：语义化，向后兼容；破坏性变更须升 `version` 并保留旧 subject 一个期，由 22.5 契约门禁检测未升级即失败。
- 日志：全量记录、可追溯，载体为 JetStream 流，保留期见 21.4。
- 忽略表：`EventIgnore(business_id, event_type, ignored_at, operator)`，实现「人工删除后不重建」，落在**归属服务自己的 schema**。
- 顺序：不承诺全局有序，只承诺同一 `(source_system, source_id)` 的分区内有序（JetStream 按 subject 分组消费者）。消费端不得依赖跨对象事件顺序。

## 十一、迭代规划与 Agent 推进机制

### 11.1 去 MVP 化原则

- **不设 MVP**：不以「最小可用」为目标，不以残缺功能上线。
- **每面完整闭环**：每一面都按完整业务域设计，且**在自己的出生期一次做完整面**（闭环 + 深度域同批交付），不留「下期补齐」的尾巴。
- **一期一面**：迭代单位是「底座 + 一个面」的垂直切片，不是横向的能力层。六期串行推进，每期只有一个对外交付对象与一套期末验收。
- **分期交付**：不是砍功能，而是按依赖关系分期推进——被依赖的面先出生（财务 → 采购 → 饮食 → 家人 → 成长 → 出行）。
- **底层先行**：家庭核心、时间、权限、通知、同步、事件总线、关键词搜索**全部在 P1-M1 建成**；此后各期不再改底座主干，只扩事件目录与投影映射。识别/录入类 AI 随宿主面交付，不进底座；AI 归类与预测属 P6。
- **服务随面出生**：`svc-homeos` 与 `svc-finance` 在 P1 创建，其余五个服务在各自出生期创建；七个 code 的命名域在 P1 一次性登记进 registry（卷首第 12 项），CI 门禁按 registry 校验，不要求服务已存在。
- **联动后置但不由缺位变常态**：总线骨架随 P1-M1 交付；**与该面相关的联动随该面出生期末交付**（例：P2 采购出生时，「库存耗尽 → 生成采购项」「清单完成 → 生成流水」必须同期可用）；**规则引擎与 S1-S6 全链路场景验收在 P6**。先让每面独立可用，再拉通。
- **Agent 全流程参与**：需求、设计、开发、测试、部署、文档、复盘均由 Agent 协作推进，人类负责目标、优先级、验收与伦理。一期一面使验收对象唯一，人类走查带宽是排期的真实约束而非并行度（11.7）。

### 11.2 迭代分层

| 层级 | 内容 | 目标 | 交付位置 |
|---|---|---|---|
| L0 底层底座 | 家庭核心、时间系统、协作系统、数据系统、智能系统（仅骨架：总线与关键词搜索）、设置系统、**事件总线骨架**、七服务运行形态与 CI 门禁 | 六面共用基础设施 | **P1-M1** 一次建成，此后不改主干 |
| L1 单面整面 | 一个面的闭环域 + 深度域同批（含该面自带的录入侧 AI 与手工降级） | 该面可独立使用、可替代单点工具 | **各面出生期**：财务 P1、采购 P2、饮食 P3、家人 P4、成长 P5、出行 P6 |
| L2 跨面联动 | 与该面相关的事件联动与只读投影；规则引擎、联动配置 UI、生成型单据与冲正、跨面对账 | 面与面自动流转 | 联动随各面出生期；**规则引擎与全链路收口在 P6** |
| L3 智能化 | AI 归类、补货/消耗预测、菜谱推荐、营养分析、行程建议、照护提醒、成长报告、产品内家庭助手 | 主动服务家庭 | **P6**（录入侧 AI 不在此层，见 L1 与 11.3） |

### 11.3 迭代期规划

**总周期**：各期净工作量合计 **148-181 周**；严格串行下另有**期与期之间的期末验收走查、发布收口与下一期开工准备，按六期合计约 8 周**（不计入单期工作量，也不得压缩），因此**墙钟合计 156-189 周（36-44 个月）**；六期之外的远期不计入。**周期全部串行**，因此这个墙钟显著长于「底座一期 + 六面并行」的形态；换取的是**每期只有一个对外交付对象、一套期末验收、一条发布线**，人类走查带宽与跨服务联调规模都被压到当期一个面内。这是排期决定，不是效率结论：若某期出现可并行的独立功能域，期内多 Agent 并行不受本条约束（11.7），但**不得跨期并行**——第 N+1 期不得在第 N 期期末验收通过前开工。**每期末验收未过不得进入下一期；周期可以顺延，单面完整度不得压缩。**

**P1-M1 的八项增量**（2026-09-29 依 family-ledger 功能对照补入，见 `docs/p1-page-structure-navigation.md` 第十一章）：全局时间窗切换器（**月/季/年三档，⑬**）、环比、累计余额、通知分型与未读红点、分类停用与排序、账户归档与恢复、设备锁 PIN 与 L3 本地解锁、wgt 启动静默检查更新。八项合计约 2-3 周工作量，**在 M1 的 26-31 周区间内由 S6 与 S14 的缓冲吸收，M1 区间与墙钟 156-189 周均不变**；若实测超出，按本条前一句处理——周期顺延、单面完整度不得压缩，**不得以裁剪这八项来对冲工期**。**⑬ 的三档不把第一项扩成两件事**：同一套时间窗组件多两个档位与一套 `period` 编码解析，属第一项之内，**不新增第九项增量**。

**P1-M1 的第二项增量：面可配置与热插拔**（2026-09-29 需求补充，17.8）：`homeos_family_module` 表与迁移、`family/modules` 读写接口与审计、新家庭创建的强制选面引导、「我的 → 开通更多面」目录页、首页矩阵与五个导航消费位改为按已启用集合渲染（**顶栏面切换器已由 ⑫ 移除，不再是本项要改的位**）、`app/bundles` 分包清单契约 + 按需加载 + sha256 校验与失败回退 + 缓存清理、停用后跨面统计口径不变的一致性断言、18.2#9 的度量脚本。合计约 **1.5-2 周**工作量，与八项增量同理由 S6/S14 缓冲吸收，**M1 的 26-31 周与墙钟 156-189 周不变**；P1 只交付「按需启用 + 分包清单与校验回退的代码路径」，**真实远程下发包自 P2 起用**，这不构成裁剪本项（17.8 的阶段表）。

**AI 交付期口径**：P1-M1 的**底座段**不含任何识别/录入类 AI；小票 OCR 与语音记账随财务面进 P1-M1，条码识别进 P2，菜谱拍照识别进 P3；AI 归类与预测（补货预测、菜谱推荐、营养分析、成长报告、产品内助手）统一 P6。凡依赖第三方服务的能力，其手工降级路径与主能力同期交付，不接受「先上 AI、以后再补手工」。

每面在它的出生期均含同一批底座附带项——面内二级 Tab、到期对象注册（16.4）、只读投影接入（16.3）、录入能力的手工降级路径、本面契约冻结；录入侧 AI 本身按宿主面排期（11.3 口径）。这些不单列在各面路线里，但计入该期工作量。财务面的「多账本」按 4.5.1 视图分组口径执行；比价与智能比价不在排期范围。

### 11.5 Agent 体系设计

| Agent | 职责 | 输入 | 输出 | 度量 |

| Architect Agent | 架构、数据模型、API、事件总线 | 需求、技术约束 | 架构文档、接口定义 | 架构评审通过率 |
| UX/UI Agent | 交互、视觉、组件、原型 | 用户故事、品牌规范 | 原型、设计稿、组件库 | 可用性评分 |
| Frontend Agent | 前端开发、组件、状态管理 | 设计稿、API | 前端代码、页面 | 一次通过率 |
| Backend Agent | 后端服务、数据库、API | 架构、接口定义 | 后端代码、服务 | 接口稳定性 |
| Data Agent | 数据管道、指标、报表 | 数据模型、埋点 | 数据报表、指标 | 数据准确率 |
| Test Agent | 测试用例、自动化、回归 | 需求、代码 | 测试报告、缺陷 | 覆盖率、缺陷密度 |
| Security Agent | 权限、隐私、加密、审计 | 架构、数据流 | 安全报告、合规建议 | 漏洞数、合规率 |
| DevOps Agent | CI/CD、监控、发布 | 代码、环境 | 部署、监控、回滚 | 发布成功率 |
| Docs Agent | 文档、帮助、更新日志 | 代码、需求 | 文档、帮助中心 | 文档同步率 |
| Growth Agent | 埋点、分析、增长实验 | 用户行为、指标 | 实验报告、增长建议 | 留存、转化 |
| Review Agent | 复盘、总结、改进 | 迭代数据、缺陷 | 复盘报告、改进项 | 改进落地率 |

**流程载体**：上述 13 个 Agent 角色保留为**职责划分**；任务卡、看板、认领、人工审核门禁**不自建**，直接复用 `~/www/agent-task-board`（Jarvis Workbench：Tauri + NestJS sidecar + Prisma/SQLite，Agent 经 MCP `/mcp` 或 9 个 REST 工具 `claim_next_task`（带租约）认领，六列看板，生效前强制人工审核）。详见 22.3。

### 11.6 Agent 工作流

1. **人类设定目标**：确定各期目标、优先级、验收标准。
2. **Orchestrator 拆解**：生成任务卡、依赖图、排期。
3. **Product Agent 细化**：输出用户故事、验收标准。
4. **Architect Agent 设计**：输出架构、数据模型、API。
5. **UX/UI Agent 原型**：输出交互稿、视觉稿、组件。
6. **Frontend / Backend Agent 开发**：并行编码，提交 CI。
7. **Test Agent 测试**：单元、集成、回归、自动化。
8. **Security Agent 审计**：权限、隐私、加密、漏洞扫描。
9. **DevOps Agent 部署**：灰度、监控、回滚。
10. **人类验收**：关键节点审批，确认业务价值。
11. **Docs Agent 更新**：文档、帮助、更新日志。
12. **Review Agent 复盘**：输出迭代报告，进入下一期。

**验收粒度（第 10 步「关键节点」具体化）**：人类审批发生在三个粒度——① 任务卡进入「待审核」列（每卡，复用 Jarvis Workbench 的强制人审）；② 每 Sprint 末的功能切片验收（按面）；③ 每一期末的场景链路验收（2.4 S1-S6）。**期末验收未过不得进入下一期。**

**步骤并行规则**：**只在当期那一个面内并行**——多个 Agent 可同时承担同一面内互不依赖的功能域（11.7 第 4 条给出人审切片上限）；**不同面之间不得并行**，第 N+1 期的任何步骤（含设计稿与数据模型）不得在第 N 期期末验收通过前启动（11.7 第 1 条）。未出生面的 Agent 步骤一律不排进当期看板。

**Agent 任务卡模板：**

```
任务ID：
所属面：
目标：
输入：
输出：
依赖：
验收标准：
负责Agent：
人类审批：
归属数据源（16.2 权威表）：
外部依赖（19.1，无则填"无"）：
```

后两个字段为必填：`归属数据源` 防止 Agent 在任务卡里自由发明第二套实体，`外部依赖` 防止隐性引入第三方服务。

### 11.7 迭代节奏与看板

- **Sprint 周期**：2 周。
- **期周期**：P1-M1 = 26-31 周，P1-M2 = 10-12 周，P2 = 20-24 周，P3 = 20-24 周，P4 = 16-20 周，P5 = 18-22 周，P6 = 38-48 周；各期净工作量合计 148-181 周，加期间期末验收与发布收口约 8 周，**墙钟合计 156-189 周**（口径见 11.3）。
- **每日站会**：Agent 报告进度、阻塞、风险。
- **看板列**：需求池 → 已拆解 → 设计中 → 开发中 → 测试中 → 待验收 → 已发布 → 复盘。与 Jarvis Workbench 六列（需求池→待执行→执行中→待审核→已完成/异常）的映射见 22.3，不新起一套看板。
- **推进策略与瓶颈约束**：底座与业务面**串行**，一期只交付一个面，联动随期末、全链路收口在 P6。新模型下的真实瓶颈不再是「多面并行的组织成本」，而是**单面整面的工作量**与**人类期末走查的深度**。五条硬约束：
  1. **第 N+1 期不得在第 N 期期末验收通过前开工**：业务服务、schema、迁移序列与前端分包一律不得提前创建（registry 里的七域命名登记除外，卷首第 12 项）；
  2. **P1 内部 M2 不得在 M1 验收通过前开工**；
  3. **底座契约在 P1-M1 末冻结后，后续各期才允许在该面内并行开发**（22.2 第 7 条）；
  4. **每 Sprint 人类验收切片上限 = 当期 1 面 × 每面 2 个功能域**，超出即顺延，不许压缩验收；
  5. 需提速时**只允许顺延期末，不允许压缩单面完整度**（守 1.3 第 5 条）。
- **版本节奏**：**每期末对外发布一个大版本**（P1 … P6 共六个对外版本），期内按 Sprint 出内测包；单面在其出生期内不发布「半成品版」。

### 11.8 验收与度量

| 维度 | 指标 | 口径 |
|---|---|---|
| 功能完整度 | 每面独立可用性评分 | 该面出生期的期末验收项通过数 / 总项数（十八章） |
| 业务闭环 | 核心任务完成率 | 以 2.4 S1-S6 场景步数完成率度量，非问卷 |
| 跨面联动 | 联动成功率、数据一致性 | 分母 = 已发布事件数；一致性 = 对账差异为 0 的比率（18.6） |
| 质量 | 缺陷密度、自动化覆盖率 | 缺陷密度按功能域统计；覆盖率门禁：财务/权限/同步 ≥ 80%，其余 ≥ 60% |
| 安全 | 漏洞数、隐私合规率 | 二十章合规检查单逐项打勾，儿童数据为阻断项 |
| 效率 | Agent 任务完成率、一次通过率、人类返工率 | 返工率 = 被打回任务数 / 已审核任务数 |
| 用户价值 | 留存、活跃、任务完成率、建议采纳率 | 此处仅列指标名，**具体埋点口径与计算式在 P1-M1 交付的「埋点字典」中定义**（依赖见 19.5）；未在字典中定义的指标不得作为验收依据 |

### 11.9 风险与治理

- **Agent 幻觉**：关键需求、架构、安全节点必须人类审批。
- **代码质量**：CI 强制检查，Test Agent 与 Security Agent 双重审计。
- **隐私安全**：家庭数据分级、加密、权限最小化。
- **多 Agent 冲突**：Orchestrator 统一调度，冲突升级人类决策。
- **架构漂移**：Architect Agent 定期评审，版本冻结。
- **人类监督**：产品负责人、技术负责人、家庭用户代表参与验收。
- **回滚机制**：灰度发布，一键回滚，数据备份。
- **从零新建的覆盖度风险（高）**：七个系统全部新写，风险形态是「第一版比成熟单点工具弱」，财务面尤其如此——**P1 的财务面整面（M1 闭环 + M2 深度）即须达到生产级单点记账工具的完成度**。处置：M1 末按 18.3 走查闭环域，M2 末整面逐域对照清单走查，不允许以「新系统先简版」降级；每域须给出与同类主流工具的功能覆盖差异说明（覆盖走查口径见 18.6）。
- **同类账本工具并存与用户混淆风险（中）**：HomeCube 与市场上已有的家庭账本类工具长期并存，风险是同一个人或家庭同时使用两款定位相近的产品。处置：① 产品名、图标、域名、包名必须与任何其他在运产品可区分；② HomeCube 不承接、不合并任何其他系统的存量数据，文案中不出现「升级/迁移」字样（14.3）；③ 若未来发生产品合并，属六期之外的议题，不承诺时间点。
- **交付与回滚能力缺位风险（中）**：离线部署包、CI 流水与热更新链若不在 P1-M1 显式验收，仓库到期末时仍可能只有代码没有可用的发布能力。处置：P1-M1 门禁含「干净机器一条命令拉起可用环境 ≤30 分钟」（11.3、14.5 第 1 项）。
- **合规文本滞后风险（中）**：隐私政策与法务文本不在 P1-M1 判定，风险是 P1 末集中补文本导致上架与公开注册延误。处置：P1-M1 期间把四项**合规素材**做成可持续更新的底稿并纳入交付——L2/L3 字段清单（20.1）、埋点字典（19.5）、数据与日志保留期（21.4）、第三方 SDK 与数据出境清单（19.1、19.3）。P1 末附加门禁只判文本定版与确认留痕，不判素材收集。
- **七服务拓扑的运维与联调风险（高）**：目标形态是 7 个服务 + NATS JetStream + Nginx + 单集群 7 schema，家庭自托管场景的单机资源占用与部署复杂度显著高于单进程形态；跨面读与到期注册是最终一致，缺陷形态多为"时序与补偿错"而非"写错"。处置：① 一条命令全栈起停与首次恢复演练列为 P1-M1 附加门禁（14.5 第 1 项、18.2）；② 服务间调用一律带超时与降级，禁止请求链路上多跳同步 fan-out（16.3、14.7）；③ 引用完整性与投影一致性进每日对账，并作为**各期期末的阻断项**（18.6）；④ 单机资源不足时的降级路径是**同镜像多进程合并部署**（homeos 与业务面同容器不同进程），不改代码拓扑。
- **服务随面出生的重复验证风险（中）**：P1 只建两个服务，P2-P6 每期都要新建一个服务，五道门禁、Compose 编排、鉴权 SDK 接入与 Nginx 前缀都要在该面出生期重走一遍；风险是「复制上一个面的骨架时漏掉一项约束」。处置：每面的服务创建本身是一张独立任务卡，出口判据固定为四项——门禁五道全绿、`/healthz` 与 `/metrics` 可拉、该面跨服务五步走通（18.2 附加门禁①的同一判据在该面复验）、上一条目的对账零孤儿引用。**这条判据不因重复而豁免**。
- **串行排期的墙钟风险（高）**：六期串行意味着 156-189 周，任何一期的期末验收延误都会**整段后移**后续所有期，且早期缺陷（底座与财务面）的返工成本会在后期放大。处置：① P1 内分 M1/M2 两个验收点，底座缺陷最迟在 M1 末暴露；② 期末验收对象唯一（一个面），走查深度可预期；③ 期内允许按功能域并行，不得跨期并行（11.7 第 1 条）；④ 每期期末把实测周期与本表周期对比回写 18.1，连续两期偏差 >20% 即触发排期复核，而不是 silently 顺延到最后一期。
- **验收压缩风险（高）**：排期失真的根因是「用周期当承诺、用压缩代替拆解」。人类验收带宽已写成硬约束（11.7 第 4 条）；需提速时**只允许顺延期末，不允许压缩单面完整度**。

## 十二、非功能需求

本章是基础口径。数据分级与安全合规见二十章，容量、RPO/RTO、冲突解决、推送口径、AI 成本与降级、日志保留与可观测性补充见二十一章。**安全与合规口径以二十章为准，性能与容量以二十一章为准。**

### 12.1 性能

| 指标 | 要求 |
|---|---|
| 启动时间 | ≤2 秒 |
| 页面响应 | ≤300ms |
| 同步延迟 | ≤1 秒 |
| 离线支持 | 核心功能可用，可用范围见 21.6 |

| 指标 | 要求 |

| 指标 | 要求 |
|---|---|
| 可用性 | 99.9%，**按服务分别计量**（`svc-homeos` 与六个业务面服务各自一个可用性 SLA，**当期只对已出生的服务计量**，服务随面出生即 +1；家庭实例上以 `/healthz` 探针与请求成功率统计，不用全栈平均值掩盖单服务故障，22.2 第 10 条） |

## 十三、总结

**家立方 HomeCube——全家生活，立体管理。**

**一个底层系统 HomeOS + 六个业务系统：财务、采购、饮食、出行、家人、成长。**

**每面完整可交付、可独立验收，运行期依赖 HomeOS 底座；面间通过底层事件总线与规则引擎拉通。**

**七个系统 = 七个独立服务**：独立进程、独立构建、独立部署与发布，各占一个路由域、一个 schema 与一条迁移序列；服务间只经事件总线、只读接口与逻辑引用通信，不存在跨服务分布式事务与跨 schema SQL（22.2）。**服务随面出生**——P1 只建 `svc-homeos` 与 `svc-finance`，其余五个在各自出生期创建，七个命名域在 P1 一次性登记 registry（卷首第 12 项）。

**迭代不设 MVP，按 P1-P6 分期交付，每期严格交付一个面（P1 额外含底座与前端 shell），由 Agent 全流程推进，人类负责目标、优先级、验收与伦理。**

**底座路线**：七个系统全部在本仓库内从零新建，代码、schema、部署、CI 与热更新链自建，不依赖任何既有在运系统的代码、数据与资产；并存与不合并的政策见十四章。

**六面一句话：**
> 钱有账，物有库，吃有谱，行有程，人有录，长有迹。

**完成判定**：每一期的验收项（十八章）逐条可测，当期场景链路分段（2.4 S1-S6 中已出生的步骤）走通，才算该期完成；P6 期末额外要求六条场景全链路复跑。**周期可以顺延，单面完整度不压缩，验收不得压缩**（11.7 第 5 条）。

## 十四、建设边界与资产关系

### 14.1 建设边界

HomeCube 的七个系统（HomeOS 与财务、采购、饮食、出行、家人、成长六面）全部在 HomeCube 自己的新仓库内从零实现：**一面一服务**——每个系统是一个独立进程、独立构建、独立部署与独立发布的服务，独占一个 schema 与一条迁移序列。运行时拓扑与服务边界约束见 22.2 与卷首第 12 项。

新仓库的第一件事是初始化仓库与**当期服务骨架**：实建 `svc-homeos` + `svc-finance`，同时把**七个 code 的命名域一次性登记进 registry**（16.1、卷首第 12 项），其余五个服务与它们的路由、schema、分包在各自出生期创建。所有服务从第一张表起按 16.1 的 code 命名。

### 14.2 与既有项目的关系

- HomeCube 与任何既有项目**不存在**代码、表结构、迁移脚本、数据、部署或账号体系层面的复用与依赖关系。
- 禁止 import、vendor、fork 任何其他项目的源码；禁止复用其他项目的表结构与迁移文件；禁止共享数据库、域名、包名与账号体系。
- CI/CD 与部署形态（GitHub Actions 流水、离线 Docker 一键部署、热更新发布链）在 HomeCube 仓库内自行建立，不与其他仓库共享 workflow 文件。
- 名称或主题与其他项目重合不构成依赖：成长面的「学习计划」与其他本地文档类项目无引用、无数据关系，不得据此评估工作量或风险。

### 14.3 两套并存策略

- 新系统不承接任何旧系统的需求，不承诺数据迁移，不提供面向旧系统的导入导出对接。
- 文案中不得出现「升级」「迁移」类引导，避免用户误认为同一产品（11.9）。产品名、图标、域名、包名必须与其他在运产品可区分。
- 若家庭需要带走其历史账目：由原系统自身能力自理。这既不构成 HomeCube 的功能项，也不构成 HomeCube 的依赖或发布门禁。
- HomeCube 从空库开始，首个版本的数据由用户自行录入。
- 任一系统的退役、两套数据打通、单点登录，均属六期之后的议题，本文档不设计、不排期。

### 14.4 研发流程载体

不自建看板与任务卡机制，复用本地工具 Jarvis Workbench（`~/www/agent-task-board`）：

- 形态：Tauri 桌面壳 + NestJS sidecar + Prisma + 本地 SQLite。
- 接入：Agent 经 MCP `/mcp` 或 9 个 REST 工具认领任务，`claim_next_task` 带租约，避免多 Agent 抢占同一卡。
- 流程：六列看板，任务生效前强制人工审核；Agent token 与 UI token 分离；带审计日志。
- 边界：仅监听 127.0.0.1、单用户本地，属研发工具而非 HomeCube 的产品组件，不得进入产品依赖清单。
- 看板列与 PRD 流程的对应关系见 22.3；任务卡模板与人工审核的三个粒度见 11.6、11.7。

### 14.6 范围外

HomeCube 全生命周期内不做以下能力，任何相关需求默认驳回，需改变范围须另行立项评审：

- 银行、支付宝、微信账单的自动导入。
- 投资与资产管理（证券、基金、房产估值）。
- 多账本切换器：账本只是报表与归集分组单元（标签 + 成员范围 + 时间窗），不是数据隔离域，不提供账本级权限边界。
- 社交功能（好友、关注、公开动态）。
- iPad 与桌面客户端。
- 微信小程序。
- 商用短信通道；如需接入另立一期，并先确定计费与频控。
- 电商实时比价与价格抓取。
- 航司、12306 的票务状态数据。
- WHO 生长百分位参考数据。
- 真实资金划转（仅记录，不碰钱）。
- 外卖与餐厅平台对接。

工程与运行形态上不做（引入即视为超范围，需另行立项）：Kubernetes 与服务网格、分布式事务框架（2PC/SAGA）、分布式追踪全链路采样、多区域容灾与异地多活、SaaS 化多租户（每个家庭实例独立部署的口径见 21.1，不演进为共享多租户）、独立网关服务与自建服务治理组件。七服务拓扑本身的复杂度由 22.2 的边界规则与 11.9 的降级方案控制，不靠上述组件解决。

范围内但受分期约束的近期项：OCR 票据识别与语音记账为 P1-M1 新建项，接入第三方且必须可失败回落手输；多币种汇率 P1-M2；AI 消费分析 P6。

### 14.7 工程约定

以下约束对全部七个服务一致生效，由 CI 门禁（22.5）拦截：

- 金额一律以「分」为最小单位的整数存储（`amount_cents`），不使用浮点。
- 业务表软删：`deleted_at` + `deleted_by`。
- 所有写接口必须携带 `client_request_id` 幂等键。
- 列表接口强制游标分页，不接受无上限返回。
- 预置数据用可空的 `family_id` 表达：为空即系统预置，非空即家庭自定义。
- 附件目录 `uploads/{family_id}/`；单笔 ≤3 张、单张 ≤5MB、格式限 jpg/png/webp（3.6）。
- 图标使用图标集名称，禁止 emoji 回流；`check-no-emoji` 闸门进 CI。

跨服务调用与配置约定（服务端一致性，22.2 的可执行化）：

- **每个跨服务只读调用必须声明三件事**：超时（≤300ms）、重试（≤1 次）、降级结果（返回什么占位或跳过该区块）。声明写在调用点的构造参数上，未声明即 CI 失败——不存在"默认无限等待"的调用。
- **每个事件消费者必须幂等**：以 `event_type + business_id`（或 16.4 的注册幂等键）判重，重复投递不产生重复业务对象；幂等表落在**消费方自己的 schema**。
- **服务间不共享进程内状态**：不共用连接池、缓存、内存里的用户上下文；配置各自一份（同集群的连接串不同 schema 与账号），禁止读别人的环境变量文件。
- **每服务一个容器镜像、一条发布线**：镜像内只含本服务与其依赖的 `packages/*`，禁止"一个镜像七个进程"的打包形态（11.9 的临时降级除外，且降级须写进当期风险记录）。
- **对账与死信是常规手段而非异常兜底**：逻辑引用的孤儿检查、投影与源的一致性校验每日跑（18.6）；死信在本服务查询与人工重放（22.2 第 10 条），不靠"应该不会发生"。
- **健康与指标命名统一**：`/healthz`（含依赖就绪态：自己的 schema 可连、JetStream 已连）、`/metrics`（服务名 `code` 作为常量标签），供 12.3 可用性判定与 Compose 探针使用。

## 十五、权限与角色矩阵

### 15.1 角色定义

| 角色 | 可登录 | 说明 | 关键限制 |
|---|---|---|---|
| 管理员（owner） | 是 | 家庭创建者或被转让者，唯一可转让/解散 | 不能移除自己，避免家庭失去唯一管理员 |
| 成人成员（member） | 是 | 默认角色，可写业务数据 | 不能管理成员与邀请，邀请仅 owner 可发起 |
| 儿童/老人（ward） | **可无账号** | 被记录对象；有账号时（如青少年）仅有限写权限 | 由 `guardian_id` 指向监护人，代管写入带 `on_behalf_of` |
| 访客（guest） | 是（临时凭证） | 限时只读，用于保姆/亲属临时协作 | 默认有效期 30 天，可撤销；不可导出 |
| 已退出成员 | — | 历史作者标记 | 数据留家庭，作者显示「已退出成员」，见 15.5 |

### 15.2 权限三维模型

`Permission(scope, resource, action, condition)`：

- **scope = module**：某系统整体可见/可用开关，家庭可按面关闭（如不使用出行面）。**判定的唯一输入是 `FamilyModule`（3.6、16.2）**——registry 给面目录，`FamilyModule` 给本家庭启用了哪些面；除它之外不得有第二个面级开关（`Family.feature_flags` 只放非面开关）。服务端仍按本条拒绝被停用面的请求，客户端则让入口消失：**停用 = 入口消失 + 数据保留并继续参与统计**（17.8）。
- **scope = data**：数据行范围，取值限于**当前会话家庭 / 本账本 / 本人 / 指定成员**四类。一个账号最多归属 5 个家庭并可切换当前会话家庭（3.4.1）；判定始终以 token 内的 `family_id`（当前会话家庭）为界，跨家庭访问一律拒绝并落审计。「本账本」只是报表归集范围的过滤条件，不是权限边界。
- **scope = action**：`read` / `create` / `update` / `delete` / `export` / `invite` / `admin`。
- **condition**：时间窗（访客有效期）、字段（L3 字段需二次确认）、对象归属（`author == me`）。

**判定顺序**：显式拒绝 > 角色默认矩阵 > 家庭级覆盖 > 对象级 ACL。缓存失效见 15.6。

### 15.3 默认权限矩阵（角色 × 系统 × 动作）

图例：**A**=全部（读写删导）、**M**=仅自己的/本人相关、**R**=只读、**—**=无权限、**O**=仅管理员

| 系统 | 管理员 | 成人成员 | 儿童（有账号） | 儿童/老人（无账号） | 访客 |
|---|---|---|---|---|---|
| HomeOS（成员/权限/设置） | O | R（成员列表） | — | — | — |
| **HomeOS · 面配置**（面目录与本家庭挂载哪些面，17.8） | **A**（开通/停用/读写） | R（只读，用于渲染首页矩阵、「＋」目标、搜索分组等五个消费位，⑫；无开关） | R（同左，只读渲染） | —（无登录入口） | R（同左，随其有效期） |
| 财务 | A | **M 写 + R 全家庭读**；导出需管理员授权，且只导授权范围内可读的行 | — | 被记录（无写） | — |
| 采购 | A | A（清单与库存为家庭共有物） | M（可勾选完成，不可删） | — | R + 勾选 |

| 成长 | A | M 本人；R 自己监护对象的 | 记录自己 | 记录由监护人写 | — |

**本表新增的「面配置」行**：读的是「哪些面可被渲染」这一件事，不含任何业务数据；写一律收敛到管理员。18.2 附加门禁②的逐格断言**包含本行**，且必须两个服务各打一次（`scope=module` 的判定输入就是这张表，15.2、17.8）。

**账本语义**：账本只是报表与归集分组单元（标签 + 成员范围 + 时间窗），不是数据隔离域，也不是权限边界。权限一律由角色矩阵、数据范围与字段可见性决定。

**财务隐私默认**：家庭流水全员可见，作者可编辑自己创建的流水，他人流水可看不可改。「私密标记」（把某笔流水设为仅作者与管理员可见，也可对整个私密分组开启）为管理员可开启的可选特性，实现为**行级可见性**：命中该标记的行仅作者与管理员可读，且不参与 AA 分摊与跨面归集（否则与 4.9 的零误差口径互斥）。

**AA 分账适用面**：仅标记为「共享」的账本参与分摊，日常账本不摊。

**儿童记账**：默认不能记账（无写权限，仅被记录）；青少年账号可由管理员逐面开放。

**逐格断言与本表的关系**：本表七行对应七个系统，**测试用例在 P1 即按七行全量生成**，未出生系统的格子按其默认策略与 16.4 注册契约断言（服务不存在时判定为「拒绝访问 + 未启用」），该面出生期末复验本行全部格子（18.2 附加门禁②）。

### 15.4 字段级可见性

| 字段类别 | 默认可见范围 | 备注 |
|---|---|---|
| 姓名、头像、关系 | 全家 | — |
| 生日 | 全家（纪念日功能依赖） | 农历/公历同 |
| 血型、过敏史、紧急联系人 | 全家（急救场景白名单） | L3 分级；锁定屏展示需家庭开关（8.5.6） |

### 15.5 数据归属与成员退出

成员退出家庭：其创建的流水/清单/记录**留在家庭**，作者显示「已退出成员」；**其个人偏好与私密账本内容随退出删除**（导出请求需在退出前完成）；监护人代管的数据归属被记录的成员，而非代管人。

### 15.6 权限生效与缓存

- **鉴权实现只有一份**：由 HomeOS 服务发布的 `authz` SDK（随 homeos 服务的 OpenAPI 契约同仓分发），七个服务在各自中间件调用同一实现完成 `family_id` 隔离与权限判定（token 携带 `family_id`、角色快照与 `pver`）。业务 handler 内不得用裸 SQL 现场判定家庭归属，也不得自行实现判定分支，该形态由 22.5 第 4 道门禁做 CI 静态检查拦截。
- 各服务进程内权限缓存 TTL 60 秒 + 数据库层 `pver` 比对；**HomeOS 权限变更即发布 `homeos.permission.updated`，各服务订阅后立刻失效本地缓存**。「权限变更 ≤1 秒生效」（3.8、18.2#6）的口径为**服务端跨服务立即、客户端下一次请求**；SDK 不可达时按**拒绝写、允许读已缓存**降级并落审计。
- 客户端权限缓存 TTL 60 秒，同样收到该事件即失效。
- **越权尝试全部落审计日志**（21.5），连续 5 次触发通知管理员。

**本表是「面目录」，不是一份封闭清单**：六行业务面是当前登记的条目，后续新增一面即在此追加一行（新 code 的七类命名域一次性登记进 registry），并按 11.7 的「服务随面出生」在它自己的出生期创建服务、schema 与分包。**一个家庭拥有本表的哪几行由 `FamilyModule` 决定**（17.8）——registry 与家庭配置是两件事，前者是"世界上有哪些面"，后者是"这个家开通了哪些面"。

**code 是全文唯一命名权威**：同一个 code 同时是七类命名——**服务名**（`svc-{code}` 容器与进程标识）、**schema 名**（每服务一个，数据库账号仅可访问本 schema）、接口路由 `/api/{code}/*`、事件名 `{code}.`（JetStream subject 同名）、表名 `{code}_`（如 `homeos_family`、`finance_transaction`、`purchase_stock`）、前端分包名 `pages/{code}`（17.7 第 4 条）、迁移文件名 `{code}_{序号}_{描述}`（16.6）。七处必须一致，任何一处偏离即视为架构漂移，由 22.5 的第 2、4 道门禁拦截。表名在 schema 之内仍带 `{code}_` 前缀是刻意的双保险：一旦出现跨 schema 前缀的建表，门禁立刻发现。CI 归属门禁据此判定"某张表属于哪个服务"，分域边界因此在**服务、代码、事件、数据库与前端工程五层**都可见。

### 16.2 数据归属权威表（唯一可写方；他面一律只读）

本表每一行的权威归属对应**一个独立服务与其 schema**，只有该服务可写这些表；他服务读取一律走 16.3 的三种方式，跨 schema 直连在数据库账号层即被禁止（不是靠约定）。**本表是目标形态的固定七行，不随排期变化**：服务随面出生只影响「哪一行的表此刻真实存在」，不改变任何一行的归属（P1 只有 `homeos` 与 `finance` 两行落地）；CI 门禁 2 按本表逐行校验表名与所在服务，未出生行的表若提前出现即失败（11.7 第 1 条、22.5）。

### 16.3 跨面读取的（且仅此三种）方式

| 方式 | 适用 | 约束 |
|---|---|---|
| **只读接口**（跨服务 HTTP） | 实时查询（库存、偏好、余额） | 归属服务提供，鉴权走 15.2 共用 SDK；调用方**必须设超时 ≤300ms、至多重试 1 次、并有降级展示**；禁止任何形式跨 schema SQL（含只读视图），数据库账号即边界 |
| **事件订阅 + 本地投影** | 高频渲染（首页各面格子的状态句与角标、过滤缓存） | 投影表命名 `{code}_proj_{来源域}`，**只允许被本服务的订阅器写入**，可随时重建；对账任务每日校验（18.6）。渲染密集的他面数据一律走此路，不在请求链路上同步 fan-out |
| **逻辑 id 引用** | 金额、附件等不可复制对象 | 只存对方 `id`，**无物理外键、无跨 schema 约束**（微服务下不存在跨服务外键）；展示时批量调只读接口；**禁止存金额副本**（防漂移）；引用完整性由每日对账校验，孤儿引用进对账报表并告警（18.6） |

**禁止**：任何其他服务出现与权威表同构的实体或字段级第二数据源；跨 schema 直连（含 DBLink、只读视图、共用账号）；一次请求内同步 fan-out 超过 1 个他服务（首页聚合类读一律由 HomeOS 的 `home/summary` 单请求承担，**不得由前端并行请求多个服务拼装**，17.2）。

| `growth.Habit.frequency` | 周期任务 | 每日/自定义 | 打卡幂等（9.5.3） |
| `growth.Plan.deadline` | Reminder | 前 30 天 | — |

**本表按七域目标形态列全，各行随归属面出生期落地**：`finance.*` 四行在 P1（其中 `Loan→RepaymentPlan`、`Goal` 属 M2），`purchase.*` 三行在 P2，`diet.Menu` 在 P3，`kin.*` 三行在 P4，`growth.*` 四行在 P5，`trip.*` 三行在 P6。**未出生面不得预建注册行、占位提醒或空对象**（11.7 第 1 条）；到期中心在每个出生期末新增该面的注册来源，聚合与触发逻辑不改。

**注册字段映射（统一格式）**：`{ source_system, source_id, source_family_id, title, due_at|start_at|end_at, participants[], repeat, priority, done_returns_to, visibility }`

**跨服务注册方式**：业务服务在自己的写事务内登记注册意图，经 outbox 发布 `{code}.due.registered`（撤销发 `{code}.due.revoked`），由 HomeOS 服务消费并落 `homeos_*` 三对象；注册幂等键为 `(source_system, source_id, kind)`。到期触发后的完成回写同样走事件（`homeos.todo.completed` → 归属服务消费），**不回写成功即视为缺陷并进对账报表**（18.6）。注册与回写均不在请求链路上做同步跨服务调用。

**删除语义**：业务对象被删除 → 注册项级联失效；注册项被用户在到期中心完成 → **回写业务面对象状态**（`done_returns_to` 指定的回调），不回写视为缺陷。

**不注册清单（明确排除）**：`diet.MealRecord`（历史事实）、`growth.GrowthRecord`（历史事实）、`purchase.PurchaseRecord`（历史事实）、所有 `{code}_proj_*` 投影表。

### 16.5 跨面费用分类映射

- `finance.Category` 为唯一费用字典；采购/出行/成长/饮食的对象携带 `finance_category_id`。
- 首次出现"物品分类 → 费用分类"未映射组合时，**转支出前弹一次确认框**，确认结果落入 `CategoryMapping(物品分类, 费用分类)` 永久生效。
- 无映射的生成型支出进默认「其他」，并在月度对账报表中列出待认领（18.6）。

### 16.6 对研发流程的约束

- Agent 任务卡必须填 `归属数据源`（任务卡模板字段，11.6）**与 `归属服务`**，Architect Agent 评审时**核对权威表**，发现新建同构实体直接打回。
- 数据库迁移文件命名带系统前缀（`finance_0007_...`、`purchase_0001_...`），使归属在迁移层可见；**每个服务一条独立迁移序列**，版本表 per-service（22.2 第 2 条）。
- 跨服务外键（含引用他域 id 的物理外键约束）在评审中一律驳回；引用完整性走对账。

## 十七、面导航与信息架构（面集合由家庭配置）

### 17.1 一级结构（全 App 唯一）

```
┌──────────────────────────────────────────────┐
│ [示例家庭 ▾]                      🔍  🔔·    │ ← 顶栏一行：左 = 家庭切换器｜右 = 两个动作位（全局搜索、消息入口）｜**中间不放面切换器**
├──────────────────────────────────────────────┤
│                                              │
│              当前面 / 首页内容区             │ ← 首页时这里的服务矩阵是全 App 唯一的面入口
│                                              │
├──────────────────────────────────────────────┤
│  首页    动态    ＋    消息    我的          │ ← 底部 Tab 固定五项（HomeOS，不随面变化）
└──────────────────────────────────────────────┘
```

- **顶栏是一行，不是两行**（定版）：家庭切换器在左、**右侧是两个动作位**——全局搜索与消息入口（17.5）。顶栏高度与结构**与面的数量无关**，面多少都不改顶栏一个像素——这是「面目录可持续扩展」在形态上的前提。
- **面切换器不在顶栏（定版 ⑫，2026-09-29 效果图第二轮确认）**：早期定版里「面 chip 横滑在顶栏中段」这一半**已被取代**，顶栏中段是空的。**面入口只有一处 = 首页的家庭服务矩阵**（17.2），进入某面后顶栏与 D 行都不提供切面能力。
  - **接受的代价**：面内切面必须经首页——最深路径 = 返回到该面一级页 → D 行「首页」→ 点目标格 = **3 步**。这与 ⑪ 给消息入口的理由（二级页压栈后 D 行被盖住）是同一种代价，**两处结论相反是刻意的**：未读是「随时可能要看」的被动信息，切面是「带着明确目标去」的主动动作，后者本就该先回全景页。
  - **换来的红利**：客户端的面集合消费者从**六处减为五处**（首页矩阵、「＋」目标对象、搜索分组、到期中心注册项、动态流筛选），导航位与矩阵位「一处可点另一处不可点」的分歧面在结构上不存在了；面图标也不必再压缩到 14px 才能塞进顶栏，图标的唯一用途回到首页矩阵、开通页与「＋」目标列表。
  - ① 的**一行制没有被推翻**：被推翻的只是「面切换器平铺在顶栏」，保留的是「顶栏只有一行、结构恒定」。
- **顶栏消息入口与未读红点（定版）**：
  1. **它补的是 D 行覆盖不到的一条路径**：二级页压栈后 D 行被内容区盖住，未读消息仍要一步可达。首页与各面一级页上顶栏位与 D 行位同时可见，这是刻意冗余，**两处必须同源同清**。
  2. **未读只有一个口径**：服务端 `homeos_notification.read_at IS NULL` 按 `member_id` 聚合（3.6）。首页首屏由 `home/summary` 的 `unread` 字段带出（不新增第二个请求，17.2「首屏一个请求」不破），消息列表与「全部已读」由 `notifications` 接口在同一字段上返回。**客户端只持有 shell 里的一份未读状态**（与 `period` 同样归 shell 持有，17.7 第 8 条），顶栏位与 D 行位读同一份，不得各存一份、不得缓存第三份。
  3. **按位置分工呈现，语义不得混用**：顶栏位**只显红点、不显数字**（该位宽度不容纳计数）；D 行「消息」显**红点 + 未读计数**（>0 才渲染、上限 99+，3.4.2 已定版口径）；消息页内按 `budget_alert`/`system`/`reminder` 三分型各显未读计数。**C 区格子的 `badge` 是「待处理数」，与「未读」是两件事**（17.2），两词不得互相顶替、不得共用字段。
  4. **熄灭即已读**：进入消息页即读（3.4.2），顶栏位与 D 行位同时熄灭；「全部已读」走统一确认弹层，确认后两处同清。跨设备的清除按 18.2#3 口径 P95 ≤1 秒。
  5. **归 shell 所有**：红点组件、未读 store 与两个出口位都由 HomeOS 主包提供，业务面不得自建消息入口、通知中心或未读计数（17.7 第 1 条）；**分包内出现自建未读计数即 22.5 第 4 道失败**。
  6. 沿用 3.4.2 的既有约束：**免打扰时段红点照常显示、只是不发声**；`unread` 由服务端按权限过滤后给出，客户端不自行判断某条通知是否可见；红点不对 L3 内容分级，也不外露 L3 正文。深色态下红点色走 shell 的 `--danger` 令牌并满足 17.9 的对比度要求。
- **底部 Tab 恒定为 HomeOS 五项**；切换面**不改变底部 Tab**，也不清空其他面已压入的页面栈。**「首页」位是唯一的切面枢纽**：不管当前停在哪个面的一级页，点它即回到面入口矩阵；会话起始默认位也是它，用户上次所在面在会话内保持（下次进入该面仍落在它的一级页）。
- **首页矩阵的集合 = 本家庭已启用且服务已出生的面**（17.8）：未启用与未出生的面**不出现在这里**，不留描边或置灰占位。顺序恒为 registry 登记顺序（当前为 `财务/采购/饮食/出行/家人/成长`）；首页本身不在矩阵里（首页就是本页）。
- **面入口只有一处，但面集合仍是五处同源**：全景感与切面动作合并到首页矩阵（17.2）。同一份 `faces[]` 的其余四个消费者是**「＋」的目标对象选择器、搜索结果的分组、到期中心的注册项、动态流的面筛选**——五处读同一个集合，不得任何一处自己算一遍（17.8）。面内的「我在哪个面」由**该面的二级 Tab 与页内标题**承担，shell 不再提供面名标签；不出现「别处可点而矩阵不可点」的分歧。
- 各面**自己的二级 Tab 在内容区内**（面内导航），不叠加第三层底部栏；二级 Tab 的每一项落到一条列表路由（动作段 `list`，P1 落地名为 `index`，见 `docs/p1-page-structure-navigation.md` 第四章），Tab 本身由面内导航组件承载。

### 17.2 HomeOS 首页（家庭服务矩阵是首页主视觉）

首页是「家庭操作系统」的门面，职责是**一眼看见这个家开通了哪几面、每面今天要办什么**。顶栏之下先有一条**时间窗条**，再从上到下四个区：

| 区 | 内容 | 数据源 |
|---|---|---|
| （区之上）时间窗条 | 当前时间窗的标签 + **月 / 季 / 年三档**分段控件。**首页恒渲染它**——C 区财务格的状态句读 `period`，所以「只有业务面才有时间窗」的说法不成立；切换即重拉 `home/summary?period=`，四处同源（4.5.3） | shell 级 `period` store |
| A 家庭区 | **问候语**（`{时段}好，{称谓}`，时段按家庭时区、称谓取 `Member.relation`，定版 ⑭）+ 当前家庭名 + 成员头像排：**前 3 个头像 + 溢出用虚线圈「+N」**（定版 ⑮；N = 未画出的成员数，含无账号被记录成员），整排点击进入成员管理页；**家庭切换动作仍在顶栏左侧的同一入口**，A 区不放切换器 | 首屏全部由 `home/summary` 的 `family`（含 `members[]` 的 `name`/`avatar`/`relation`/`has_account`）带出，**不另发 `family` 与 `members` 两个请求** |
| B 今日区 | **跨整行卡片**：标题行「今日 N 项 · 到期与待办」+ 右上角「日历 ›」进到期中心；卡内是**当日时间轴**，横向最多渲染 **3 张小卡**——小卡 = `HH:MM` + 一句对象摘要，**底色按归属面**取面色令牌 | `home/summary` 的 `due_today` |
| **C 家庭服务矩阵** | **已启用面的宫格，首页主视觉，也是全 App 唯一的面入口**（⑫）：每格 = 面图标 + 面名 + **一句今日状态**（待买 3 件 / 今晚吃红烧肉 / 明日 09:00 接送 / 宝宝 102cm / 作业 2 项 / 预算剩余 ¥860）+ 待处理角标 | 同一聚合接口按面返回状态字段；**集合 = `FamilyModule` 已启用 ∩ 服务已出生**，服务端只返回这个集合，客户端**不补齐、不占位** |
| D 动态区 | 家庭动态流前 20 条 + 「查看全部」；条目 = **归属面图标 + 人名 + 一句动作描述（含对象摘要）+ 相对时间** | 同一聚合接口的 `dynamics`（与 `GET /api/homeos/dynamics` 同一个口径） |

- **`due_today.count` 与 `items[]` 长度可以不等**（定版）：`count` 是**今日全部**到期与待办数（标题行显「今日 N 项」），`items[]` 是服务端按 `due_at` 升序给的**前 3 条**，首页只画这三张。剩余项在到期中心看，**客户端不自行截断、也不补第 4 条**；今日只有 1~2 项时小卡按实际条数排布，不填空位。
- **到期与待办在同一条时间轴上混排**，不分两段、不打「待办」标签——B 区不是任务清单，是「今天要办的时间顺序」。小卡的强调**只由归属面决定**（面色令牌），**不存在优先级/加急字段**，服务端要给优先级请先给它一个到期时间。
- **问候语的称谓来自 `Member.relation`**（家庭内称呼，权威归属 `homeos`，16.2 与 ⑭）：P1 建档即可填，无值时回落成员名，**不得为凑一个「爸爸」去读未出生的家人面**。时段划分与文案由客户端按家庭时区计算（属格式化，不是统计聚合）。
- **头像排里无账号成员与有账号成员呈现一致**（都是姓名首字占位或头像）：「有没有账号」是治理属性，只在成员管理页显式标注（15.5、3.4.1），**首页不用虚线、灰度或角标把家庭成员分成两级**。虚线圈「+N」**是溢出计数、不是邀请入口**——首页不放任何写操作入口，邀请唯一在「我的 → 家庭成员」。
- **动态流条目的文案由服务端拼好整句下发**（与 `headline` 同一条原则：客户端只做格式化，不拼动词、不做二次聚合）；条目前面的标记**复用 registry 的面图标与面色令牌**，不引入第二套「事件类型缩写」图形——两套图标在门禁 4 里算「硬编码面清单」的同族问题。相对时间的格式（`N 分钟前` / `今天 HH:MM` / `MM 月 DD 日 HH:MM`）属格式化层，一律按家庭时区。
- **动态条目的可见性由服务端裁剪**：按 15.3 权限矩阵与 15.4 字段级可见性、20.2 分级决定某条进不进 `items[]`，被裁掉的条目**不返回、不占位、不显示「无权限查看」**；客户端收到什么就显示什么，不得自行过滤（17.7 第 4 条）。

**矩阵是变长宫格**（定版）：格数等于本家庭已启用面数，行列自适应，顺序恒为 registry 登记顺序——1~2 面每行 2 格、3~4 面 2×2、5~6 面 2×3、超过 6 面每行 3 格继续换行。**格子尺寸固定、高度由内容自然决定，不设任何首屏占比阈值**（定版：原「矩阵占首屏高度 ≥45%」的分配口径作废）——一格时强凑高度会在首页中央留出一大片空白，多格时按内容换行自然向下扩展，D 动态区被推到几屏之外不是缺陷。**格内元素顺序恒定**：面图标在上、面名其次、状态句在下，角标压在图标同一行的右上角。矩阵区标题行显示「已启用 N 面」的纯文案，右侧只允许**一句不可点的提示文案**（如「开通在「我的」」）——**首页不放「开通更多面」的入口位，也不放任何可点的说明**；开通与停用统一在「我的 → 开通更多面」（17.5、17.8）。首页是一页**纵向滚动的单页**，四区顺序 A→B→C→D 恒定，不做折叠、轮播、吸顶。

格子只有两种状态（**未启用与未出生的面根本不成格**）：

| 状态 | 触发 | 呈现 | 可否进入 |
|---|---|---|---|
| 可用 | 该面已启用、服务已出生且模块权限允许 | 实心格 + 今日状态句 + 角标 | 点击进入该面（首次进入走 17.8 的按需加载） |
| 暂不可用 | 已启用，但该面服务不可达，或它的分包校验/下载失败 | **与可用格同尺寸同结构**，仅按面去色 + 最后一次值与时效标注（12.3，「截至 HH:MM」）+ 一个「重试」动作位 | 进入后为该面不可用态，不白屏 |

- **「重试」的语义是定死的三件事**：① 重新请求一次 `home/summary`（**不是**单独打那个面的接口，首屏单请求原则不破）；② 若该格是因为分包缺失/校验失败，同时重走一次 17.8 的按需加载；③ 失败后**保持原态与最后值**，不弹错误页、不清缓存。重试是**读操作**，不进幂等键与离线队列，也不进 18.2 的任何分母。
- 首页**不呈现未启用与未出生的面**（原「六格恒在、未出生面以同尺寸描边格占位」的口径由本节取代）：一个只开通财务面的家庭，首页矩阵就是一格；开通三面即三格。
- 聚合读只走 `svc-homeos` 的聚合接口与本面投影，**不得在前端并行请求多个服务**（17.7 第 4、5 条）：**首页首屏只有一个业务请求** `GET /api/homeos/home/summary`，四区（含未读红点、时间窗三档下的状态句）全部由它带出，抓包可断言（18.2#9）。
- 格子的集合、顺序、可用性由 **registry + `FamilyModule` + 聚合接口**驱动，不由前端硬编码；**新增一个面在客户端只是多一个格子 + 按需挂载它的分包，导航结构不变**（11.3 第 ⑧ 项、17.8）。

### 17.3 面内二级 Tab（异构保留，见 1.3 第 2 条）

| 面 | 二级 Tab | 主交互形态 |
|---|---|---|
| 首页（HomeOS） | — | 摘要 + 动态流 |
| 财务 | 流水 / 报表 / 预算 / 账本 / **账户与设置** | 数据表格 + 图表 |
| 采购 | 清单 / 库存 / 记录 / 统计 / **设置** | 勾选清单 + 网格 |
| 饮食 | 菜单 / 菜谱 / 冰箱 / 记录 / **设置** | 图片卡片 + 周视图 |
| 出行 | 行程 / 车辆 / 旅行 / 记录 / **设置** | 时间线 + 地点卡片 |
| 家人 | 成员 / 照护 / 纪念日 / 分工 / **设置** | 人物卡片 + 标签 |
| 成长 | 记录 / 课程 / 习惯 / 计划 / **设置** | 时间轴 + 打卡格子 |

- **面内二级 Tab 的末位不得命名为「我的」**（定版）：底部五项的第五项已经是「我的」，面内再取同名会让用户以为两处是同一个地方。财务面末位承载账户与分类维护，命名为「账户与设置」；其余面统一「设置」。新增面按同一规则命名，不再产生重名。
- 面内末位 Tab 只管**本面对象的维护**（账户、分类、提醒阈值、记账默认项）；账号、家庭、成员、权限、导出、隐私一律在 HomeOS 的「我的」（17.5），**两处不互相复制入口**。

### 17.4 全局「＋」

四种输入：文字 / 语音 / 拍照 / 模板。**P1 至 P5 期间目标面由用户手选**（可选项只有**本家庭已启用且服务已出生**的面，未启用与未出生的面不出现在目标面选择器里，17.8），AI 归类在 P6 交付；手选路径必须保持 ≤2 步，保证"记账 ≤3 步完成"（4.9）可达。

**「＋」是一条独立路由页**（`pages/homeos/quick-add/index`），不是覆盖层：它要同时承载四种输入形态、目标对象选择器与识别结果预览，覆盖层放不下，且覆盖层会让键盘、语音按住、拍照预览三态互相抢占。取消即返回进入前的页面；**未提交的草稿不入任何业务对象**，只有用户显式「存为待办」才落 HomeOS `Todo`（17.7 第 6 条）。

### 17.5 消息 / 我的

- **消息**：站内通知（含 @、免打扰、分组）、留言板、投票入口；**是推送的唯一 App 内落点**（各面无独立消息中心）。未读红点在顶栏消息入口与底部「消息」Tab 两处呈现，**同源于服务端一个未读口径、进入即同时清零**，呈现分工见 17.1。
- **我的**：账号、家庭管理（成员/邀请/角色/权限，见十五章）、**开通更多面**（全量面目录与本家庭的启用配置，仅管理员可变更，17.8）、设置（主题/时区/货币/日期格式/语言，**主题三态见 17.9**）、数据（导出/备份/迁移，见 3.4.4）、隐私与紧急卡开关（见 15.4）、帮助与关于。

### 17.6 搜索与深链

- 全局搜索从顶栏右端进入，跨七系统；结果按面分组，且**只出现本家庭已启用且服务已出生的面**（未启用面不返回空组、不出现组标题，17.8），点击直达对象（深链格式 `homecube://{code}/{entity}/{id}`）。**搜索入口与索引都在 HomeOS 服务**：各面数据经事件投影进 `homeos_search_index`，客户端只调 `GET /api/homeos/search` 一个接口，不按面并行请求七个服务。
- 通知点击同样走深链；**L3 字段对象的深链进入需二次确认**（20.2）。

### 17.7 导航约束（防架构漂移）

1. 任何面**不得新增一级导航、不得自建消息中心、不得自建推送、不得自建全局搜索入口**。
2. 首页矩阵与「我的 → 开通更多面」是**家庭面配置**在客户端的两个消费位（module 级权限，见 15.2、17.8）：家庭停用某面时该面的首页格子消失（不置灰、不占位；**顶栏本来就没有面切换器，⑫**），该面的深链返回「未启用」态、服务端对该面的请求一律拒绝并落审计；**该面的历史数据保留且继续参与统计**。
3. 一级导航（顶栏一行、底部五项、时间窗条）与首页服务矩阵的组件由 HomeOS 提供，业务面消费（见 2.3 第 4 条「能力不重复」）；面内的「我在哪个面」由该面的二级 Tab 与页内标题承担，**不得为补位置感在分包内自建面切换器**——那正是 ⑫ 刚从顶栏拿掉的东西。
4. 前端工程按面分 **subPackage**：`pages/homeos`（一级导航 + 面 shell + 动态 + 消息 + 我的 + 面配置）为主包，每个面一个分包；**分包随面出生、按启用加载**——`pages/{code}` 与其路由只在它的出生期创建，未出生面与家庭未启用的面**都不留空分包、不在任何导航位上占位**（11.3 第 ⑧ 项、17.8）；用户首次进入某面（或该面被本家庭启用）时**按需加载**它的分包，可按清单远程下发并做完整性校验，校验失败降级为「暂不可用」而不是白屏。分包不得互相引用页面，跨面跳转只走深链（17.6）。分包边界避免各面在主包体积与构建产物上互相拖累，也是服务随面出生在客户端侧的对应物。**分包与路由域一一对应**：`pages/{code}` 内的页面只调 `/api/{code}/*` 与它显式声明的他服务只读接口，跨面聚合数据取 HomeOS 聚合接口或本面投影，不得在前端拼装七个响应。
5. 客户端**只对一个 base URL**：所有请求走 `https://{host}/api/{code}/*`，由 Nginx 按前缀反代到七个服务（卷首第 12 项、22.2 第 8 条）。客户端不得持有各服务的独立地址与端口，不得在 App 内做服务发现；离线重放队列、同步游标与埋点同样按 `(family_id, service)` 分组，但目标地址始终是同一个 host。
6. **页面全部为独立路由，按「面 + 功能域 + 动作」三段划分**：`pages/{code}/{feature}/{action}`，一条路由对应一个页面一个职责。**不注册原生 tabBar**——一级五项导航与首页服务矩阵由 HomeOS shell 的自定义导航组件承载（顶栏不含面切换器，⑫），一级页之间用**无栈替换**，二级页压栈、返回即出栈；这样面及其功能域可以随出生期无限增页、无限增面而不受原生 tabBar 的槽位数与固定页面栈约束，也让每条路由都可被深链直达。
7. **动作成页的判定**（防页面数失控）：`list`（列表位，P1 落地动作段名为 `index`）/ `detail` / `create` / `edit` 各占一条路由；**破坏性动作不占路由**——删除、撤销、结清、恢复、退出家庭、解散家庭一律走统一的**破坏性确认弹层**（二次确认 + 影响说明 + 需要时填理由 + 落审计），空态是页面的一个状态而不是一个页面；列表内多选是列表页的操作态，不单独成页。
8. 一级导航、家庭服务矩阵、面目录与启用配置视图、全局「＋」、深链解析、状态组件、格式化与埋点由 **HomeOS 主包提供**，业务面只消费；业务面不得在自己的分包内实现或改写跨面导航组件与本家庭面配置逻辑（17.7 第 1、3 条的可执行形态）。


### 17.8 面目录与热插拔（面集合由家庭配置）

**六个面不是固定承诺**。产品形态是「一个 HomeOS 底座 + 一个可持续扩展的面目录」，一个家庭拥有其中哪些面由**家庭管理员选择配置**——这同时是客户端导航规则、服务端权限规则与前端工程的加载规则。

| 概念 | 唯一权威源 | 说明 |
|---|---|---|
| **面目录** | registry（16.1） | 全量可选面及其七类命名域；新增一面 = 追加一条 registry 条目，不改动导航与配置的既有结构 |
| **面配置** | `FamilyModule`（3.6、16.2） | 本家庭启用了哪些面，一行一个 (家庭, 面)，**无行即未启用**；`Family.feature_flags` 不放面开关 |
| **已挂载面集合** | 两者的交集 ∩ **服务已出生** | 首页矩阵、「＋」目标对象、搜索分组、到期中心注册项、动态流筛选**共用的唯一集合**（**五处**；「顶栏 chip」这一处已由 ⑫ 移除，顶栏不消费面集合的任何形态） |

**生效与传播**：管理员开通/停用某面 → 写 `FamilyModule`（`version` 乐观锁）→ 落审计 + `pver+1` + 发 `homeos.family.module.updated` → 各服务鉴权缓存失效（15.6）、客户端重建首页矩阵与其余四个消费位。生效时限按 **18.2#9** 判定。**不新增第二套开关**：服务端权限判定仍走 15.2 的 `scope = module`，其输入就是本表的启用状态。

**停用语义（定版）：入口消失 + 数据保留并继续参与统计。** 停用某面后——

1. 首页格子、「＋」目标、搜索分组、到期中心注册项、动态流筛选**五处同时消失**（不置灰、不占位）；该面的深链返回「未启用」态，服务端对该面的请求一律拒绝并落审计。
2. **该面的历史数据不删、不隐藏、不改变任何统计口径**：HomeOS 动态流、跨面费用归集（16.5）、AA 分摊、每日对账（18.6）、备份与恢复（21.3）、已生成单据与逻辑 id 引用一律照常。**停用是入口开关，不是数据开关。**
3. 重新启用即入口回来，历史数据立即可见，不需要重新导入或补算。
4. **停用有下限：不允许出现 0 面家庭。** 当本家庭只剩最后一个已启用面时，停用请求被服务端拒绝并返回业务错误码，客户端在该面的开关上提示「至少保留一个面」——与创建期「至少选 1 个面」是同一条约束的两端（14.5 第 2 项、17.8 选面引导）。因此首页服务矩阵恒 ≥1 格，不存在「空矩阵」态位。

**新家庭创建必须经过选面引导（定版）**：`family-create` 提交家庭信息后**强制**进入选面步骤，**至少启用 1 个面**才能完成创建，该步骤不可跳过。可选项只列服务已出生的面；未出生的面在目录页以「即将上线」呈现且不可选。**加入已有家庭不重新选面**——跟随该家庭当前的配置。

**客户端热插拔**：App 默认只加载**基座**（HomeOS shell + 一级导航 + 面配置 + 状态组件 + 鉴权与同步 + 格式化与埋点），面的前端代码按分包独立交付、**按需加载**：

| 环节 | 口径 |
|---|---|
| 构建 | 每面一个分包 `pages/{code}`，与它的路由域一一对应（17.7 第 4 条）；**基座不 import 任何面分包** |
| 清单 | `GET /api/homeos/app/bundles?codes=…&installed=…` 返回每个面分包的 `version` / `url` / `sha256` / `size` / `min_compat`（与基座的最低兼容版本） |
| 加载 | 用户首次进入该面、或该面被本家庭启用时拉取并校验；**校验失败、超时、版本不兼容都不进白屏**——该面显示「暂不可用」态并提供重试，基座与其他面照常可用 |
| 缓存 | 分包按 `(code, version)` 缓存；该面有新版本或被关闭时清理旧缓存；本地空间不足按最近未使用淘汰 |
| P1 范围 | **按需启用、清单接口、校验与回退、缓存清理全部在 P1 落地**（14.5 第 8 项、18.2#9）；**真实远程下发链路自 P2 起启用**——P1 的财务分包随基座一起发布，但走同一条清单与校验代码路径，不存在"以后再改架构"的欠账 |
| 合规 | Android 侧动态下发代码受应用商店政策约束：**iOS 不采用动态代码执行形态**，只走 wgt 资源包与商店更新（3.4.8）；下发的包必须服务端签名 + 客户端校验，禁止任何未校验来源（二十章） |

**明确不做**：面配置不是租户边界（15.2 的 `scope = data` 仍以 `family_id` 为界）；不为开通面设付费墙或试用（商业化不在此范围，需另行立项）；不在首页、顶栏或「＋」里常驻未启用面的占位入口。

### 17.9 主题与外观（亮 / 暗 / 跟随系统）

**三态**（定版）：`跟随系统`（默认值）/ `亮色` / `暗色`。入口在「我的 → 设置」的既有主题项（`homeos/settings/index`，**不新增页面与路由**）；选「跟随系统」时订阅系统主题变化并即时重绘。

| 项 | 口径 |
|---|---|
| 生效范围 | **设备与账号本地偏好，不是家庭级配置**：同一家庭的两个成员可以一个亮一个暗；存 `storage`，不与服务端同步、不进 3.4.4 的数据导出范围 |
| 切换代价 | 不丢页面栈、不清 `period`、不需重新登录、不闪白屏；当前页在同一帧内重绘（18.2#10 逐三项断言） |
| 令牌单源 | 颜色、圆角、阴影、间距与字号层级**由 shell 出一份主题令牌（亮/暗两套值）**，业务面只引用令牌；**分包内出现硬编码色值即 22.5 第 4 道失败**（与「无切换家庭调用」「无硬编码面清单」「无自造时间窗状态」同一条门禁，17.7 第 8 条的可执行形态） |
| 对比度 | **亮、暗两态分别达标**：正文与图标对背景 ≥4.5:1，大号文字与图形 ≥3:1（WCAG AA）；六个面的识别色在两态下各给一组值，暗色下降饱和度以保住叠加在其上的文字对比度。**灰阶层数由达标线决定，不由视觉偏好决定**：凡是承载文字的次级/三级灰（含 10~11px 的时效标注、相对时间、`as_of`、「+N」、区标题右侧的纯文案）在两态下都必须各自 ≥4.5:1；达不到这条线的**第四级浅灰只能用于描边、分隔线与占位图形，不得承载文字**——效果图 0929 复核时亮态第三/四级灰实测 3.0:1 与 2.3:1，即按本条上调后达标 |
| 不反色的内容 | 用户产生的图片类内容（票据附件、菜谱图、头像、二维码）**不做反色或滤镜**，暗色下只调整容器、描边与阴影 |
| 一套态复用 | 九个全局态（`docs/p1-page-structure-navigation.md` §八）在两态下**是同一组件、同一文案库，只有令牌值不同**（17.7 第 8 条）；未读红点与待处理角标的取色见 17.1 第 6 条 |
| P1 范围 | **深色随 P1-M1 交付并进 P1-M1 验收**（18.2#10）。它是 shell 的一次性投入（令牌表 + 逐屏走查），**不新增业务功能、不计入 11.3 的八项增量**；若实测因此超出 M1 的 26-31 周区间，按 11.3 的顺延规则处理，**不得以裁剪深色来对冲工期** |
| 不做 | 不做自定义皮肤与主色选择器；不做「省电模式自动深色」；不做单页局部反色与页面级主题覆盖；**语言与英文本地化不在此节**（12.4，P6 末统一交付） |

## 十八、验收口径表

本章是七个系统验收的唯一权威口径：每条指标均补齐度量定义、分母/样本与判定方式后方可进入各期验收；其他章节的验收表述与本表冲突时，以本表为准。**本章按「一期一面」组织**——每个面的验收项在它的出生期末判定，期次归属见 18.1 与 11.3。

### 18.1 通用判定规则

- **计数口径**：除特别说明，性能指标一律取 **P95**，样本量 ≥ 100 次，测试环境为**中端 Android 真机 + iPhone 各一台**，网络分别取 Wi-Fi 与 4G 两轮。
- **跨服务测量口径**：七服务目标拓扑（随出生期逐段达成，11.1）下，延迟类指标一律测**客户端可观测的端到端耗时**，包含 Nginx 反代、服务间调用与事件消费等待；**不得用单服务内部 handler 耗时替代**。跨面聚合类接口（如 HomeOS 首页摘要）必须在测量报告中记录 **fan-out 跳数与降级后取值**；一次请求同步调用超过 1 个他服务即视为实现缺陷（16.3），不是性能问题。**当期尚无他服务时，该口径判已出生服务之间的调用**（P1 = `homeos` ↔ `finance`）。
- **最终一致性测量口径**：跨面效果（生成型单据、到期回写、投影刷新）的验收以**收敛时间**度量，默认 P95 ≤ 5 秒、P99 ≤ 60 秒；超时未收敛计入 18.6 对账差异。
- **判定人**：Test Agent 出报告 → 人类按任务卡/切片/期三级验收（11.6）。**任何「零误差/100%」项必须给构造样本，不接受「未发现异常」作为通过理由。**
- **期次口径（一期一面）**：本章各表按其**出生期**判定——18.2 底座段在 P1-M1，18.3 在 P1（M1 判闭环域、M2 判整面），18.4 在 P2，18.5 按面分判（饮食 P3、家人 P4、成长 P5、出行 P6），18.6 的全链路收口在 P6。判定前不存在的对象不得作为「未通过」计入分母，也不得用「以后再测」跳过：属当期的项当期判，属后期的项在 11.3 对应期列里判。
- **依赖未出生面的指标延后判定**：凡度量集合依赖尚未出生的面（例：跨六面搜索命中、忌口端到端、跨面对账），在 P1-P5 只判**当期可测的子集**并记录子集口径，完整口径在该依赖面出生期或 P6 判定。延后判定不等于降级，目标值不因延后而改变。
- **不可测即阻断**：无法定义分母的指标不得写进验收。尚未定死目标值的项集中于 18.7（P6），统一按「先测基线再定目标」执行。

### 18.2 HomeOS 与跨面通用（以 3.8 为主体，含 3.4.2、15.3、17.8、17.9 的补充验收项，共 10 条 · 底座段判定于 P1-M1）

| # | 指标 | 度量定义 | 分母/样本 | 判定方式 |
|---|---|---|---|---|

| S1-S6 场景分段走通 → **P6 全链路复跑** | 每条场景按 2.4 的步骤序列执行，人工 + 自动化各 3 轮；**当期只判已出生对象覆盖的步骤段**，段名与 2.4 的场景定义一一对应 | **分段与完整判定期见 2.4 表末列**：P1-M1 = S6 财务段（单人）、P1-M2 = S6 财务段（家庭多成员 + 预算/账单）、P2 = S5 采购段与 S1 的采购→财务段、P3 = S5 完整 + S1 菜单段、P4 = **S1 与 S4 完整链路**、P5 = S3 成长段、P6 = S2/S3 完整 + **六条全链路复跑**。判定内容：步骤可全部完成、无死链、无数据丢失，且每步的归属服务写入与只读引用可核对。**分段通过不豁免 P6 复跑** |

### 18.7 P6 智能化验收（目标值暂不定）

建议采纳率、自动化率、预测准确率等指标：P6 上线后**先测 4 周基线**，再由人类定目标值并回写本节。硬性要求只有两条：

1. AI 不可用时主流程 100% 可手工完成（降级链路与 19.1 「失败降级」列、21.7 超时回落口径一致）。

### 19.2 明确排除的外部数据源

以下外部数据源一律不接入，对应能力不做（已写入 14.6 范围外的不再重述）：电商商品库与实时价格抓取、促销信息抓取；航司/铁路票务状态与延误数据；外卖平台订单同步；餐厅点评数据；营养成分权威库（饮食营养为自填参考值，6.5.7）；WHO/国标生长百分位数据（9.2）；银行/支付宝/微信账单自动导入；真实资金划转通道（4.5.7）。

### 19.3 供应商与成本决策的落地要求

由 Architect + DevOps Agent 产出**依赖选型表**（供应商、单价、免费额度、限流、合同与数据出境评估）。**定版时点分两级，两级都在本表判**：

- **随面定版**：某项依赖是它**宿主子域**的开工前置——OCR 与 ASR 随财务面录入，须在 **P1-M1 开工前**定版（11.3 第 ⑩ 项、14.5 第 10 项）；条码库随 P2、菜谱识别随 P3、地图 SDK 随 P6，各在**该子域开工前**定版。未定版的依赖**不得进入对应功能的排期**。
- **整表定版 = P1 末附加门禁②**（18.2、14.5 第 14 项）：推送通道、对象存储与其余候选项在同一张表内定版；**未定版阻断 P2 开工，不阻断 P1 的底座与财务交付**。

两级都不阻断 P1-M1 的底座骨架——底座段内一切外部服务以适配器接口 + 本地实现或桩交付（站内信、手工录入、纯文本地点、单机磁盘附件）。本文档不锁供应商，但锁三条规则：

1. 任何付费依赖必须有家庭级用量上限与用量告警。
2. 任何依赖第三方模型/识别服务的能力，其手工路径必须与自动化路径同批次交付（不允许「先上 AI、后补手输」）。
3. 选型未定版期间，代码不得写入供应商专有 SDK 调用；外部依赖只允许出现在 `adapter/` 层，替换供应商不得触及业务域与 schema。

### 19.4 存储迁移触发条件

满足任一即从单机磁盘迁对象存储：单家庭附件总量 > 20GB；全实例 uploads 目录 > 200GB；图片加载 P95 > 800ms；出现磁盘 IO 导致的写失败。迁移需含历史文件搬迁与 URL 重写，作为独立任务卡而非顺带改造。

### 19.5 埋点字典（P1-M1 交付物）

11.8「用户价值」维度依赖此字典。要求：每个指标给出事件名、触发时机、属性字段、计算式、留存周期；**每个埋点事件必须携带 `family_id` 维度**，否则家庭级指标统计与用量告警（19.3）无从计算；**未在字典中定义的指标不得作为验收依据**。字典与二十章的数据分级表交叉核对：**埋点不得携带 L3 字段内容**，只允许携带「发生了某行为」级事件。

## 二十、数据分级与安全合规

### 20.1 分级定义

| 级别 | 定义 | 加密方式 | 服务端可搜索 | 典型数据 |
|---|---|---|---|---|
| **L1 普通** | 家庭协作必需、泄露影响低 | 服务端存储加密（AES-256）+ TLS 1.3 | 是（可建索引） | 清单条目、菜谱正文、行程标题、库存数量 |
| **L2 敏感** | 财务与健康相关，泄露影响中 | 字段级加密，密钥独立管理 | **受限**：密文不落可搜索索引，走本地索引或脱敏字段 | 交易金额与备注、账户余额、借贷对象、体重 |
| **L3 高敏** | 儿童数据、医疗急救、偏好隐私 | 客户端加密后上传，服务端仅存密文与密钥封装 | **否**（服务端不参与搜索，仅本地可搜） | 成长照片与身体数据明细、血型过敏详情、紧急卡、尺码/礼物心愿 |

**与 12.2「端到端加密」、3.8「跨六面全局搜索」的并存口径**：不承诺全量端到端加密，承诺 **L3 端到端 + L2 服务端字段加密 + L1 全量可搜**。全局搜索默认覆盖 L1 + L2（L2 搜脱敏字段）；L3 仅在本机已解密状态下参与本地搜索。

### 20.2 分级访问规则

- L3 读取需**设备级解锁 + 会话内二次确认**；深链进入 L3 对象同样确认（17.6）。设备级解锁的实现载体是 3.4.8 的**本地 PIN**（散列出端、服务端不托管）；未设 PIN 的家庭在首次进入 L3 对象时引导设置，可跳过但跳过后仍需在会话内二次确认。
- L3 内容**不进入埋点、不进入导出默认集、不进入推送正文**（推送只说「有一条新记录」）。
- 锁定屏紧急卡是 L3 的**唯一受控例外**：需家庭开关显式开启 + 白名单字段（8.5.6、15.4）。
- 导出：L2 可选、L3 默认排除，导出行为本身记审计。

### 20.3 儿童数据与个人健康信息（最高风险，阻断级）

- 成长面儿童照片/身体数据/里程碑（9.5.1）与家人面健康字段（8.5.1）属**儿童个人信息与敏感个人信息**：需**监护人显式同意**（首次建档单独同意弹窗，文案可留档截图）、可撤回、可一键导出与彻底删除。
- 儿童数据默认**不参与 AI 训练与第三方模型调用**；任何 AI 能力若需处理儿童数据，必须单独评审并在此节记录结论（成长报告使用本地聚合数据，不调用外部模型）。
- 分享：成长报告「家庭分享」默认生成**脱敏摘要**，含照片的原图分享需逐次确认。

### 20.4 法规落实清单

| 法规 | 适用点 | 落实项 | 期 |
|---|---|---|---|
| 《个人信息保护法》 | 敏感个人信息（健康、金融账户）、单独同意、最小必要 | 分级表（20.1）+ 单独同意流程 + 埋点字典不含 L3 | P1 末前完成 |
| 《儿童个人信息网络保护规定》 | 家人面健康字段（P4 出生）与成长面儿童数据（P5 出生） | 监护人同意、专章 20.3、默认不外传 | **P4 起适用**（家人面建档与 L3 字段级隐私即需监护人同意链路），**P5 期末全面可测**（成长面出生，20.3 全部项为其阻断验收，11.3） |
| 《数据安全法》/ 等保实践 | 数据存储与访问审计 | 审计日志（21.5）、密钥管理、权限最小化 | P1-M1 |
| GDPR（仅在服务境外用户时） | 数据可携带、被遗忘 | 导出/删除能力已内建（3.4.4 + 20.3） | **属六期之外的运营决定**（11.2 之外的远期）：仅在实际向欧盟用户提供服务时适用，不占期排期；导出与删除能力随其宿主面出生期交付 |
| **隐私政策与用户协议** | 产品上架、注册与数据处理合规的前置项，属 HomeCube 自建交付物 | 可读的隐私政策/用户协议页面 + 首次登录确认留痕 | **P1 末附加门禁**（18.2 P1 末附加门禁①、12.2；P1-M1 不判定，但 P1 公开注册与 iOS 出包前必须完成） |

### 20.5 安全基线补充

密钥管理（KMS 或本地密钥文件 + 权限隔离）、备份包同样加密、生产环境凭据不入代码库与日志、管理台二次认证、依赖漏洞扫描进 CI。

## 二十一、非功能需求补充

### 21.1 容量模型（按家庭与按实例两级）

容量口径分两级、互不替代：**按家庭**限定单户数据量与告警线，**按实例**限定单部署可承载的家庭总数。

| 级别 | 项 | 假设 | 上限告警 |
|---|---|---|---|
| 家庭 | 人数 | 2-6 人，≤12 硬上限 | — |
| 家庭 | 财务流水 | **30 笔/周 ≈ 1.6 千条/年；5 年 ≈ 8 千条/家庭**（六口之家含代管写入，容量规划按 **×5 冗余取 ≈ 4 万条/家庭为上限**） | 单表 > 500 万行启动分区（21.2，跨家庭全表口径）。**测试用的 6 万条 = 该上限 ×1.5 的压力样本，不是家庭真实量级**（18.2#4、18.3#2 同此构造口径） |
| 家庭 | 库存条目 | ≤3000 | — |
| 家庭 | 图片/附件 | 单笔 ≤3 张、单张 ≤5MB（14.7） | 单家庭 > 20GB 触发 19.4 迁移 |
| 家庭 | 事件量 | 峰值 ≤50 事件/分钟/家庭 | 单服务死信堆积 > 100 告警 |
| 实例 | 家庭总数 | **P1-P6 各期同一口径**：单实例可承载 ≤5 万家庭（上限针对七服务全出生的目标形态；服务随面出生不改变该上限，各期只测当期服务） | 超出即触发读写分离评估 |
| 实例 | 全栈资源 | **当期服务** + NATS JetStream + Nginx + Postgres 同机 Compose 起停：P1 = 2 服务，此后每个出生期 +1；**七服务全出生时最低 4C/8G 可用**（目标形态阈值）。各出生期末按当期服务数实测并写回本行（P1-M1 首次实测即门禁，14.5 第 9 项） | 当期实测内存占用超过当期阈值即触发 11.9 第 ④ 项合并部署降级 |

**验收样本口径**：压测样本一律按单家庭容量上限**上浮 50%** 构造——18.2#4 与 18.3#2 的 6 万条流水样本即 5 年上限 4 万条 × 1.5；其余各面的样本库同此系数。

### 21.2 性能细化

- 流水表按 `family_id + occurred_at` 分区/索引；5 年数据量（6 万条/家庭口径，见 21.1）下 18.3#2 的补充口径为 P95 ≤500ms。
- 报表一律走预聚合表（日/月粒度），不接受对明细的全表扫描式统计。
- 列表接口强制游标分页，**禁止无上限全量拉取**、**禁止用列表接口代替单条查询**（编辑场景只取单条，禁止「编辑拉整月再逐条匹配」的写法）。
- 图片：缩略图 + 原图分档；列表页不得加载原图。

### 21.5 审计与可观测

- 审计事件：登录、权限变更、跨家庭访问尝试、导出、删除、L3 读取、规则启停、死信重放、代管写入（`on_behalf_of`）。审计日志落 `svc-homeos`，由归属服务经事件上报（跨面尝试也要记，字段带 `code`）。
- 管理后台提供按家庭维度的审计查询与联动对账报表（18.6）。
- 指标采集：接口 P95/P99、错误率、事件堆积与死信数、同步重放冲突数、跨服务调用量与耗时、最终一致性收敛时间、推送回执率、依赖调用量与成本（19.1）、崩溃率。**全部指标带 `family_id` 与 `code` 两个维度，当期在运的每个服务分别出图**（服务随面出生，图板数量随期增加，每个出生期末新增该面一行）；跨服务调用的失败与降级计入被调用方与调用方两侧。P1-M1 按 14.5 第 9 项建**最小指标 + 告警集**：不追求全量可观测，先覆盖 3.8/18.2 的可测项、死信堆积与收敛时间。

### 21.6 离线与同步补充

- 离线可用范围（对齐 12.1「核心功能可用」，**按当期已出生面适用**——P1 只有记账，其余随各面出生逐期加入）：记账、清单勾选、库存出入、饮食/成长记录、查看档案与行程；**离线不可用**：跨家庭切换、邀请成员、权限修改、AI 录入。
- 重放冲突：客户端保留冲突提示（金额型被拒绝需重拉重试，3.4.4），不做静默丢弃。

### 21.7 AI 成本与延迟约束

单次 AI 调用 P95 ≤3s，超时即走手输路径且不阻塞主流程；每家庭每日调用量上限可配置；用量与成本进 21.5 指标看板，超阈值自动降级为「建议功能隐藏」。**本节约束所有已交付的 AI 能力**：P1-M1 的小票 OCR 与语音记账、P2 条码、P3 菜谱识别即已适用（家庭级用量上限随 19.3 定版写入设置项），P6 的归类与预测沿用同一上限与降级机制，不另设一套。

### 21.8 推送到达率口径

见 18.2#2 的双口径拆分；系统级不保证送达的通道（APNs/厂商通道）不计入产品验收分母，改测服务端触发成功率 + 客户端展示率观测值。

## 二十二、技术约束与研发流程载体

本章不重复需求内容，只给研发侧的既定约束。

### 22.1 技术栈约束

1. **既定选型**：服务端 Go + Gin + GORM + PostgreSQL（单集群、每服务一个专属 schema 与一个专属数据库账号）；消息载体 NATS JetStream（3.4.6、10.4）；客户端 uni-app(Vue3) → Android/H5；管理台 Vite + React。选型理由：同栈复用团队已有的部署、热更新与 CI 能力，换栈收益不明确。「顺手换框架」的提案默认驳回。
2. **偏离需评审**：任何换栈/加中间件（缓存、搜索引擎、第二套消息载体）必须在任务卡标注，并经 Architect Agent 评审通过。**JetStream 属既定选型，不算新增中间件**；除此之外 P1-M1 不引入 Redis 与独立搜索集群：搜索用 PostgreSQL 全文索引，索引由 `svc-homeos` 单独持有、**各面数据在它的出生期经事件投影喂入**（P1 = 财务面，14.5 第 7 项），达到 21.1 容量上限再评估独立集群。
3. iOS 出包依赖 Apple 开发者账号（19.1），无账号期间以 H5 + Android 交付。
4. 微信小程序不启用（14.6）。

### 22.2 架构约束

1. **一面一服务**：七个系统 = 七个独立服务 `svc-{code}`，各自独立进程、独立构建、独立部署、独立发布，独占一个 schema 与一条迁移序列。**服务随面出生**（卷首第 12 项、11.1）：P1 实建 `svc-homeos` + `svc-finance`，其余五个在各自出生期创建，七个 code 的命名域在 P1 一次性登记 registry。**不设独立 API 网关服务**：入口由 Nginx 按 `/api/{code}/` 前缀反代，跨面聚合读由 `svc-homeos` 承担。拆分粒度不因规模变化而放松，合并部署不作为架构选项（仅在 11.9 的联调风险下作为临时降级）。
2. **数据库账号即边界**：每服务一个专属账号，仅授本 schema 权限。**禁止跨 schema SQL、DBLink、只读视图、共用账号**——隔离靠权限而非约定。
3. **跨面读取三选一**（16.3）：跨服务只读 HTTP／事件订阅 + 本地投影／逻辑 id 引用。**跨服务无物理外键**，引用完整性走每日对账（18.6）。跨服务只读调用超时 ≤300ms、至多重试 1 次、必须声明降级结果；**一次请求内同步 fan-out 至多 1 个他服务**。
4. **联动一律走事件，不存在跨服务分布式事务**：一次写只落在一个服务，跨面效果经 outbox + JetStream 达到最终一致（3.4.6、10.4）。**禁止在请求链路上同步调用他服务的写接口来完成联动**；禁止发布事件目录外的事件。
5. **鉴权单一实现**：`authz` SDK 由 `svc-homeos` 发布，七服务在各自中间件的同一位置调用（15.6）。**各服务 handler 内禁止自写角色判定分支**。
6. **迁移文件带系统前缀并各成序列**（16.6）：`{code}_{序号}_{描述}`，每服务只重放自己那条序列，使数据归属在服务与版本两层都可见。
7. **契约冻结**：**P1-M1 末**冻结 `svc-homeos` 底座契约（3.7 + 16.4）与七域 registry（命名域一次性登记，卷首第 12 项）——此后各期不得改底座主干，只扩事件目录与投影映射；**每面出生期末**冻结该面自己的对外契约（OpenAPI + 该域事件目录），冻结后该面进入维护态。**期与期之间不因契约冻结而并行**（11.7 第 1 条）。任何已冻结契约的破坏性变更必须升 `version` 并过契约门禁（22.5 第 5 道）。
8. **路由必须分域**：`/api/{code}/*`，不允许出现根路径业务接口；Nginx 只做前缀转发与 TLS，**鉴权不因反代而豁免**，仍在服务内中间件完成。
9. **写模型必须有版本与软删**：所有业务实体带 `version`（乐观锁）与 `deleted_at`/`deleted_by`（软删）；展示字段不得挂在实体结构体上由 handler 拼装，一律走 DTO/投影层。
10. **每服务可独立运维**：暴露 `/healthz`、`/metrics`，死信查询与人工重放走本服务 `/api/{code}/dead-letters`；日志、埋点与指标必须带 `family_id` 与 `code` 两个维度，按服务分别出图（12.1、21.5）。

第 2、3、4、5、8、9 条为架构红线，自第一行代码起生效，不接受「先这样以后再改」。

**明确不做**：Kubernetes、服务网格、分布式事务（2PC/SAGA 框架）、分布式追踪全链路采样、多集群分片。家庭级私有部署的规模不需要它们，引入即视为超范围（14.6）。

### 22.4 仓库与并存关系

- HomeCube 代码仓库：`~/www/HomeCube`，**七服务 + 共用 SDK + Web + Admin 同仓 monorepo**（14.1）：`server/services/svc-{code}`×7 与 `server/packages/*`（authz SDK、总线、到期注册、同步、DTO），`web`、`admin`、`deploy`。**目录按服务随面出生**：P1 只存在 `svc-homeos` 与 `svc-finance` 两个服务目录与一个 `pages/finance` 分包，其余五域只占 registry 条目；未出生面不得建空目录、空 schema、空分包（11.7 第 1 条）。同仓不等于同进程：每服务一个 `cmd`、一个镜像、一条发布线。数据库从空库开始，schema 与迁移序列逐服务随出生期新建，目标形态为七个 schema、七条序列。
- 目录结构、依赖方向（服务可依赖 `packages/*`，`packages/*` 不得反向依赖任何服务，服务之间不得直接 import）由 22.5 第 4 道门禁静态检查。
- 部署形态：离线 Docker Compose 全栈（**当期服务镜像** + Nginx + NATS JetStream + Postgres，P1 = 2 镜像、目标形态 7 镜像）与热更新发布链在本仓库自建；单服务可独立升级，发布顺序为 `svc-homeos` 先于各业务面服务。
- HomeCube 与其他在运系统是**独立产品、独立数据库集群**：不存在主干/分支关系，不做代码合并，不承接其他系统的存量数据，不共用任何 schema、账号与域名（14.3）。
- 红线（14.2）：不 import / vendor / fork 其他项目的任何源码；不复用其他项目的表结构与迁移文件；不共享部署环境、域名、包名与账号体系。
- 产品文案不得引导用户「升级/迁移」，产品名、图标、域名、包名必须与其他在运产品可区分（14.3、11.9）。

### 22.5 CI/CD 与发布门禁

CI/CD 在 HomeCube 仓库内自建：GitHub Actions（lint/test/build，按服务并行且互不阻塞）、离线 Docker 部署包、一条命令部署带回备份与回滚；workflow 文件不与其他仓库共享。发布门禁**共五道**，P1-M1 起全部接驳，任一命中即阻断合并或发布；**每个新服务出生时即按同一五道复验，不因前一面已通过而豁免**（11.9）。检查项按 registry 的七域命名而非当期在运服务，因此未出生面的规则同样在 CI 中生效：

1. **迁移门禁**：CI 按服务校验各自迁移序列——迁移文件必须落在自己 `code` 的序列内且只触碰本 schema，测试库可逐服务全量重放。
2. **归属门禁**：CI 静态检查新建表是否命中 16.2 权威表、表名前缀是否与所在服务一致，出现跨域同构实体或跨 schema 建表即失败（16.6）。
3. **验收门禁**：十八章指标接入自动化测试报告，未达标不得进灰度；发布按家庭白名单灰度，回滚 = 切回原镜像 tag + 恢复备份。
4. **分域与鉴权门禁**：CI 检查路由是否全部落在 `/api/{code}/*`；handler 内是否出现家庭归属裸 SQL、自写角色判定分支（必须经 `authz` SDK）；业务表是否带 `version` 与软删字段；是否出现跨 schema SQL / 跨服务 import / 请求链路上的同步写调用；跨服务只读调用是否声明了超时、重试与降级（14.7），事件消费者是否带幂等键；**前端工程同属本门禁**——`pages.json` 的分包集合必须等于 registry 中「出生期 ≤ 当期」的域集合、**无原生 `tabBar` 字段**、每条路由都是三段式（17.7 第 4、6 条、14.5 第 8 项）；七条前端同源检查同时生效：**分包内出现切换家庭的调用即失败**（家庭切换只归 shell，17.2）、**分包内硬编码面清单即失败**（挂载集合只能来自 `faces[]`，17.8）、**分包内出现 `/api/homeos/search` 之外的搜索调用即失败**（17.6）、**分包内自造时间窗状态即失败**（`period` 必须来自 shell 级 store 且四处同源，4.5.3、18.3#9，且只接受月/季/年三档编码，⑬）、**分包内出现第二处面入口或自建面切换器即失败**（面入口唯一在首页矩阵，⑫）、**分包内出现硬编码色值即失败**（颜色只能引用 shell 的主题令牌，17.9）、**分包内自建未读计数或消息入口即失败**（未读只归 shell 的一份 store，17.1）；命中即失败（对应 22.2 第 2-5、8、9 条）。
5. **契约门禁**：七服务 OpenAPI 与事件目录（10.1、10.2）纳入版本控制，CI 对二者做向后兼容检查——删除字段、改类型、改必填、改 subject 命名一律要求升 version，未升即失败；发布的 event 若不在事件目录内亦失败（14.5 第 6 项）。
