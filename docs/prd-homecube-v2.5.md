## 一、产品概述

### 1.1 产品背景

家庭日常生活涉及钱、物、吃、行、人、成长六大核心场景，但现有工具高度碎片化：记账用记账 App，购物用清单 App，菜谱用菜谱 App，提醒用日历 App，家庭成员信息分散在微信、备忘录、相册中。家庭缺少一个统一入口，也缺少面与面之间的自动流转。

家立方 HomeCube 以"一个家，六个面"为核心理念，把家庭生活管理拆成六个完整业务系统，每面独立完整，面间通过底层能力拉通，形成家庭生活闭环。

### 1.2 产品定位

- **一句话定位：** 全家生活一站式管理 App。
- **品牌 Slogan：** 全家生活，立体管理。
- **六面一句话：** 钱有账，物有库，吃有谱，行有程，人有录，长有迹。
- **产品形态 [v2.5]（依 P1）：** iOS、Android 为主形态；H5 随技术栈天然具备并作为 Web 的过渡形态，**一期不做桌面级 Web 客户端**；平板与折叠屏走响应式兜底；智能家居接入属 Wave 5 远景，不在本版承诺范围。
- **目标用户：** 有家庭生活管理需求的个人与家庭，覆盖无娃家庭、有娃家庭、有老人家庭、养宠家庭。
- **单人可用原则 [v2.5 新增]（补 B20）：** 六面在**无家庭（单人）状态下必须完整可用**，加入家庭只是把数据从个人域提升到家庭域并开启协作。理由：家庭协作类工具的真实失败模式是"一人记录，全家不用"，冷启动必须由单人独立价值支撑。每一面的 Wave 1 交付都必须包含"一个人的完整闭环"。

### 1.3 设计原则

1. **每面独立完整**：每一面是一个完整业务系统，内部高内聚，外部低耦合。
2. **交互因面而异**：不追求六面交互一致。财务偏数据报表，采购偏清单勾选，饮食偏图片卡片，出行偏时间线地图，家人偏档案标签，成长偏记录打卡。 **[v2.5]** 一级导航例外，全 App 统一（见 P5 与十七章）。
3. **底层拉通**：时间、日历、提醒、待办、人员、权限、通知、同步、动态、搜索、AI 归类，全部下沉为底层基础能力。
4. **面间联动**：通过底层事件总线与规则引擎，不直接耦合。
5. **去 MVP 化**：不以最小可用为目标，每面按完整业务域分波次交付。 **[v2.5]** 边界澄清：去 MVP 指**不裁剪单个业务域的功能完整度**，不表示「一个 Wave 内六面同时全量交付」；跨面联动能力（规则引擎）本身按 Wave 3 交付，属分期而非砍功能。
6. **Agent 驱动**：需求、设计、开发、测试、部署、文档、复盘由 Agent 协作推进，人类负责目标、优先级、验收与伦理。

### 1.4 名词定义

| 名词 | 定义 |
|---|---|
| 面 | 六大业务域之一，如财务面、采购面 |
| 系统 | 一个面即一个完整系统，如财务系统 |
| 底层 | 六面共用的基础系统 HomeOS |
| 事件总线 | 系统间联动的基础设施 |
| 规则引擎 | 系统间自动流转的配置中心 **[v2.5]** 与总线分离：总线是 Wave 0 底座能力，规则引擎是 Wave 3 产品能力 |
| Wave | 迭代波次，按依赖关系分波推进 |
| Agent | 参与研发全流程的智能体 |
| **系统 code [v2.5 新增]** | 七系统的英文标识，用于事件命名与接口前缀：`homeos` / `finance` / `purchase` / `diet` / `trip` / `kin` / `growth`（见 16.1，解决 B19 中 `family` 与 HomeOS `Family` 实体同名冲突） |

## 二、系统总览

### 2.1 系统分层

家立方由 **7 个系统**组成：

| 层级 | 系统 | code | 定位 | **[v2.5.1] 建设方式（依 D5）** |
|---|---|---|---|---|
| 底层 | 家庭操作系统 HomeOS | `homeos` | 六面共用的基础系统 | **全新建**（身份/家庭/权限/日历到期/通知/同步/总线/搜索全部新写；仅沿用 `family-ledger` 已验证的产品口径与工程约定） |
| 业务层 | 财务系统 | `finance` | 管钱 | **全新建**（`family-ledger` 的账本口径作为需求基线，代码与表结构不复用） |
| 业务层 | 采购系统 | `purchase` | 管物 | 新建 |
| 业务层 | 饮食系统 | `diet` | 管吃 | 新建 |
| 业务层 | 出行系统 | `trip` | 管行 | 新建 |
| 业务层 | 家人系统 | `kin` | 管人 | 新建 |
| 业务层 | 成长系统 | `growth` | 管长 | 新建 |

**[v2.5.1]** 七个系统同仓分域（monorepo + 模块化单体），表名按 16.1 的 code 加域前缀，路由按 `/api/{system}/*` 挂载；实现层约束见 22.2。`family-ledger` 不在本表任何一格里——它是**平行运行的另一款产品**，HomeCube 只从它取运维资产与经验（14.3）。

一句话：

> **一个底层系统 + 六个业务系统。**
> **底层管连接，六面管生活。**

### 2.3 系统设计原则

1. **一面一系统**：每个面是一个完整系统，内部高内聚，外部低耦合。
2. **系统有边界**：每个系统明确"做什么、不做什么"。
3. **数据有归属 [v2.5]（依 D3，解决 B5/B6/B7/B10）**：每个数据对象**有且只有一个归属系统**，归属系统是唯一可写方；其他系统通过只读接口或事件订阅消费，**不得建立字段同构的第二套实体**。全量清单见十六章「数据归属权威表」。
4. **能力不重复**：时间、权限、通知、同步等能力只在底层实现。 **[v2.5]** 补充：到期型对象（有 `due_at`/`schedule`/`expire_at`/`trigger_at` 语义的）必须在 HomeOS 注册可被到期中心与日历聚合，注册契约见 16.4（解决 B8）。
5. **交互可异构**：每个系统按自己的业务逻辑设计交互，不强制统一。 **[v2.5]** 一级导航除外（P5）。
6. **联动靠事件**：系统之间不直接调用，通过底层事件总线通信。
7. **系统可独立 [v2.5]（解决 B2，措辞收敛）**：原文"每个业务系统可独立运行、独立交付、独立验证"不成立——业务面依赖 HomeOS 的权限、提醒与同步，无法脱离底座运行。收敛为：**每个业务系统可独立交付、可独立验收、可作为独立进程/独立模块演进，但运行期依赖 HomeOS 底座**。"可独立成 App"只在 Wave 5 远景下成立，本版不作为设计约束。

### 2.4 关键场景串联 [v2.5 新增]（补 B20：原文只有功能清单，无用户故事）

PRD 的验收以功能域为单位，但交付判定必须回到场景。以下为六条**贯穿链路验收场景**，每个 Wave 结束时逐条走查（对应 18.6 场景验收）：

| 场景 | 链路 | 涉及面 |
|---|---|---|
| S1 周末吃什么 | 家人面看忌口 → 饮食面点菜投票 → 生成周菜单 → 菜单生成采购清单 → 采购完成 → 库存入库 → 费用进财务 | 家人→饮食→采购→财务 |
| S2 一次旅行 | 出行面建行程 → 旅行预算与行李清单 → 采购面出游物资 → 行程结束费用归集进财务（标记项目=旅行账本） | 出行→采购→财务 |
| S3 孩子兴趣班 | 成长面排课程 → 课程进 HomeOS 日历 + 上课提醒 → 费用归集财务 → 接送排班到出行面 | 成长→HomeOS→出行→财务 |
| S4 老人生日 | 家人面纪念日提前 7 天 → 礼物心愿转采购清单 → 采购完成费用进财务 → 生日当天提醒全家 | 家人→采购→财务→HomeOS |

## 三、底层系统：家庭操作系统 HomeOS

### 3.1 系统定位

HomeOS 是六面共用的基础系统，负责**连接、协调、支撑**，不直接面向家庭业务。它相当于家庭生活的"操作系统"，六面是运行其上的"原生应用"。

### 3.2 系统边界

**做：**
- 家庭、成员、角色、权限
- 时间、日历、提醒、待办、周期任务
- 通知、消息、动态、协作
- 数据同步、备份、加密、导出
- 全局搜索、语音、拍照、AI 归类
- 事件总线、规则引擎 **[v2.5]** 拆分口径：**Wave 0 交付事件总线骨架**（事件定义/发布/订阅/日志/幂等/重试/死信/版本），**Wave 3 交付规则引擎**（规则配置/优先级/模拟测试）。原 B1 冲突按此消解。
- 设置、主题、账号、安全

**不做：**
- 不做记账、清单、菜谱、行程、档案、成长记录等业务
- 不存储业务数据，只做索引与引用
- 不定义业务规则，只提供规则执行能力

**[v2.5.1] 边界补充（依 D5，取代原"依 D1 从 family-ledger 上提"口径）**：HomeOS 的账号体系、家庭体系、权限模型、离线同步**全部新写**。不复用的技术依据（代码层复核，见 14.2）：它的 `internal/model` 是单包平铺（身份域与财务域同包、无领域分层、无 service 层，展示字段用 `gorm:"-"` 塞在 `Entry` 结构体里由 handler 拼装）、路由扁平无系统前缀、JWT claims 只有 `UserID`（无 family_id / role / permission，权限靠各 handler 的裸 SQL `family_id = ?` 判定）、隐含"一人一个当前家庭"、无 `version` 字段（乐观锁缺失）。这五条与 HomeCube 的"七系统分域 + 多家庭切换 + 三维权限 + 到期中心"是结构性冲突，"上提改造"的实际工作量与风险高于新写。可从它继承的是**口径与运维资产**（14.3）。

### 3.3 系统职责

| 职责 | 说明 | **[v2.5.1] 建设范围（依 D5，全表新建；括号为可参考口径）** |
|---|---|---|

| 时间与提醒 | 所有系统的时间触发统一由底层处理 | **全新建**（无日历/提醒/待办/到期中心，既无代码也无口径可参考）。 |

### 3.4 详细需求

#### 3.4.1 家庭核心

- 创建家庭、加入家庭、切换家庭、解散家庭
- 邀请成员：链接、二维码、邀请码、通讯录
- 成员管理：添加、编辑、移除、转让管理员
- 角色：管理员、成人成员、儿童/老人、访客
- 权限：模块级、数据级、操作级
- 隐私：字段级可见性、财务隐私、健康隐私、儿童保护

**[v2.5] 细化与冲突消解：**

- **切换家庭**：**[v2.5.1]** 多家庭是底座的一等设计，不是后补开关。`family-ledger` 的实现是"一个用户当前一个有效家庭"（可属多家庭但产品限制切换），HomeCube 从数据模型阶段就定义为：一个账号 ≤5 个家庭，切换后重建上下文缓存（权限、币种、时区、投影表全部按 `family_id` 重新装载），同账号跨家庭的数据不合并。JWT claims 必须携带 `family_id` 与角色快照，服务端每请求校验（不允许"裸 SQL 现场判定"）。
- **儿童/老人成员** **[依 P4]**：**允许无账号成员**（`Member.user_id` 可为空），由监护人代管，代管人写入时携带 `on_behalf_of`；无账号成员不可登录、不出现在邀请列表。这是家人面与成长面能建模"被记录者"的前提。
- **权限三级维度**定义与默认矩阵见 **十五章**。
- **解散家庭**：需管理员 + 二次确认；数据保留 30 天冷存后可导出，逾期物理删除（口径见 21.4）。

#### 3.4.2 时间系统

- 日历：家庭共享、个人、多视图（日/周/月/年）
- 提醒：单次、周期、位置、到期
- 待办：创建、分配、完成、归档、子任务
- 周期任务：每天/周/月/年、自定义、跳过、顺延
- 到期中心：聚合六面所有到期事项
- 通知：推送、站内信、@、免打扰、分组

**[v2.5] 关键补充（解决 B8）**：到期中心不是"轮询六面私有库"，而是六面按 **16.4 注册契约**把到期型对象登记为 HomeOS 的 `CalendarEvent` / `Todo` / `Reminder`，HomeOS 是唯一聚合与触发方。六面**不得自建推送链路**。字段映射、删除与完成回写语义见 16.4。

**[v2.5] 位置提醒限制**：iOS/Android 后台定位权限受限，位置提醒（如"到超市提醒"）默认降级为地理围栏 + 失败即回落到时间提醒，需在设置里明示不保证触达（原 3.8「到达率 ≥99.9%」不含位置类提醒，见 18.2）。

#### 3.4.3 协作系统

- 动态流：六面所有变更、完成记录
- 留言：家庭留言板、模块内评论
- 投票：单选、多选、匿名、截止时间
- @提醒、已读状态、家庭公告

**[v2.5] 补充**：动态流的写入路径**只有事件总线**（业务面不直接写 `Dynamic`），保证 Wave 3 接规则引擎时动态流不需要改造；投票（饮食面点菜、家人面照护轮值）由 HomeOS 提供投票对象，业务面引用 `vote_id`，不自建投票表（依 D3）。

#### 3.4.4 数据系统

- 多端同步：实时、离线、冲突解决（LWW + 业务合并）
- 备份恢复：自动每日、手动、版本回滚
- 加密：传输 TLS 1.3、存储 AES-256、敏感端到端
- 导出：Excel、PDF、CSV、图片
- 迁移：导入、导出、跨设备

**[v2.5] 冲突解决口径（解决 B18：原文只写 LWW + 业务合并，未定义走哪种）**：

| 对象类别 | 策略 | 说明 |
|---|---|---|
| 财务流水、账单、借贷 | **服务端版本号乐观锁 + 拒绝后到** | 金额型数据不允许静默覆盖；客户端冲突需重拉后重试 |
| 清单条目、库存数量 | **字段级 LWW + 数量走增量合并** | 数量用 `delta` 而非绝对值合并（避免两人同时出库互相覆盖） |
| 档案、偏好、菜谱正文 | 字段级 LWW | 文本型可接受后到覆盖 |
| 打卡、完成状态 | **幂等 + 只进不退** | 状态机单向（`done` 不可被旧 `pending` 覆盖） |

**[v2.5.1]** `family-ledger` 的离线冲突策略是「FIFO + 服务端时间戳决胜」，属上表第二类的退化版，**HomeCube 不沿用**：新底座在写路径一开始就落 `version` 字段与乐观锁（对象级版本 + 冲突返回 409 及双版本 payload），列入 Wave 0（14.4 第 5 项）。业务对象无 `version` 列不得进 Wave 1。

**[v2.5] 备份口径**：每日全备 + binlog/WAL 连续归档，**RPO ≤ 15 分钟**（财务数据不接受"最多丢 24 小时"），RTO ≤ 30 分钟。详见 21.3。

**[v2.5] 加密与搜索的互斥处理（解决 B15）**：端到端加密与"服务端跨六面全局搜索"不能同时成立于同一字段。本版按**对象级分级**处理，见 **二十章数据分级表**：L1（服务端加密 + 可索引）、L2（服务端字段加密 + 密文/本地索引）、L3（端到端，不参与服务端搜索，仅本地可搜）。

#### 3.4.5 智能系统

- 全局搜索：跨六面、自然语言
- 语音输入：记账、添加、提醒
- 拍照识别：OCR 小票、条码、菜谱、证件
- AI 归类：内容识别 → 归入对应系统
- 智能建议：基于家庭数据的主动建议
- 产品内 Agent：家庭助手、问答、主动提醒

**[v2.5.1] 波次切分（依修订后的 P7，解决 B3）**：Wave 0 **不含任何识别类 AI**，只做关键词全局搜索；**录入侧**（语音转文本、OCR 小票、条码识别、拍照建菜谱）随其宿主功能域在 **Wave 1** 交付，且必须与**降级手输链路**同批次（服务不可用时可纯手输，不阻塞记账主流程）；Wave 4 做**理解与预测侧**（AI 归类、补货预测、菜谱推荐、营养分析、成长报告、产品内 Agent）。11.1 原文"AI 归类先建成底座"据此修正。

**[v2.5.1] 外部依赖**：以上能力全部依赖第三方识别/模型服务，成本、供应商与降级见 **十九章**；19.3 规定"供应商未定的能力不得进排期"，这也是录入侧 AI 移出 Wave 0 的直接原因。依 D5 后本节**没有任何一项 AI 能力可以从既有系统白拿**——`family-ledger` 的"明确不做"清单里就有 OCR、语音、多币种、AI 消费分析，HomeCube 侧它们全是新建 + 新签供应商。

#### 3.4.6 事件系统 **[Wave 0 交付，依 P6]**

- 事件定义、发布、订阅、日志
- 幂等、重试、死信、版本管理

**[v2.5] 补充**：总线为**同进程内投递 + 持久化日志**起步（单体或模块化单体阶段不引入 Kafka 等外部 MQ，避免 Wave 0 运维面扩大）；跨服务拆分为 Wave 5 议题。事件必须落库可回放，回放不产生重复业务对象（幂等键见 10.4 + P2 忽略表）。

#### 3.4.7 规则系统 **[Wave 3 交付，依 P6]**

- 规则配置、默认规则、自定义规则
- 优先级、冲突处理、模拟测试、执行日志

**[v2.5] 补充**：默认规则即 10.3 的十一条联动，Wave 3 出厂即启用且**可关闭**（每家庭粒度）；自定义规则只允许"事件 → 创建 HomeOS 待办 / 通知 / 只读投影更新"三类动作，**不允许业务面注入任意代码执行**（安全边界）。

#### 3.4.8 设置系统

- 主题、通知、账号、安全、帮助、关于
- 多语言、时区、货币、日期格式

### 3.5 交互设计

- **首页**：家庭切换器、动态流、快捷入口、到期中心
- **导航**：底部 Tab（首页、动态、+、消息、我的）
- **全局 +**：语音、拍照、文字、模板
- **设置**：分组列表、搜索、帮助

- 事件幂等、可重试、可追溯
- 权限变更实时生效
- 敏感数据加密存储
- 崩溃率 ≤ 0.1%

**[v2.5]** 以上 8 条已补「度量定义 + 分母 + 采样方法 + 判定方式」，见 **18.2**（其中「到达率 99.9%」修正为**不含位置类提醒与服务端无法保证的 APNs/厂商通道回执**，改测"服务端触发成功率 + 客户端展示率"两个可测口径；「权限变更实时生效」定义为 ≤1 秒内新请求生效）。

**[v2.5.1] 多账本口径（解决 A1 产品定义冲突，依 D5 重新定调）**：`family-ledger` 的产品口径是「一个家庭 = 一个账本，账本切换器不在范围」。HomeCube **采纳同一结论**——不是因为它有代码要兼容（依 D6 无数据迁移），而是这条口径在 A1 上是对的：**隔离靠权限与字段可见性实现，不靠账本实体实现**。因此本版把 `Ledger` 定义为**账本视图/归集分组**（按 `project` 标签 + 成员范围过滤出的报表单元），而**不是**独立的数据隔离域与权限边界；`Ledger` 表只存分组定义与成员范围。收益：旅行/装修/孩子账本的需求用报表与标签即可满足，且不引入跨账本权限爆炸。真正的隔离需求（R1 私密密账本）由**字段级可见性**（15.4）实现。

- 多人共享、实时同步、认领

**[v2.5]** 「认领」实现为 HomeOS `Todo` 分配给成员（16.4），清单面读投影；「到超市提醒」受位置提醒降级口径约束（3.4.2）；「分类」为物品分类，不等同费用分类，但入库转支出时需映射到 `finance.Category`（P3，映射表由用户在首次使用时确认，之后自动）。

#### 5.5.2 库存

- 物品档案：名称、分类、数量、单位、位置
- 位置：冰箱、厨房、卫生间、储藏室、药箱
- 入库、出库、调整、批次
- 阈值、低库存提醒
- 保质期、临期提醒
- 扫码、拍照录入

**[v2.5]** 本域是**食材库存的唯一归属**：饮食面「冰箱临期」「剩余食材推荐」全部查询本域的 `InventoryItem` + `Batch`，不得写入。临期与低库存的提醒对象注册到 HomeOS 到期中心（16.4），本面不自建定时器。「扫码」依赖条码库（19.2），识别失败必须可手输。

**[v2.5] 盘点口径**：为解决 5.9「库存数量与实际一致（盘点误差 ≤2%）」的可测性，新增 `Stocktake`（id、family_id、location、started_at、items、diff、done_at）对象，误差 = 盘点差异条目数 / 盘点条目总数，按位置粒度做，不做全仓盘点（家庭场景不现实）。

#### 5.5.3 补货
- 消耗记录、消耗速度
- 自动补货建议、低库存自动加购
- 临期优先使用

**[v2.5]** 消耗记录 = 出库事件累计；「自动加购」在 Wave 1 只做**阈值触发**（低于阈值即生成清单条目，规则固定、无学习），Wave 4 才引入消耗速度预测。5.9 的"准确率 ≥98%"因此只对阈值触发口径度量（18.4 已改写）。

#### 5.5.4 采购记录
- 历史、价格、商家、统计、月度支出

**[v2.5]** 采购完成 → 生成财务支出的事件链路（10.3）适用 **P2 生成型单据语义**：财务侧可改可删，删后不重建。

#### 5.5.5 比价
- 优惠券、价格跟踪、促销提醒

**[v2.5]（依 R5）** 范围收敛为：人工录入优惠券（名称/面额/有效期/使用状态）、同一物品的历史价格曲线、促销提醒仅来自用户自建周期提醒。**不做**电商实时价格抓取（无合规数据源、单机做不到、成本不可控）。

#### 5.5.6 协作

### 5.6 交互设计

**[v2.5] 命名前缀改用 16.1 系统 code（解决 B19）**：`meal.` → `diet.`；`family.` → `kin.`（避免与 HomeOS `Family` 实体同名）。本版事件清单：

- `diet.menu.created`
- `purchase.order.completed`
- `finance.transaction.created` / `finance.budget.exceeded`
- `kin.birthday.upcoming` / `kin.preference.updated`
- `trip.maintenance.due` / `trip.completed`
- `growth.course.scheduled` / `growth.course.fee`

**[v2.5] 字段补充**（原结构无法实现幂等与追溯）：

### 10.3 关键联动事件

| 事件 | 源 | 目标 | 动作 | **[v2.5] 说明** |
|---|---|---|---|---|
| `diet.menu.created` | 饮食 | 采购 | 生成清单 | 条目携带 `recipe_id`；缺料计算读库存快照，不锁库存 |

| `kin.birthday.upcoming` | 家人 | HomeOS | 提醒 | 走 16.4 注册契约，非直接推送 |

### 10.4 事件治理

- 幂等键：`event_id + business_id` **[v2.5] 修正为** `event_type + business_id`（`event_id` 每次发布都不同，用它做幂等键等于没有幂等；`causation_id` 用于链路追溯）
- 重试：指数退避，最大 3 次
- 死信：失败进死信队列，人工处理 **[v2.5] 载体为 `DeadLetter` 实体 + 管理台入口，重放接口见 3.7**
- 版本：语义化，向后兼容
- 日志：全量记录，可追溯 **[v2.5] 保留期见 21.4**
- **[v2.5 新增] 忽略表**：`EventIgnore(business_id, event_type, ignored_at, operator)` —— 实现 P2"人工删除后不重建"
- **[v2.5 新增] 投递保证**：至少一次（at-least-once）+ 消费端幂等；不承诺恰好一次

## 十一、迭代规划与 Agent 推进机制

### 11.1 去 MVP 化原则

- **不设 MVP**：不以"最小可用"为目标，不以残缺功能上线。
- **每面完整闭环**：每一面都按完整业务域设计。
- **分波次交付**：不是砍功能，而是按依赖关系分 Wave 推进。
- **底层先行**：家庭核心、时间、权限、通知、同步、搜索、AI 归类先建成底座。 **[v2.5.1]（依 D5 + 修订后 P7）** → "家庭核心、时间、权限、通知、同步、关键词搜索先建成底座（Wave 0）；录入侧 AI（OCR/语音/条码）随宿主功能域在 Wave 1 交付；AI 归类与预测属 Wave 4。"
- **六面并行**：业务面可并行迭代，底层能力统一提供。 **[v2.5]（依 D2 保留）** 并行成立的前提见 11.7 人力与验收瓶颈。
- **联动后置**：先让每面独立可用，再通过事件总线与规则引擎拉通。 **[v2.5]（依 P6）** → "总线骨架随底座交付，规则引擎与联动业务后置至 Wave 3。"
- **Agent 全流程参与**：需求、设计、开发、测试、部署、文档、复盘均由 Agent 协作推进，人类负责目标、优先级、验收与伦理。

### 11.2 迭代分层

### 11.6 Agent 工作流

1. **人类设定目标**：确定 Wave 目标、优先级、验收标准。
2. **Orchestrator 拆解**：生成任务卡、依赖图、排期。
3. **Product Agent 细化**：输出用户故事、验收标准。
4. **Architect Agent 设计**：输出架构、数据模型、API。
5. **UX/UI Agent 原型**：输出交互稿、视觉稿、组件。
6. **Frontend / Backend Agent 开发**：并行编码，提交 CI。
7. **Test Agent 测试**：单元、集成、回归、自动化。
8. **Security Agent 审计**：权限、隐私、加密、漏洞扫描。
9. **DevOps Agent 部署**：灰度、监控、回滚。
10. **人类验收**：关键节点审批，确认业务价值。
11. **Docs Agent 更新**：文档、帮助、更新日志。
12. **Review Agent 复盘**：输出迭代报告，进入下一波。

**[v2.5] 两处口径补齐（解决 B12/B13 的验收粒度缺口）：**

- **第 10 步"关键节点"具体化**：人类审批发生在三个粒度——① 任务卡进入「待审核」列（每卡，复用 Jarvis Workbench 的强制人审）② 每 Sprint 末的功能切片验收（按面）③ 每个 Wave 末的场景链路验收（2.4 S1-S6）。**Wave 末验收未过不得进入下一 Wave。**
- **步骤 3-5 允许并行**：原文十二步近似串行瀑布，与"六面并行"（11.7）冲突。改为：同一面内串行（3→4→5→6），**不同面之间并行**，且 Wave 0 期间六面不参与。

### 11.7 迭代节奏与看板

- **Sprint 周期**：2 周。
- **Wave 周期**：8-24 周，视范围而定。 **[v2.5.1]** 按 11.3 实排：Wave 0 = 8-10 周，Wave 1 = 32-38 周，Wave 2 = 20-28 周，Wave 3 = 14-18 周，Wave 4 = 14-20 周。

- **看板列**：需求池 → 已拆解 → 设计中 → 开发中 → 测试中 → 待验收 → 已发布 → 复盘。 **[v2.5]** 与 Jarvis Workbench 六列（需求池→待执行→执行中→待审核→已完成/异常）的映射见 22.3，不新起一套看板。

- **版本节奏**：每 4 个 Sprint 发布一个大版本。

### 11.9 风险与治理

- **Agent 幻觉**：关键需求、架构、安全节点必须人类审批。
- **代码质量**：CI 强制检查，Test Agent 与 Security Agent 双重审计。
- **隐私安全**：家庭数据分级、加密、权限最小化。
- **多 Agent 冲突**：Orchestrator 统一调度，冲突升级人类决策。
- **架构漂移**：Architect Agent 定期评审，版本冻结。
- **人类监督**：产品负责人、技术负责人、家庭用户代表参与验收。
- **回滚机制**：灰度发布，一键回滚，数据备份。

**[v2.5.1] 新增四条（来自本轮评审与代码层复核的真实风险；原"生产迁移风险"随 D1 作废移除）**

- **从零重写的覆盖度风险（高）**：D5 后七个系统全部新写，不再有"底座上提"这条捷径，也没有生产数据兼容包袱。风险从"改造带流量的系统"变成"**新写的第一版比现网跑了两年多的版本弱**"——尤其财务面（`family-ledger` 已验证的功能水位即 Wave 1 的最低线）。处置：Wave 1 验收按 18.3 逐域对照清单走查，不允许以"新系统先简版"降级；每域须同时给出与 `family-ledger` 对应能力的差异说明。
- **双产品并存与用户混淆风险（中）**：依 D6，`family-ledger` 与 HomeCube 长期并存、数据不打通。风险是同一个人/家庭同时看到两款"家庭账本"。处置：① 二者产品名、图标、域名、包名必须可区分，HomeCube 不在文案中出现"账本升级/迁移"字样；② `family-ledger` 冻结新功能，只接受安全修复（22.4）；③ 若未来要合并，属 Wave 5 议题，本版不承诺。
- **运维资产移植不落地风险（中）**：D5 只继承部署/CI/热更新，若不显式验收，新仓库会在 Wave 0 结束时仍没有可用的离线部署与回滚能力。处置：Wave 0 门禁含"干净机器一条命令拉起 ≤30 分钟"（11.3、14.3）。
- **验收压缩风险（高）**：v2.4 排期失真的根因是"用周期当承诺、用压缩代替拆解"。本版把人类验收带宽写成硬约束（11.7），若需提速，**只允许减少并行面数，不允许压缩单面完整度**（守 1.3 第 5 条）。

### 14.2 D1 为何作废：代码层复核记录（2026-09-28）

D1 原结论建立在 README 与实现状态文档层面。对源码复核后，以下七条使其不成立：

| # | 复核点 | 代码事实 | 与 HomeCube 要求的冲突 |
|---|---|---|---|
| 1 | 分层与包结构 | `server/internal/model/model.go` 一个包内平铺 10 个模型：身份域（User/Family/Membership/FamilyInvite/RefreshToken/SmsCode）与财务域（Account/Category/Entry/EntryAttachment/Budget/RecurringEntry）同包；无 service 层，handler 直接拼 SQL；`Entry` 结构体挂 7 个 `gorm:"-"` 展示字段由 handler 逐条拼装（entry.go 552 行、auth.go 564、stats.go 592） | 十六章要求"一面一系统、数据唯一归属"；单包平铺 + 胖 handler 无法划出七个域，也无法阻止跨域直连库 |

### 14.6 存量数据与双系统并存（依 D6）

- **不迁移**：`family-ledger` 生产库的家庭、成员、账户、分类、流水**不进入** HomeCube，也不提供一次性迁移脚本或导入器。HomeCube 从空库开始，首个版本的数据由用户自行录入。
- 理由：① 域模型不同（`entries` 无 `ledger_id`/`version`/`generated_by`，`Membership.Role` 无角色表支撑），迁移动的是语义而不是行；② 迁移正确性验证成本高于让用户重录一次一年数据的成本；③ D1 作废后两者不再有"同源主干"关系，合并反而制造耦合。
- **并存策略**：`family-ledger` 冻结新功能，只接受安全修复与合规必修（22.4）；两套系统不共享域名、包名、账号体系与数据库，文案上不得出现"升级/迁移到 HomeCube"的引导，避免用户误认为同一产品（11.9）。
- **退役与本版主不承诺**：任一系统的退役、二者数据打通、单点登录，均属 Wave 5 之后的议题，本版不设计、不排期。
- 若家庭确需带走历史账目：使用 `family-ledger` **自身**的导出能力（其现网导出缺陷属该项目内部待修，不构成 HomeCube 的依赖或门禁）。

## 十五、权限与角色矩阵 **[v2.5 新增]**（处置 B14，含 R1-R4 默认值）

### 15.1 角色定义

| 角色 | 可登录 | 说明 | 关键限制 |
|---|---|---|---|
| 管理员（owner） | 是 | 家庭创建者或被转让者，唯一可转让/解散 | 不能移除自己（**[v2.5.1]** 沿用 14.3 继承的产品口径，避免误删唯一管理员） |
| 成人成员（member） | 是 | 默认角色，可写业务数据 | 不能管理成员与邀请（邀请仅 owner，**同一口径继承**） |
| 儿童/老人（ward） | **可无账号** | 被记录对象；有账号时（如青少年）仅有限写权限 | 由 `guardian_id` 指向监护人，代管写入带 `on_behalf_of`（依 P4） |
| 访客（guest） | 是（临时凭证） | 限时只读，用于保姆/亲属临时协作 | 默认有效期 30 天，可撤销；不可导出 |
| 已退出成员 | — | 历史作者标记 | 见 R4：数据留家庭，作者显示"已退出成员" |

### 15.2 权限三维模型

`Permission(scope, resource, action, condition)`：

- **scope = module**：某系统整体可见/可用开关（家庭可按面关闭，如不用出行面）。
- **scope = data**：数据行范围（自己的 / 本账本的 / 全家庭的 / 指定成员的）。
- **scope = action**：`read` / `create` / `update` / `delete` / `export` / `invite` / `admin`。
- **condition**：时间窗（访客有效期）、字段（L3 字段需二次确认）、对象归属（`author == me`）。

**判定顺序**：显式拒绝 > 角色默认矩阵 > 家庭级覆盖 > 对象级 ACL。缓存失效见 15.6。

### 15.3 默认权限矩阵（角色 × 系统 × 动作）

图例：**A**=全部（读写删导）、**M**=仅自己的/本人相关、**R**=只读、**—**=无权限、**O**=仅管理员

| 系统 | 管理员 | 成人成员 | 儿童（有账号） | 儿童/老人（无账号） | 访客 |
|---|---|---|---|---|---|
| HomeOS（成员/权限/设置） | O | R（成员列表） | — | — | — |
| 财务 | A | **M 写 + R 全家庭读**；导出需管理员或本账本授权 | — | 被记录（无写） | — |
| 采购 | A | A（清单与库存为家庭共有物） | M（可勾选完成，不可删） | — | R + 勾选 |
| 饮食 | A | A（菜谱/菜单）；记录仅本人 | R + 被点菜 | 被记录（忌口/饮食记录由代管） | R |
| 出行 | A | M 写 + R 全家庭行程 | R（自己的行程） | 被记录（接送对象） | R |
| 家人 | A（档案） | M 本人档案；R 他人档案的**非隐私字段** | — | 档案由监护人写 | R（白名单字段） |
| 成长 | A | M 本人；R 自己监护对象的 | 记录自己 | 记录由监护人写 | — |

**财务隐私默认（R1，需复核）**：**家庭流水全员可见可编辑自己的、他人流水可看不可改**；"私密密账本"为管理员可开启的可选特性，开启后该账本仅作者与管理员可读，且**不参与 AA 分摊与跨面归集**（否则 4.9 零误差与隐私互斥）。

**AA 分账适用面（R2，需复核）**：仅标记为「共享」的账本参与分摊，日常账本不摊。

**儿童能否记账（R3，需复核）**：默认不能（无写权限，仅被记录）；青少年账号可由管理员逐面开放。

### 15.4 字段级可见性

| 字段类别 | 默认可见范围 | 备注 |
|---|---|---|
| 姓名、头像、关系 | 全家 | — |
| 生日 | 全家（纪念日功能依赖） | 农历/公历同 |
| 血型、过敏史、紧急联系人 | 全家（急救场景白名单） | L3 分级；锁定屏展示需家庭开关（8.5.6） |
| 尺码、礼物偏好、心愿、颜色品牌 | **仅本人与管理员** | 惊喜场景反直觉，默认隐藏 |
| 财务金额（他人流水） | 全家可读，作者唯一可改 | 依 R1 |
| 成长照片、身体数据 | 全家（监护人可设"仅家庭可见"，禁对外分享导出） | L3 + 儿童保护（20.3） |

### 15.5 数据归属与成员退出（R4）

成员退出家庭：其创建的流水/清单/记录**留在家庭**，作者显示"已退出成员"；**其个人偏好与私密账本随退出删除**（导出请求需在退出前完成）；监护人代管数据归属被记录的成员而非代管人。

### 15.6 权限生效与缓存

- 服务端每次请求校验 `family_id` 隔离 + 权限判定。 **[v2.5.1]** 依 22.2 第 5 条：两者都在**鉴权中间件**统一完成（token 携带 `family_id` 与角色快照），不允许在业务 handler 内用裸 SQL 现场判定家庭归属——该形态是 `family-ledger` 的现状，列为 HomeCube 禁止复刻项（14.3）。
- 客户端权限缓存 TTL 60 秒，且收到 `homeos.permission.updated` 事件即失效 → 满足 3.8「权限变更 ≤1 秒生效」的口径是**服务端立即、客户端下一次请求**。
- **越权尝试全部落审计日志**（21.5），连续 5 次触发通知管理员。

- 全局搜索从首页与「我的」进入，跨七系统；结果按面分组，点击直达对象（深链格式 `homecube://{system}/{entity}/{id}`）。

### 17.7 导航约束（防架构漂移）

- 一级导航与六面切换器的组件由 HomeOS 提供，业务面消费（依 2.3 第 4 条「能力不重复」）。
- **4. [v2.5.1 新增，依 D5]** 前端工程按面分 **subPackage**：`pages/homeos`（一级导航 + 六面 shell + 动态 + 消息 + 我的）为主包，六个面各一个分包，分包不得互相引用页面，跨面跳转只走深链（17.6）。这条是六面并行开发的前提——没有分包边界，六面会在主包体积与构建产物上互相拖累（`family-ledger` 的 46 页单包即为此反面案例，14.2 第 6 条）。

## 十八、验收口径表 **[v2.5 新增]**（处置 B13，依 D4）

### 18.1 通用判定规则

- **计数口径**：除特别说明，性能指标一律取 **P95**，样本量 ≥ 100 次，测试环境为**中端 Android 真机 + iPhone 各一台**，网络分别取 Wi-Fi 与 4G 两轮。
- **判定人**：Test Agent 出报告 → 人类按任务卡/切片/Wave 三级验收（11.6）。**任何"零误差/100%"项必须给构造样本，不接受"未发现异常"作为通过理由。**
- **不可测即阻断**：无法定义分母的指标不得写进验收；本版已把全部原 v2.4 验收条目补为可测，剩余模糊项集中在 18.7（Wave 4），标注为"先测基线再定目标"。
- **条数更正**：v2.4 各章验收条目合计为 **51 条**（HomeOS 8 + 六面各 7-8），评审报告初稿写作 47 条，以本版为准。

### 19.2 明确排除的外部数据源（解决"隐性依赖"）

电商商品库与实时价格抓取、促销信息抓取（R5）；航司/铁路票务状态与延误数据；外卖平台订单同步；餐厅点评数据；营养成分权威库（饮食营养为自填参考值，6.5.7）；WHO/国标生长百分位数据（9.2）；银行/支付宝/微信账单自动导入（沿用 14.5）；真实资金划转通道（4.5.7）。

### 19.3 供应商与成本决策的落地要求

Wave 0 开工前由 Architect + DevOps Agent 产出**依赖选型表**（供应商、单价、免费额度、限流、合同与数据出境评估），未定的依赖**不得进入对应功能的排期**。本 PRD 不锁供应商，但锁两条：① 任何付费依赖必须有家庭级用量上限与用量告警；② 任何依赖第三方模型/识别服务的能力，其手工路径必须与自动化路径同批次交付（不允许"先上 AI、后补手输"）。

### 19.4 存储迁移触发条件

满足任一即从单机磁盘迁对象存储：单家庭附件总量 > 20GB；全实例 uploads 目录 > 200GB；图片加载 P95 > 800ms；出现磁盘 IO 导致的写失败。迁移需含历史文件搬迁与 URL 重写，作为独立任务卡而非顺带改造。

### 19.5 埋点字典（Wave 0 交付物）

11.8「用户价值」维度依赖此字典。要求：每个指标给出事件名、触发时机、属性字段、计算式、留存周期；**未在字典中定义的指标不得作为验收依据**。字典与二十章的数据分级表交叉核对：**埋点不得携带 L3 字段内容**（只允许携带"发生了某行为"级事件）。

| 级别 | 定义 | 加密方式 | 服务端可搜索 | 典型数据 |
|---|---|---|---|---|
| **L1 普通** | 家庭协作必需、泄露影响低 | 服务端存储加密（AES-256）+ TLS 1.3 | 是（可建索引） | 清单条目、菜谱正文、行程标题、库存数量 |
| **L2 敏感** | 财务与健康相关，泄露影响中 | 字段级加密，密钥独立管理 | **受限**：密文不落可搜索索引，走本地索引或脱敏字段 | 交易金额与备注、账户余额、借贷对象、体重 |
| **L3 高敏** | 儿童数据、医疗急救、偏好隐私 | 客户端加密后上传，服务端仅存密文与密钥封装 | **否**（服务端不参与搜索，仅本地可搜） | 成长照片与身体数据明细、血型过敏详情、紧急卡、尺码/礼物心愿 |

**[v2.5] 与 12.2「端到端加密」和 3.8「跨六面全局搜索」的冲突消解**：不承诺全量端到端加密，只承诺 **L3 端到端 + L2 服务端字段加密 + L1 全量可搜**。全局搜索默认覆盖 L1+L2（L2 搜脱敏字段），L3 只在本机已解密状态参与本地搜索。这是可实现的口径，替代 v2.4 的自相矛盾表述。

### 20.2 分级访问规则

- L3 读取需**设备级解锁 + 会话内二次确认**；深链进入 L3 对象同样确认（17.6）。
- L3 内容**不进入埋点、不进入导出默认集、不进入推送正文**（推送只说"有一条新记录"）。
- 锁定屏紧急卡是 L3 的**唯一受控例外**：需家庭开关显式开启 + 白名单字段（8.5.6、15.4）。
- 导出：L2 可选、L3 默认排除，导出行为本身记审计。

### 20.3 儿童数据与个人健康信息（最高风险，阻断级）

- 成长面儿童照片/身体数据/里程碑（9.5.1）与家人面健康字段（8.5.1）属**儿童个人信息与敏感个人信息**：需**监护人显式同意**（首次建档单独同意弹窗，文案可留档截图）、可撤回、可一键导出与彻底删除。
- 儿童数据默认**不参与 AI 训练与第三方模型调用**；任何 AI 能力若需处理儿童数据，必须单独评审并在此节记录结论（本版：Wave 4 成长报告使用本地聚合数据，不调用外部模型）。
- 分享：成长报告"家庭分享"默认生成**脱敏摘要**，含照片的原图分享需逐次确认。

### 20.4 法规落实清单（替代 v2.4 的"符合隐私法规"一句）

| 法规 | 适用点 | 落实项 | 波次 |
|---|---|---|---|
| 《个人信息保护法》 | 敏感个人信息（健康、金融账户）、单独同意、最小必要 | 分级表（20.1）+ 单独同意流程 + 埋点字典不含 L3 | W1 前完成 |
| 《儿童个人信息网络保护规定》 | 成长面儿童数据 | 监护人同意、专章 20.3、默认不外传 | W1 |
| 《数据安全法》/ 等保实践 | 数据存储与访问审计 | 审计日志（21.5）、密钥管理、权限最小化 | W0 |
| GDPR（仅在服务境外用户时） | 数据可携带、被遗忘 | 导出/删除能力已内建（3.4.4 + 20.3） | W2 视运营地决定 |
| **隐私政策与用户协议** | **[v2.5.1] 不是"继承缺口"，而是 HomeCube 自建项**：`family-ledger` 的教训是「无页面，注册页『服务条款和隐私政策』是不可点文字」，其文档自标为"合规硬门槛"却始终未做 | **Wave 0 必补**：可读的隐私政策/用户协议页面 + 首次登录确认留痕 | **W0 门禁**（14.4 第 9 项、18.2 新增项④） |

### 20.5 安全基线补充

密钥管理（KMS 或本地密钥文件 + 权限隔离）、备份包同样加密、生产环境凭据不入代码库与日志、管理台二次认证、依赖漏洞扫描进 CI。

见 18.2#2 的双口径拆分；系统级不保证送达的通道（APNs/厂商）不计入产品验收分母，改测服务端触发成功率 + 客户端展示率观测值。

## 二十二、技术约束与研发流程载体 **[v2.5 新增，v2.5.1 依 D5 改写]**（依 D5/A2；PRD 不选型，但给约束）

### 22.1 技术栈约束

1. **技术栈沿用同一套，但为新建选型**：服务端 Go + Gin + GORM + PostgreSQL，客户端 uni-app(Vue3) → Android/H5，管理台 Vite + React。 **[v2.5.1] 理由变更**：不再是因为"复用既有代码所以不能换栈"，而是这套栈在 `family-ledger` 上跑通了家庭场景的性能、离线部署与热更新需求，且部署资产（Docker 编排、CI、wgt 发布链）可直接移植——**换栈的收益归零、成本仍在**，故沿用。任何"因为新仓库所以顺手换框架"的提案默认驳回。
2. **偏离需评审**：任何换栈/加中间件（消息队列、缓存、搜索引擎）必须在任务卡标注并由 Architect Agent 评审通过。**Wave 0 明确不引入外部 MQ 与独立搜索集群**（3.4.6 总线走同进程 + 落库；搜索先建 PG 全文/索引，量级到 21.1 上限再评估）。
3. iOS 出包依赖 Apple 开发者账号（19.1，与 `family-ledger` 无关的独立缺口），无账号期间以 H5 + Android 交付。
4. 微信小程序不启用（14.5）。

### 22.2 架构约束

1. **模块化单体优先**：七系统同仓同库分域（表前缀按 16.1 的 code），拆分服务是 Wave 5 议题。
2. **禁止跨域直接 JOIN 写入**（依 16.3），只读接口/投影/引用外键三选一。
3. 迁移文件带系统前缀（16.6），使数据归属在版本层可见。
4. **底座接口冻结**：Wave 0 结束时冻结 HomeOS 对外契约（3.7 + 16.4），六面此后才并行开发（11.7 约束③）。
5. **[v2.5.1 新增] 三条防复刻约束**（针对 14.2 复核发现的既有结构缺陷，新仓库从第一行代码起生效，不接受"先这样以后再改"）：
   - **路由必须分域**：`/api/{system}/*`，不允许出现根路径业务接口；网关层按域注入权限校验。
   - **鉴权必须在中间件**：`family_id`、角色与权限快照随 token 下发并由中间件统一校验；**业务 handler 内禁止出现家庭归属的裸 SQL 判定**（CI 静态检查项，22.5 第 4 道门禁）。
   - **写模型必须有版本**：所有业务实体带 `version`（乐观锁）与 `deleted_at`/`deleted_by`（软删）；展示字段不得挂在实体结构体上由 handler 拼装，一律走 DTO/投影层。

### 22.3 Agent 研发流程载体（复用 Jarvis Workbench）

| PRD 看板列（11.7） | Jarvis Workbench 列 | 说明 |
|---|---|---|
| 需求池 / 已拆解 | 需求池 | Orchestrator 拆解即建卡 |
| 设计中 / 开发中 / 测试中 | 待执行 → 执行中 | Agent 经 MCP `claim_next_task`（带租约）认领 |
| 待验收 | **待审核（强制人工审核）** | 对应 11.6 第 10 步的三个粒度中的每卡粒度 |
| 已发布 / 复盘 | 已完成 / 异常 | 异常列承接阻塞与被打回 |

复用其既有的任务模板、Agent/UI token 分离、审计日志、租约与通知机制；**不自建第二套看板**。局限须知：仅监听 127.0.0.1、单用户本地，属研发工具而非产品组件（14.1）。**[v2.5.1]** D5 后新仓库是它的第一批任务来源，需在 Wave 0 第 1 项里同步建好项目与任务模板。

### 22.4 仓库与双产品关系

**[v2.5.1 依 D5/D6 重写]** HomeCube 与 `family-ledger` 是**两个独立仓库、两个独立产品、两套独立数据库**，不存在主干/分支关系，也不做代码合并：

- HomeCube 新仓库：`~/www/HomeCube`（当前仅有 `docs/`，尚未 `git init`——Wave 0 第 1 项的第一件事是初始化仓库与分域骨架）。
- `family-ledger`：**冻结新功能**，只接受安全修复与合规必修；不迁移代码、不迁移数据、不共享账号体系；其现有部署与 CI 脚本作为**移植蓝本**被复制改写进 HomeCube（14.3）。
- 禁止事项：HomeCube 不得 import / vendor / fork 它的任何源码；不得复用它的表结构与迁移文件；不得在文案中引导用户"升级/迁移"（11.9、14.6）。

### 22.5 CI/CD 与发布门禁

**移植**（依 14.3 运行时资产）：GitHub Actions（lint/test/build）、离线 Docker 包、一条命令部署带回备份与回滚——在 HomeCube 新仓库内**重写同名流水线**，不共享旧仓库的 workflow 文件。**四道新增门禁**：

1. **迁移门禁**：CI 校验迁移文件到最新版本且测试库可全量重放（针对 14.2 第 7 条"代码领先生产 6 个迁移"的教训，新仓库不接受该状态出现）。
2. **归属门禁**：CI 静态检查新建表是否命中 16.2 权威表，出现同构实体即失败（16.6）。
3. **验收门禁**：十八章指标接入自动化测试报告，未达标不得进灰度；发布按家庭白名单灰度，回滚 = 切回原地址 + 恢复备份。
4. **[v2.5.1] 分域与鉴权门禁**：CI 检查路由是否全部落在 `/api/{system}/*`、handler 内是否出现家庭归属裸 SQL、新建业务表是否带 `version`；命中即失败（对应 22.2 第 5 条）。

## A. 与现有资产的冲突（最高优先级，决定整个项目路线）

### A1. 财务面 = 已上线系统的重复建设

`~/www/family-ledger` 是**生产环境运行中**的家庭账本（`https://family-ledger.xuesh.cn`，Go 1.24 + gin + GORM + PostgreSQL 16 + uni-app(H5/Android)，GitHub Actions CI，一键部署带回滚）。已实现并验证过：

记账（支出/收入/转账、快捷记账、软删、幂等写 `client_request_id`、周期记账后台生成）、账户（预置+自定义、余额计算）、二级分类（按家庭预置）、流水筛选与游标分页、统计（概览/多粒度趋势/分类/成员/折线饼图）、预算（月度+分类+固定/周期、超支提醒）、站内通知 API、票据图片附件、CSV 导出、离线队列与重放、wgt 热更新 + APK 兜底、邀请码加入/退出/移除家庭、owner/member 权限与服务端 `family_id` 隔离。

对照 PRD 第四章：4.5.1 记账、4.5.2 预算、4.5.3 报表、4.5.8 账户，以及 4.9 的大部分验收项，**已被覆盖**。真正缺失的是：多账本、AA 分账/结算中心、借贷、储蓄目标、账单（待缴/发票）、多币种。

冲突点：

- **多账本 vs 单账本**：PRD 4.5.1 要求多账本（日常/旅行/装修/孩子/项目），family-ledger 的产品口径是「1 family = 1 ledger，切换器不在范围内」。这是产品定义冲突，不是功能缺口。
- **Family 语义重叠**：HomeOS 的 `Family/Member/Role/Permission`（3.6）与 family-ledger 已实现的 family/member/邀请码/owner-member 是同一套概念。PRD 把它当新建项，等于把已上线且踩过坑的模块重新设计一遍。
- **HomeOS 的三个最难能力已有实现参照**：多端同步（离线队列+重放）、幂等写、权限隔离。PRD 3.4.4 / 3.8 只给了指标值，没有引用既有实现的经验（如 family-ledger 的生产 schema 版本落后：prod v4 vs 代码 v10，这是迁移治理的真实教训）。

评审判断：HomeCube 不应是「从零第七个系统」，而应是「把 family-ledger 的家庭底座抽象上提为 HomeOS + 财务面在其上继续演进 + 其余五面新建」。否则 Wave 0/1 的 20-28 周会大量重做已完成的事，且两套账本并存会造成真实数据分裂。

> **[2026-09-28 复核更正，保留原文]** 上述"评审判断"当日即被推翻。它建立在 README 与 `implementation-status.md` 层面，**没有读源码**。按 `server/internal/model/model.go`、`internal/handler/server.go`、`internal/middleware/token.go`、`web/src/pages.json` 复核后结论相反：既有系统是单域单体（model 单包平铺、路由扁平无系统前缀、JWT claims 只有 `UserID`、隐含一人一家庭、无 `version` 乐观锁、前端四项原生 tabBar + 46 页无分包），与"七系统分域 + 六面 shell + 三维权限 + 多家庭切换"是结构冲突，上提改造等于同时改六件事，风险高于新写。作废依据与继承边界见 v2.5 **14.2 / 14.3**，路线改由 **D5 / D6** 承载。本节 A1 前半部分（资产盘点、多账本口径冲突、生产 schema 落后教训）**仍然成立**，被推翻的只有"因此应当复用它"这一条推论。

## C. 结构性缺口（修订时需新增的章节）

1. **六面导航与信息架构**：HomeOS 底部 Tab 五个入口如何容纳七个系统（3.5 未答）。这是 B20 里最硬的一条，属 P0。
2. **权限矩阵**：角色（管理员/成人/儿童/老人/访客/已退出成员）× 七系统 × 动作（读/写/删/导出/邀请）。
3. **数据归属权威表**：每个实体 → 归属系统 → 他面访问方式（读引用/订阅事件/禁止）。解决 B5/B6/B7/B10。
4. **跨面对象注册契约**：六面的到期型对象如何注册到 HomeOS Todo/Reminder/Calendar，字段映射与删除语义。解决 B8/B9。
5. **验收口径表**：每条验收补「度量定义 + 分母 + 采样方法 + 判定人/判定方式」。解决 B13。
6. **外部依赖清单**：依赖项、供应商、成本、失败降级、合规。解决 B16/B17。
7. **数据分级与合规专章**：对象级加密策略、儿童数据、搜索与 E2E 的可行性方案、审计与保留期、RPO/RTO。解决 B15/B18。
8. **技术约束章节**：PRD 不必选型，但应给出约束（是否复用既有 Go+Postgres+uni-app 栈、是否复用 family-ledger 部署体系、Agent 研发流程载体）。当前 PRD 对此完全沉默，导致 Architect Agent 无法开工。
